  2. 02

07 / 长任务 · 架构判断

goal 防止早退，但不会扩大上下文窗口

单体应用中持续使用 goal，会不断触碰到主编排会话的上下文窗口限制，导致漂移。

持续推进

目标要求不断续跑

一轮未完成就进入下一轮，执行链路不断延长。

集中承载

主会话累积全局信息

任务分派、实现细节、测试结果和返工历史汇到一处。

窗口触顶

历史反复压缩与交接

必须在有限上下文里取舍，重要约束不总能完整保留。

目标漂移

局部进展替代整体完成

容易丢失待办、重复劳动，或偏离原先的验收边界。

关键不只是让模型“再坚持一轮”，而是让长任务不依赖一个会话记住全局。

分析口径

本页是长任务的架构判断，用于解释单体持续执行的漂移风险；不把上下文触顶与某次失败之间的因果关系当作已完成的量化实验结论。goal 约束解决完成条件，不能消除单会话的上下文容量边界。

08 / AUTO 为什么在长任务上占优

fanout 分担上下文，程序承担持续编排

模型负责理解目标、提出拆分和执行任务；程序而不是主模型会话，负责维护执行状态与调度。

程序编排 / Runtime

状态 · 依赖 · 调度

接收模型的任务拆分，校验后推进各个节点；
不要求一个持续膨胀的模型会话维持整张任务图。

↓ fanout ↓
Agent A子任务 / 局部上下文
Agent B子任务 / 局部上下文
Agent C子任务 / 局部上下文
↓
合并 → 整体验收 → 定向返工验收 Agent 检查业务目标，Runtime 管理后继执行
  1. 01
    每个 Agent 只承载必要上下文

    把可独立工作拆出去，减少主会话信息堆积与重复读取。

  2. 02
    执行进度不只存在模型记忆里

    任务图与运行状态由程序管理，长程推进更可控。

  3. 03
    局部完成后仍要对整体负责

    把合并、验收、修复串起来，避免子任务完成就提前收工。

任务越长、越能拆分、越需要整体验收，编排的质量与 token 收益越容易显现。

架构依据

AUTO 并非没有模型参与规划：模型提出 single / fanout 和后继路由，Runtime 校验并调度。fanout 分支使用隔离工作区；验收 Agent 判断业务质量，程序负责协议和执行约束。整项需求的统一收尾验收由路由提示词约定。

依据：AI-DYNAMIC 产品设计（调度、fanout、验收与状态管理）。示意图表达职责分工，不表示每次 AUTO 都会产生三个并行分支。
