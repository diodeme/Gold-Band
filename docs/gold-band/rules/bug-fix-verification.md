# Bug 修复验证规则

本文件是 Gold Band Bug 根因验证、修复前复现和回归验收的详细规则真源。

## 1. 先验证根因，再修改实现

- 完成原始设计意图和缺陷形成路径分析后，应优先编写范围最小的失败测试复现问题。
- 必须先观察测试在未修复实现上稳定失败，并确认失败位置、错误信息和状态变化与根因分析一致，才能开始修改实现。
- 测试不得因为 fixture 错误、环境缺失、等待超时或无关断言失败而被当作 Bug 复现证据。
- 如果测试结果否定原分析，应回到根因分析，不得继续按原方案实施补丁。

## 2. 复现测试选择

- 优先在拥有 canonical state 或业务不变量的接口层复现；竞态、生命周期和持久化问题必须固定 identity、revision、sequence、状态转换或写入顺序。
- UI 问题除接口或状态机测试外，应增加范围最小的 DOM/交互测试，验证用户实际可见结果；不得只断言内部布尔值。
- 性能 Bug 必须先记录数据规模、基线和验收目标，再使用 benchmark、Profiler 或性能时间线复现，不得把普通功能测试耗时当作性能证据。
- 复现测试只构造触发根因所需的数据和事件，不复制完整生产历史或依赖不稳定的固定延迟。

## 3. 无法自动复现时的例外

- 只有在问题依赖不可控制的外部系统、硬件、一次性损坏现场或自动化成本与风险明显不相称时，才允许先不建立自动失败测试。
- 使用例外前必须向用户说明无法可靠自动复现的具体原因，并保留可审计的替代证据，例如结构化日志、持久化快照、协议帧、崩溃转储、最小手工步骤或前后状态对比。
- 例外不免除修复后的回归验收；能够抽取稳定接口或状态转换时，仍必须补测试固定可预防的根因。

## 4. 修复与转绿

- 实现只能修复失败测试所证明的根因，不得为通过单个断言加入特例、名称匹配、固定延迟或旁路状态。
- 修复后必须使用同一复现测试确认由红转绿，并运行受影响领域的既有测试，检查没有破坏相邻不变量。
- 修复过程中若发现第二个独立根因，应分别建立失败证据和验收，不得让一个宽泛测试掩盖多个问题。
- 最终验收必须记录复现测试修复前的失败证据、修复后的通过结果及相关测试范围。
