# 数据加载与渐进加载规则

本文件是 Gold Band 跨前端、Tauri IPC、后端服务、数据库和文件系统的数据加载边界、渐进加载、分页、刷新与性能验收真源。

## 1. 先定义数据规模和关键路径

- 涉及应用启动、页面进入、列表、选择器、目录、历史、详情、搜索、诊断或后台刷新时，必须先列出业务实体、权威事实源、消费字段、当前规模、增长上限和调用频率。
- 必须明确用户完成当前操作所需的最小数据，以及可以在首屏后、展开后、滚动后或进入具体功能后再加载的数据。
- 只要数据量会随 workspace、task、run、session、文件、日志或时间持续增长，就不得把全量读取放进首屏或基础交互关键路径。
- 数据规模有严格小上限、单次读取有明确时延预算且实测稳定满足时，可以保持一次性加载；必须记录上限与依据，不得为了形式机械拆分接口。

## 2. 按数据重量拆分接口

- 先定数据结构，再定接口：`List/Summary` 只包含稳定 ID、名称、状态和必要展示字段；`Detail` 返回单个实体完整配置；`Content` 承载正文、日志、Raw frame、工具输入输出等大字段；`Locator` 只保存稳定定位信息。
- 页面只需要名称、数量或状态时，不得调用返回完整正文、完整任务树、全部运行历史或每条记录详情的聚合接口。
- 列表加载不得对每条记录执行详情查询；发现 N+1 时应调整批量摘要接口、查询投影或索引，而不是在调用端增加并发掩盖问题。
- 读取 DTO 必须按消费重量设计，不能直接序列化完整持久化结构。索引、数据库摘要表和缓存只能作为 canonical state 的可重建投影，不得成为第二事实源。
- 不得让一个原子响应同时绑定“基础身份可见”和“全部重数据就绪”；不同重量、不同可见时机的数据必须拥有独立加载和失败边界。

## 3. 渐进加载顺序

默认顺序如下：

1. 先返回应用壳、作用域身份和轻量列表，使用户立即看到真实 workspace、导航和基础状态。
2. 再加载当前可见领域、当前选择或最近数据的首批摘要。
3. 用户打开、展开、滚动到边界或进入对应 Tab 时，再加载详情、历史和正文。
4. 诊断、能力发现、索引维护、预取和非当前领域数据在关键路径外独立执行，并以局部增量合并结果。

附加约束：

- 独立请求应并行执行，存在依赖时才允许串行；不得制造无意义 waterfall。
- 同一作用域的重复加载必须 single-flight 或合并，不能因多个 effect、事件或刷新入口并发执行相同全量扫描。
- `not-loaded`、`loading`、`ready-empty` 和 `error` 必须是可区分状态；不得把尚未加载投影为“没有数据”，也不得因局部失败清空已成功加载的基础数据。
- 渐进结果必须按稳定 identity 和 revision/generation 单调合并；迟到响应不得覆盖新选择或较新的 canonical state。

## 4. 大列表、历史和缓存必须有界

- 会话、运行历史、Activity、Raw frames、日志、大目录和搜索结果必须使用 cursor 或等价稳定定位分页。
- 首批只返回当前视口和正常操作足够的数据；旧数据在接近边界或用户主动请求时继续加载。
- 分页顺序、去重、合并和裁剪必须基于稳定 identity；不得切开同 revision 的原子事件组或破坏阅读锚点。
- 客户端和服务端缓存、分页窗口、队列与预取都必须有容量、淘汰和背压边界，禁止随历史无限增长。
- 不得默认用缓存修复慢加载；应先减少数据量、扫描范围、解析次数和刷新范围。只有重复读取确为瓶颈且一致性、失效和容量边界明确时才增加缓存。

## 5. I/O、查询和后台工作不得阻塞关键路径

- 主动检查全量目录扫描、全表扫描、重复 JSON 解析、逐项 stat/read、N+1 查询、同步网络请求和长时间持锁。
- 文件系统遍历、批量解析和重型 ViewModel 构建必须进入 blocking pool 或后台 worker，不能阻塞桌面 IPC 事件线程、UI 主线程或 runtime 调度线程。
- 普通列表和详情读取不得顺便执行迁移、修复、索引重建或写回；维护工作应有独立生命周期和失败隔离。
- MCP 健康检查、Agent Doctor、provider 能力发现、更新检查和索引回填等可变后台工作不得成为基础数据可见的前置条件，也不得以无界并发争抢首屏 I/O、CPU 或进程资源。
- 单个数据源、workspace 或记录失败时，应返回逐项结构化结果或保留其他已加载数据；只有整体无法继续时才允许命令级失败。

## 6. 刷新限定到最小作用域

- 写操作成功后优先使用接口返回的最新权威实体局部收敛；确需重读时只刷新对应实体、分页或领域。
- 已有可展示数据时，后台刷新不能让界面退回全局 Loading，也不能替换用户当前选择、展开状态或滚动位置。
- 同一刷新最多一个 in-flight；重复触发合并为至多一次后续刷新。快速切换作用域时使用 request ID、generation、revision 或取消机制拒绝迟到结果。
- 实时状态优先通过携带完整 locator 的增量事件更新，不轮询或重新加载完整列表、历史和正文。

## 7. 性能验收与回归

- 性能问题必须记录可复现的数据规模、冷/热基线、关键路径耗时和目标；不得只以主观“感觉更快”验收。
- 验收至少证明：基础身份或首批摘要先于重数据可见；首批请求不读取每条详情或全部历史；非当前领域不进入关键路径；重复触发不会产生并发全量加载；局部失败不清空已就绪数据。
- 数据规模或 I/O 风险明显时，使用生产构建、结构化 timing、Profiler、数据库查询计划、benchmark 或系统 I/O 证据验证；低风险且上限明确时，不要求增加无意义 benchmark。
- 回归测试应从接口层固定返回字段、分页边界、请求次数、加载顺序和迟到响应规则；UI 场景再补充用户可见的 loading、empty、error 与渐进呈现测试。
- 优化不得破坏 canonical state、数据完整性和可维护性；优先修复数据量、算法、接口重量、刷新范围和状态边界，不使用盲目并行、预取、缓存或微优化掩盖设计缺陷。
