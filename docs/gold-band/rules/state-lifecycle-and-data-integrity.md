# 状态、生命周期与数据完整性规则

本文件是 Gold Band 实体身份、权威状态、异步收敛、持久化、原子写入、错误隔离和资源边界的详细规则真源。

## 1. 先定数据归属与事实源

- 实现前先列出业务实体、所属领域、生命周期和持久化要求，再定义接口与实现。
- 生命周期相关的数据结构必须由同一领域统一管理，不能由页面、通知、运行时各自维护一套事实。
- 每项状态必须明确唯一权威来源、允许的写入者、状态转换和恢复方式。
- 展示模型、缓存、诊断事件和 optimistic state 都是投影，不得反向成为业务事实源。
- 新方案明确替换旧模型时，应删除旧字段和旧消费路径，不建立双写或长期兼容旁路。

## 2. 稳定身份与完整作用域

- 实体关联必须使用稳定 ID，禁止使用名称、显示文本、数组位置、当前选中项或模糊路径反查。
- 标识必须覆盖完整作用域；会话、通知、缓存、路由和去重 key 至少包含其所属 workspace/project 及业务 locator。
- Task、Run、Attempt、Session 和 Branch 等层级对象必须使用完整 locator，不得只传末级 ID 后依赖全局搜索。
- Windows 路径大小写、分隔符、相对段和软链接必须先规范化，再参与相等判断、缓存 key 或资源身份生成。
- 重命名只能改变可变展示字段；稳定身份和已有引用不得随名称变化。

典型验收：两个 workspace 中存在同名或同末级 ID 的资源时，读取、通知、编辑和事件路由仍严格隔离。

## 3. Canonical State 与统一生命周期

- 后端 canonical state 或 durable lifecycle 是最终权威，UI 只根据它进行投影。
- 一个业务对象只能有一套权威生命周期状态机；Direct、Workflow、AUTO 等模式不得建立语义不同的旁路状态机。
- `status` 表示生命周期，`outcome` 表示终局结果；非终态不得提前写入 outcome，终态不得缺少 outcome。
- `accepted` 只表示操作已被可靠接收，不等于后台执行已经开始或完成。
- 停止、继续、重试、恢复、通知、侧边栏状态和页面详情必须从同一生命周期事实派生。
- 诊断、日志和 provider response 可以解释状态，但不能代替 canonical state 推进控制流。

## 4. 异步状态单调收敛

- 快速切换、并发请求、snapshot/live 交接和后台校准必须携带 request ID、generation、revision、sequence 或 CAS 条件。
- 旧请求、迟到失败、旧 snapshot、旧 permission 和旧 live event 不得覆盖更新事实。
- 合并必须单调：revision 和 sequence 只能前进；`cancelled / failed / completed` 等终态不得回退为 processing。
- Snapshot 与增量事件交接必须定义水位、缺口追平、取消和超时语义，不得依赖固定延迟猜测“应该已经同步”。
- 分页不得切开同 revision 的原子事件组；合并和裁剪必须保留稳定身份、语义顺序及阅读锚点。
- UI optimistic state 收到权威响应后必须收敛；失败时只回滚本次操作，不覆盖其间到达的新状态。

## 5. Durable 与 Transient 分层

- 设计状态时必须先判断进程重启、页面卸载或会话切换后是否仍需恢复。
- Prompt identity、取消结果、pending interaction、任务队列和已接受操作等恢复所需事实必须 durable。
- Hover、临时 loading、当前展开项等仅服务当前视图的状态应保留在运行期。
- 用户草稿和布局偏好只有在跨页面或跨会话仍有明确价值时才持久化，并提供 schema、默认值和版本策略。
- 关键事实应先可靠落盘，再发布 UI/live event；不得先广播成功后补写持久化。
- 不得依赖短生命周期组件、内存 runtime 或扫描展示 timeline 恢复业务身份。

## 6. 原子写入、幂等与并发冲突

- 涉及多个文件、目录、索引、软链接或状态记录的操作必须作为一个事务设计。
- 根据存储类型使用临时文件加原子替换、数据库事务、唯一约束、revision/CAS 或原子目录占位。
- 写入顺序必须保证任意一步崩溃后都能识别、继续或回滚，不能留下不可判定的半完成状态。
- 创建、保存、重命名、同步、停止、关闭、恢复和重试必须定义重复调用语义，并尽可能幂等。
- 并发创建不得仅根据当前选中 ID 或一次未加锁的最大编号查询推导新 ID。
- 锁只覆盖需要原子性的最小资源和写入区间，不得把网络调用、provider 执行或长计算纳入临界区。

## 7. 局部失败隔离与结构化错误

- 单条坏数据、单个 provider 或单项导入失败不得使整个列表、页面或批次不可用。
- 批处理接口返回逐项结构化结果；只有整体无法继续时才返回命令级错误。
- 后端只返回稳定错误码和结构化参数，不生成对客文案；前端负责本地化、展示位置和可执行恢复动作。
- 应区分 unknown、stale、unsupported、unavailable、invalid 和 execution failed，不得把无法确认误报为执行失败。
- 已有可用数据时，局部错误不得清空页面或触发全局刷新；错误应显示在用户当前可以处理的位置。
- Provider 和 terminal failure 必须保留原始结构化原因，不得被兜底成功、通用错误或后续旧事件覆盖。

## 8. 能力发现与资源信任边界

- Catalog 和静态配置是候选模板，不代表当前运行实例一定具备相应能力。
- Session 恢复、模型、思考强度、权限等运行能力以 provider/doctor 实际返回的 capability 为准。
- 不得根据 Agent ID、名称或某个 provider 的历史行为猜测另一实例的能力。
- 前端只提交稳定资源 ID 和必要意图；后端解析真实路径并校验 canonical root、软链接、路径分隔符和越界访问。
- 平台差异、进程创建和路径规范化必须集中到统一适配层，不得散落为调用点特判。

## 9. 接口设计与回归验收

- 写接口应接收用途明确的 command/authoring DTO，不能直接复用完整持久化结构作为输入。
- 写操作成功时返回最新权威实体、revision 或 operation ID，供调用方局部收敛。
- 长操作应区分 accepted、progress 和 terminal result，并提供稳定 operation identity。
- 每次修复身份、生命周期、竞态或持久化问题后，都必须增加接口级回归测试固定根因。

至少覆盖与改动相关的场景：

1. 同名资源跨 workspace 不串数据。
2. 旧请求晚返回不覆盖新选择或更新终态。
3. 终态不被旧 processing snapshot 回退。
4. 重复取消、保存、关闭或恢复保持幂等。
5. 多资源写入中途失败后能够安全恢复。
6. 单条损坏数据不影响其他条目加载。
7. 缺失 capability 返回稳定结构化错误。
8. 路径大小写、分隔符和软链接变化不突破资源边界。
