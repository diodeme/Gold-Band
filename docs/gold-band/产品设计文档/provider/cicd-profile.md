# CI/CD 内置角色

## 目标与边界

仅 `wb` 内部渠道用户可在自行编排的工作流节点上绑定内置 `pf-builtin-cicd`；WeTest 依赖内部服务与网络环境。角色默认任务为构建 + 部署，构建后核实成功并推送物料，再部署至终态；具体范围由人类指令和节点 task / goal 确定。角色展示名为 `CI/CD`，不加入默认工作流，不新增 CI/CD 节点类型、执行器或专用授权状态机。

部署支持按构建和按包名两种方式，默认向用户推荐按构建部署；两种方式都须交互确认，配置预填不能代替用户选择。按包名使用本次构建产物时，先构建与推送再核实真实包名；使用已有包时询问是否仍需新构建，只有明确指令才能省略构建。

发布计划回归部署 / 审批、触发自测、查询自测和跑批均为选配，可询问用户是否追加，不主动执行。未选择时不发起、不查询、不等待，也不影响主任务完成；已选择执行自测时，必要的状态查询包含在该选择内。

复用现有 Profile 注册、按语言选择正文、稳定 ID 引用及 runtime 输出契约。角色属于 system prompt 中稳定执行方法；本次业务参数和目标属于 user prompt。正文以 `src/prompts/zh-CN/profile/cicd.md` 和 `src/prompts/en/profile/cicd.md` 为真源，作为静态角色关闭动态模板。

## 渠道可用范围

- 内置角色 seed 通过 `release_channel` 声明可用渠道；公共角色为 `None`，CI/CD 为 `Some("wb")`。
- 复用现有 dev/build 渠道脚本传入的 `GOLD_BAND_RELEASE_CHANNEL`，在 core crate 编译时通过 `option_env!` 固定选择，缺省为 `default`。不依赖可变运行时环境、用户设置、前端过滤或名称判断。
- 角色列表、内置 ID 查找和默认 Profile ID 映射共用同一过滤后的目录。`wb` 提供 10 个内置角色，`default` 及其他渠道提供 9 个公共角色；未知渠道不提供 CI/CD。
- 工作流角色解析及节点执行前读取复用该目录。非 `wb` 渠道引用此内置 ID 时沿用现有角色不存在的处理，不增加替代角色、兼容层或隐式回退。

## 能力与参数

基于用户提供的 wetest-cli skill 1.1.0 及其 CLI 0.2.9 命令参考，收录 build、deploy、weflow、batch 四域。角色正文自包含关键参数，不依赖外部 skill 的本机路径。CLI 安装、内网接入、鉴权和 Agent 命令能力均为实际运行前提，角色绑定本身不提供这些能力。

两份 `memory.json` 职责分离，不做通用的覆盖合并：

- 项目根目录文件记录所属子系统参数 `sub_sys`，允许单个子系统或多个子系统列表。只读取项目归属，与用户确认本次选择，不能默认执行全部子系统；task 配置不能反向覆盖项目归属。
- 当前 task 文件记录可复用的构建部署参数，已有配置只用于本次 run 的交互预填，本次明确指令优先。每次 run 都必须重新展示并确认构建、推送和部署的最终生效参数，即使与上一次 run 相同也不能复用上一次确认；用户可在确认时调整子系统、应用、分支、方式、模板、环境和目标。缺少文件时用双语角色正文中的同构 JSON 模板引导用户填写并生成。一次 Jenkins 构建可产出并推送多个子系统物料，因此顶层 `build` 只保存一次 Job、分支与 `app_list`；构建生命周期属于整个 task。
- 部署按子系统拆为 `deployments[]`。每项保存稳定的 `sub_sys` 及其独立 `mode`、模板 ID / 名称、部署类型、包名和有效目标，不能把一个子系统的模板或目标复用于另一个子系统。`mode` 取 `build` 或 `package`，模板预填 `build` 只是推荐值，不代表用户已经选择。
- Job ID、分支、构建覆盖的应用与子系统关系、部署模板、类型和实际目标均先核实。包名方式还需真实包名，等待本次构建产物时先标明待补项，产物就绪后更新对应部署项再执行；按构建方式不要求填写包名，但对应子系统必须属于已确认的构建和推送范围。
- 构建与推送按完整 `app_list` 确认一次。部署可逐个子系统确认，或完整列出所有部署项的模板、方式、物料与目标后一次批量确认；每项分别保存 aompJobId 与终态，局部失败不能被其他项成功掩盖，也不能自动重试。
- 仅使用 runtime 或用户明确提供的路径；确认参数后序列化写入 task 文件并回读，使用同目录临时文件与原子提交。创建前重查，已有文件保留其他用途数据，仅合并已确认的相关字段；不能安全处理并发变化时报告冲突，不盲目覆盖。
- 配置不存凭据、授权标记和运行状态。真实外部操作 ID、终态和参数来源证据保存在允许的附件，Gold Band runtime 继续拥有节点状态。文件生成属于角色引导的配置准备，未新增后端配置写入接口。

授权必须来自当前 run 对实际生效参数的明确人类确认；task 文件、上一次 run 的确认、默认值与角色绑定都不代表本次构建或部署授权。触发前核对有效环境、模板、实际主机或容器、物料来源、部署类型及授权覆盖；特别注意 env 对 ip/container 的覆盖。发布计划操作还核对审批含义和关联部署范围。所需授权缺失且无法交互时报告阻塞。

命令、子命令或参数有疑惑时，使用 `wetest <cmd> --help`，必要时继续查询子命令 help。动态发现仍遵循“查询自由、触发类确认”：按实际语义和副作用分类，触发作业或改变状态前需有覆盖有效参数的用户确认，不能仅凭命令名称判级，也不能试运行触发命令探测参数。已有同范围明确确认可沿用；选配范围、部署和审批的参数核对要求继续生效。

## 结果与恢复

- CLI 退出码和业务结果均成功只代表请求成功，构建、部署、自测需要另外验证远端终态。
- buildId、aompJobId、commandId 是各自平台操作的身份；附件保存执行证据，Gold Band runtime 继续管理节点 canonical state。
- 超时或响应丢失先查询核实，避免重复提交；恢复和新 Round 先检查前序操作。节点取消不等于远端作业取消。
- 轮询有间隔、总期限及剩余预算约束。Job 发现必须过滤分页；包列表仅必要时查询并提取目标证据。
- 报告遵守当前 artifact 契约，未执行、运行中、未知或失败不能映射成成功。

## 自评审与验收

现有 Profile 设计足以表达需求，仅在 seed 增加渠道可用范围，无需新增依赖、缓存、队列、runtime 持久字段或跨层 identity。task 模板使用一个 task 级 `build` 与按子系统展开的 `deployments`，分别对应真实生命周期与配置差异，不建立新运行状态；子系统身份仍来自项目 `sub_sys`。静态目录上限 10 项，过滤为 O(10)，非 `wb` 渠道不构造或传输 CI/CD 正文；不引入新的客户端 I/O、N+1、轮询或 React 订阅。角色实际配置准备只读取两个明确文件，并按已选子系统查询各自模板，处理和命令数量均为 O(所选子系统数)，不遍历全部项目或历史，不为此新增 benchmark。

接口测试在实际 `default` / `wb` 编译环境验证双语 list/show 内容映射、稳定身份、只读保护、工作流解析及默认工作流不自动执行 CI/CD；目录测试覆盖未知渠道仍保留公共角色。独立提示词契约测试固定默认构建部署、每次 run 的重新确认、历史确认不可复用、两种方式的交互确认、附加操作选配和项目 `sub_sys` 职责，并用 serde_json 验证双语模板一致具有唯一顶层 `build` 与逐子系统 `deployments`，且部署项各自拥有模板 ID 和名称。测试固定交付给 Agent 的契约，不等于已经验证 Agent 实际交互、文件写入或真实平台执行。
