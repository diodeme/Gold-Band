# 工作空间与任务记忆及 WB CICD 工作流

日期：2026-09-17。状态：共享记忆、正式 CICD 角色及 WB 工作流对接与本地验收完成；自动参数投影已移除，RuntimeManaged 按需读取与 Direct prompt 隔离已完成本地契约验收。真实模型及 WeTest 部署端到端验收待补。

本文是本需求的产品行为真源，依据逐轮需求拷问形成。代码与验收记录见末节；初始 CICD 交付不代表实际外部构建部署已验证。

实施清单见 [工作空间与任务记忆及CICD工作流实施方案](../../开发计划/新增流程/工作空间与任务记忆及CICD工作流实施方案.md)。

## 1. 目标与范围

记忆保存节点执行所需、由用户明确提供或确认的必要参数，支持跨节点传递和后续复用。主要使用场景是 CICD 角色通过提示词调用外部系统完成构建部署。

- 只保存必要输入，不保存模型总结、推断或执行结果；执行结果继续归属于节点产物和运行状态。
- 普通模式和 WB 模式均支持项目记忆设置、任务记忆和统一读写能力。
- Direct、Workflow、AUTO 共用同一机制。作用域以实际所属 task 为准，同一 task 内部执行共享任务记忆，不另建副本。
- 一个任务可以构建部署多个子系统。
- 子系统号、本次目标子系统、部署模板 ID、构建计划 ID 等业务参数的 key 和关联方式，由后续角色提示词契约定义。首版不预设环境分层或专用子系统数据结构。
- 只有 WB 模式提供 `subSysId1` 默认条目、内置 CICD 角色和“开发构建部署工作流”。
- 启用 `RequirementIdentity` 能力的采访和拷问节点在角色流程开始前检查任务作用域 `storyId`、`storyName`；缺失或不成对时通过结构化提问取得需求身份，选择“不存在”时写入 `0` 和从需求内容提取的简短名称。启用 `DevTestAutoCommit` 能力时，开发测试节点在可选入口关闭、身份仍缺失时自动兜底补齐。WB 当前同时启用这两项能力；具体渠道范围只在 `src/channel.rs` 的编译期能力矩阵中维护。

## 2. 数据归属与持久化

| 作用域 | 保存位置 | 用途与生命周期 |
| --- | --- | --- |
| 工作空间 | `<应用数据根>/projects/<project_id>/memory.json` | 跨任务复用的默认参数，绑定既有 canonical project_id |
| 任务 | `<应用数据根>/projects/<project_id>/tasks/<task_id>/memory.json` | 当前任务参数，随 task 持久保存 |

应用数据根复用产品既有路径解析规则，例如用户目录下 `.maling` 或 `.gold-band`；不得硬编码用户目录、显示名称或示例 project_id。关联使用完整项目与任务 locator，不新增平行业务身份。

每条记忆有三个业务字段：

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| key | 字符串 | 文件内唯一，最多 128 个字符 |
| value | 字符串 | 最多 4,000 个字符；空字符串或纯空白视为尚未提供有效值 |
| desc | 字符串 | 最多 500 个字符，描述该参数用途 |

不支持任意 JSON 对象或数组作为 value 类型。文件顶层封装、版本校验方式及序列化细节由实施时结合现有持久化机制确定，不能把接口输入直接等同于整个持久化文件。

任务记忆跨节点、重试、重新运行和后续对话保留。新建 task 不继承其他任务记忆，只读取工作空间默认值。task 删除后，其记忆随 task 生命周期失效；仍存活的任务绑定读写工具必须返回 locator 错误，不得把丢失的 task 目录当作首次初始化并重建记忆。任务删除与记忆读改写使用同一项目级锁边界，锁只覆盖目录删除或短暂文件操作。

### 2.1 WB 默认条目

WB 工作空间首次初始化记忆时必须创建：

```json
{"key":"subSysId1","value":"","desc":"xxxx子系统"}
```

已有工作空间首次初始化记忆时同样适用。之后允许用户修改、删除，不自动补回。空值不能作为有效参数使用。普通模式不自动创建此条目。

初始化必须幂等，区分首次初始化与已初始化后的空集合；不得在每次打开设置或执行节点时反复补写默认项。

实施边界：以文件是否首次创建为准。普通模式已经初始化的文件在切换 WB 后保留原集合，不补写默认项。

## 3. 有效记忆与作用域规则

1. 任务不存在同名 key 时，使用工作空间值。
2. 任务存在同名 key 时，使用任务值，包括空值。
3. 任务空值不回退到工作空间默认值，而是按缺失参数处理。
4. 节点获得用户回答后，默认将本次参数或纠正结果保存到任务记忆。
5. 只有用户明确要求长期复用或修改项目默认配置时，才更新工作空间记忆。

WB 工作流的固定 key 作用域：

| 参数 | Scope | 写入方与生命周期 |
| --- | --- | --- |
| `subSysId1`、`subSysId2` 等 | workspace | 项目子系统清单，由项目记忆设置维护 |
| `storyId`、`storyName` | task | 当前任务需求身份，由采访、拷问或开发测试维护 |
| `cicd.build.*` | task | 当前任务构建参数，由 CICD 按本次确认值维护 |
| `cicd.deploy.<S>.*` | task | 当前任务逐子系统部署参数，由 CICD 按本次确认值维护 |

CICD 不把任务生效的 `cicd.*` 参数写入工作空间默认值。跨任务复用的 Job 或模板默认值必须使用独立默认 key，不得与任务生效参数混用。

例如工作空间 `buildPlanId=B1`，任务 `buildPlanId=B2`，当前任务使用 B2；任务将该值清空后应补问，不能继续使用 B1。这里的 key 仅作示例，不定义最终 CICD 参数契约。

用户回答本身可以构成确认，不机械增加二次确认。模型推断不能自动成为已确认事实。

## 4. 统一读写与并发

- 模型通过应用提供的统一工具读写记忆，设置页复用同一领域写入入口；不让模型直接覆盖 JSON 文件。
- 模型决定保存哪些 key 及其作用域，应用负责作用域校验、字段与容量校验、并发冲突检查和原子落盘。
- 按 key 更新，不将旧的整份表单或文件覆盖为最新状态。
- 不同 key 的并发修改自动合并。
- 同一 key 在读取后被其他写入者修改时，拒绝覆盖并返回最新值，由用户或节点重新判断；不得盲目重试覆盖。
- 保存成功必须代表可靠落盘，工具与设置页收到最新权威结果后局部收敛。
- 冲突校验与写入需处于同一原子边界，锁只覆盖必要的短暂文件操作，不持锁等待模型、用户或外部系统。
- 后端返回结构化错误码与参数，前端负责本地化文案。

文件是权威保存源。角色通过工具读取成功后得到的快照只是本次执行中的短期上下文，不是新的持久事实源。不新增数据库副本、模式专属记忆层或后台同步队列。

### 4.1 已实现接口契约

- 文件 schema 为 `{version: 1, entries: [...]}`；条目除三个业务字段外携带不透明 `revision`，它只用于并发校验，不是另一套业务身份。
- 读取返回完整 locator、真实路径、两层条目、有效条目及统一容量配置。MCP 写命令为 `{scope, operation, key, expectedRevision?, entry}`：`operation=create` 且省略 `expectedRevision` 表示新增不存在的 key；`operation=update` 必须提供读取时的 revision 并更新已有 key；`operation=delete` 必须提供 revision 且 `entry=null`。不得把字符串 `"null"` 当作缺失 revision。
- 修改 key 时在同一原子边界校验原 key 版本及新 key 不存在，再执行重命名；目标已存在时返回冲突，不覆盖目标。
- 复用 `atomic-write-file` 落盘，使用 `fs2` 项目级文件锁串行化两个作用域的短暂读改写。任务记忆落盘不自动创建父目录，task locator 在锁内重新校验；任务删除持有同一锁，因此删除后的迟到工具调用不能复活任务目录。MCP helper 与桌面设置使用相同锁；不同项目独立，不持锁等待外部调用。
- 标准 MCP 工具为 `memory_read`、`memory_write`，通过官方 Rust SDK `rmcp` 实现 stdio。持久化的内置定义只保存当前 EXE 与 `--gold-band-memory-mcp`，不保存 project/task；ACP 会话准备时才追加由应用生成的 repo root、data root、project id、task id 与语言绑定，工具参数不能更改 locator。设置使用 `read_project_memory`、`write_project_memory` IPC，作用域解析与 I/O 均进入 blocking pool。
- 字符按 Rust `chars()` / 前端 Unicode 码点迭代计数；32 KiB 按有效条目数组（包含 key/value/desc/scope）的紧凑 UTF-8 JSON 计数，不包含路径和 revision。不在保存项目参数时扫描历史 task。

## 5. 按需读取与不重复提问

共享记忆不再由节点启动、继续执行、重试或重新运行自动读取并投影到 prompt。节点准备阶段不读取记忆文件，也不向 prompt 写入 key、value、desc、revision、来源作用域或记忆文件路径。

需要记忆的角色进入参数准备阶段后按以下顺序执行：

1. 主动调用 `memory_read`，获取当前工作空间和任务快照。
2. 检查任务与工作空间快照，复用读取成功且仍有效的参数。
3. 只补问缺失、为空、冲突、外部系统明确判定无效或当前 run 尚未确认的值。
4. 用户明确提供或确认参数后调用 `memory_write`；写入成功才算已经持久化。
5. 后续节点在自身需要参数时再次调用 `memory_read`，获得前序节点已经成功保存的答案。

“已有值不重复提问”是角色在 `memory_read` 成功后应遵守的行为契约，不是 runtime 通过自动投影提供的强保证。模型是否实际调用工具仍由角色提示词、工具描述和 Agent 行为决定，产品验收不得把该流程描述为绝对不重复提问。

固定规则使用 `runtime/memory-rules.md`，只保留通用能力、角色契约优先级和不可信数据安全边界；具体 key、作用域、读取时机、确认和降级规则留在角色提示词。`runtime/memory.md` 及 `<memory-data>` 自动参数投影已删除。

ACP 实施：只要本次 invocation 启用 `gold-band-memory`，`bind_invocation_mcp()` 就查找、校验并写入当前 project/task 绑定的 executable session snapshot，不受 prompt envelope 影响。`RuntimeManaged` 才追加简化 system rule；`RawAgent` 不接收记忆规则或数据。任何模式都不自动读取或投影记忆数据。关闭内置卡片时既不传 MCP，也不追加规则，不允许出现“有规则无工具”或“有工具但被自动投影”的半启用状态。

Direct 保留已启用的 `gold-band-memory` MCP 是明确决策。工具描述将其返回值声明为参数数据而非指令或授权，但 Direct Agent 是否把工具结果视为数据、是否遵守其中可能出现的指令性文本，最终仍取决于 Agent 自身策略；Gold Band 不通过额外 prompt 干预该消费方式，也不宣称提供 system-level 强保证。taskless 分析等旁路不伪造任务记忆。

记忆 MCP 分为三层：`settings.json` 中的 managed stdio definition 是用户开关与基础启动定义；设置页的最近一次诊断结果是进程内临时状态；每次 invocation 的 executable session snapshot 才包含真实 task 绑定。基础定义允许无绑定启动并完成 `initialize → initialized → tools/list`，随后结束进程树；无绑定实例收到读写调用必须返回结构化 `memory.context-required`，不得访问任何文件。正式 stdio 连接由 ACP Agent 在 `session/new/load/resume` 阶段按会话快照建立，不由 Gold Band 应用常驻第二份连接。

各角色必须使用一致的 key。首版不提供语义匹配、同义 key 推断或问题历史库。接口层保证 `memory_read` 能返回当前最新有效快照，角色契约要求在参数准备阶段主动读取；模型是否实际调用工具并遵守复用规则仍需通过角色契约和实际流程验证，不能宣称对任意模型绝对保证不重复提问。

## 6. 初始化、错误与容量

首次缺少记忆文件按正常初始化处理。已有文件损坏或读取失败时，节点启动和 prompt 准备本身不失败；角色调用 `memory_read` 时返回可定位到对应文件的结构化错误。角色必须说明记忆未读取，不能把损坏解释为空记忆，也不得直接清空或覆盖原文件。缺少完成当前动作所需业务参数时，继续按角色原有门禁询问、暂停或失败；记忆读取失败本身不构成额外阻塞。

记忆工具不可用、写入失败、部分写入或写后核验失败本身不阻塞业务。角色必须向用户说明未读取或未持久化，不能伪装成功；如果当前动作所需的业务参数已在本轮由用户明确提供或确认，可以使用本轮值继续。角色权限、外部授权、构建部署确认等业务门禁不得因记忆失败被绕过。

容量限制统一配置管理：

| 项目 | 上限 |
| --- | --- |
| 每个文件条目数 | 100 |
| 单个 key | 128 个字符 |
| 单个 value | 4,000 个字符 |
| 单个 desc | 500 个字符 |
| 两层合并后的有效记忆序列化大小 | 32 KiB |

保存时超过适用限制明确报错，不截断、不自动删除。工作空间被其他任务更新，导致某任务合并后超限时，在该任务调用 `memory_read` 时返回容量错误；节点启动不扫描全部历史任务检查组合。

字符计数口径与有效记忆序列化口径需在接口契约中统一并测试。32 KiB 是数据容量上限，不是固定 token 预算。

## 7. 项目记忆设置

- 每个工作空间右侧新增书本图标按钮，打开标题为“项目记忆设置”的右侧抽屉；该按钮与新增会话、删除工作空间按钮在同一悬浮操作组中展示，点击不触发同一行的工作空间展开/收起行为。
- 复用 shadcn/ui Sheet、表单、图标按钮、Tooltip 及现有主题能力，不自研基础控件。
- 每条展示 key、value、desc，支持新增、修改和删除。
- 逐条保存或取消，删除单独确认；单条失败或冲突不影响其他条目。
- 冲突采用最新值时以后端结构化原因与权威记录收敛。普通 revision 冲突若权威 key 已变化，原行按权威 key 重投影并去重；重命名目标已存在时，后端未执行写入，界面必须保留原 key，并只更新已存在目标 key 的权威记录，不能吞掉原行或假装重命名成功。
- 关闭时若存在未保存内容，提示用户处理。
- 只在打开时加载当前工作空间记忆，不将记忆加载加入工作空间列表首屏路径。
- 抽屉的目标 locator 由稳定 WorkspaceShell 布局层持有，表单草稿留在抽屉/行内；侧边栏因窄窗口卸载时，抽屉和草稿不能被卸载。
- 首版不提供任务记忆管理界面；任务记忆由节点通过统一工具维护。

响应式、焦点、加载与错误反馈等遵循 [UI 交互规则](../../rules/ui-interaction.md)。

## 8. WB CICD 角色与工作流

新增内置角色 CICD，以及“开发构建部署工作流”：

```text
grill -> dev-test -> accept -> CICD -> 结束
```

前序节点与默认轻量工作流一致，复用其可选拷问入口、验收行为和验收失败后的修正路径。验收成功直接进入 CICD；CICD 节点默认不配置 AI 输出验证，会话自然结束后由用户人工判断成功或失败。

CICD 人工判定失败或执行阻塞时展示原因，用户处理后可以仅重试该节点；不自动回到开发节点，不自动重复构建部署。人工判定失败没有显式 failure edge 时按现有控制契约结束工作流。实现需核实并复用现有节点重试和 durable lifecycle，不能单靠提示词模拟停止或成功。

### 8.1 一起交付与正式角色边界

记忆功能、WB 内置 CICD 角色及新工作流一起交付，不拆成两次产品交付。

正式 WeTest 角色已经合入，现已完成共享记忆对接：

- 进入参数准备阶段后先调用 `memory_read` 获取快照，针对已明确需要且缺失、冲突或当前 run 未确认的参数补问并保存回答。
- 只有外部系统调用方式和成功判据明确时才执行构建部署。
- 必要参数、能力或授权缺失时报告具体阻塞；不能把参数收集完成当作部署成功。
- 双语角色统一使用共享记忆工具，不再自行维护另一种 task 配置文件。

正式对接：WeTest 双语角色已接入共享记忆工具。WB 默认模板的 CICD 节点改为人工 check，不配置 `output`、`success_condition` 或 `cicd-result`；自定义节点显式配置 AI 输出验证时仍保留既有产物与控制结果校验。CICD 单次提交，失败通过既有人工恢复生命周期处理；不触发自动产物补问或 provider 自动重试。

WB 需求身份与提交职责：采访、拷问通过 `memory_read` 检查任务作用域 `storyId/storyName`，缺失时以“不存在 / 其他（用户自行输入）”语义提问并写任务记忆；开发测试在节点成功收尾时自动按具体路径提交本次任务改动，生成 `--story=[{storyId}] {storyName}`、`{type}: {中文描述}`、`#AI COMMIT#` 三行提交并报告 commit OID。CICD 只检查这些提交是否已推送；拒绝 push 或 push 失败时必须询问用户是否继续构建，选择继续后按远端现状推进。

上述行为实现为渠道中立的 `requirement-identity` 和 `dev-test-auto-commit` overlay。文件名、标题和正文不包含渠道名；Profile 组合根据 `ProfileChannelCapability` 决定是否追加，非启用渠道仍使用原基础角色正文。

CICD 使用两类字符串条目：整个 task 的唯一构建保存为 `cicd.build.jobId/branch/appList/appCoverage`，每个子系统部署保存为 `cicd.deploy.<S>.*`。S 为真实子系统 ID 的 UTF-8 百分号编码（仅保留 ASCII 字母、数字、连字符、下划线、波浪号，其余含点号编码为大写 %HH）。工作空间 `subSysId1` 等提供成员清单，任务 `cicd.deploy.<S>.selected` 表示部署选择而非授权。一次 Jenkins 构建可覆盖多个子系统，其生命周期归 task；模板、方式与目标归各子系统部署。列表及差异变量使用单字段 JSON 字符串，不存整份配置对象。字段表及 WeTest 方法见双语角色与 [CICD 角色设计](../provider/cicd-profile.md)。逐 key CAS 后刷新核实完整构建与所选部署参数；每次 run 必须重新确认生效范围，上一次 run 的确认不得复用。不得直接读写文件，容量限制不变。外部 ID、部分完成及终态证据存附件，人工恢复先查询已有作业。真实模型和平台链路仍需在具备环境与授权时验收。

## 9. 方案自评审

### 9.1 根因与设计方向

这是新增能力，不是已复现 Bug。原始“仅提供文件路径”的方案缺少稳定的读取时机、统一写入和冲突边界，不能支撑跨节点复用要求。采用统一文件服务与运行前上下文投影补齐契约，不依赖模型自行覆盖文件或零散提示词补丁。

### 9.2 复用与过度设计

优先核实项目已有 JSON 序列化、原子写入、工具注册、提示词渲染、内置模板和节点重试能力；前端优先现有 copy-in 组件。无需引入通用 AI 记忆框架、向量库、自动摘要、缓存、额外身份或状态机。具体工具接入与并发校验机制在实施前检查现有代码后确定。

### 9.3 性能影响

合并复杂度为 O(P + T)，P、T 各不超过 100。节点启动不再读取记忆文件或序列化 prompt 投影；只有实际调用 `memory_read` 的角色读取当前两个有界文件，不扫描其他任务或历史运行，不逐条请求。抽屉只加载当前作用域，保存只更新对应条目投影。文件操作不得阻塞 UI 或事件线程，锁内无用户等待、模型请求或外部网络调用。

移除自动投影后，普通节点不再承担两个文件读取、最多 32 KiB 有效数据序列化及对应 prompt token 成本。真正需要记忆的 CICD 和 WB 身份/提交角色增加按需工具调用，成本出现在实际消费点。采用 IndexMap 线性合并，不增加缓存、后台队列或历史扫描。

## 10. 验收原则

接口级测试应固定作用域隔离、优先级与空值、跨运行持久化、首次初始化与删除不补回、并发合并与冲突、保存失败、文件损坏及容量边界。流程验收须证明前序节点成功保存后，后序节点调用 `memory_read` 可以获得该值；读取成功后不重复提问属于角色契约保证，不是 runtime 强保证。

UI 验证覆盖逐行操作、关闭草稿、冲突、错误、窄窗口、长文本和主题。WB 工作流验证覆盖正常前序路由、验收后自动进入 CICD、配置缺失不误报成功、失败不自动重部署及人工重试。

实施后同步维护本文与开发计划，记录真实测试结果，不将计划项标为已完成。
