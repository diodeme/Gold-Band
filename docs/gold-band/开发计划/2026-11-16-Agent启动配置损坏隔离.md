# Agent 启动配置损坏隔离

## 根因

- 本机 `settings.json` 中，内置 Agent 由 Catalog 注入启动命令，而 `qoder`、`deepseek-harness`、`zcode-acp` 等自定义/Registry Agent 的 `adapter.command` 与 `adapter.args` 缺失。旧实现要求每个 `AcpAdapterConfig.command` 必填，导致整个 `SettingsConfig` 反序列化失败。
- Windows release 构建使用 GUI 子系统，`main()` 里的 `eprintln!` 不可见；配置解析失败后进程以 0 退出，用户看到的是点击启动没有反应。

## 方案

- `AcpAdapterConfig.command` 反序列化默认为空字符串：缺失启动命令的自定义 Agent 可以随 Settings 一起加载，其他 Agent 与应用启动不被单条损坏数据阻断。
- `ManagedAgentConfig::executable_adapter()` 在生成执行快照前拒绝空命令，返回结构化错误 `agent.launch-command-missing`；Provider Doctor 在生成执行快照失败时也返回不可用诊断结果，错误映射保留该错误码，前端按 locale 显示“补充命令后重新诊断”。
- Windows 致命启动错误在退出前显示原生 `MessageBoxW` 错误框；非 Windows 继续输出 stderr。
- 不猜测缺失的 qoder/deepseek/zcode 启动命令，不把它们加入内置 Catalog，也不自动改写用户 settings；用户在 Agent 管理中补齐后即可恢复。

- 同步 settings schema 13：本机较新客户端已把 settings 迁移为 v13。v12→v13 的唯一差异是内置 `codebuddy-code` 默认显示名 `CodeBuddy → WorkBuddy`；当前分支同步该迁移、Catalog 模板与文档，避免拒绝已迁移配置或产生半迁移状态。

## 验收

- 红测：`missing_custom_launch_is_isolated_to_the_execution_boundary` 在旧实现上稳定失败，错误为 `missing field command`。
- 转绿：同一测试验证内置 Claude 仍注入 Catalog 启动命令、缺失启动的自定义 Agent 可加载，并在执行边界得到 `agent.launch-command-missing`。
- 错误映射：`doctor_diagnostic_error_preserves_setup_error_codes` 验证 Doctor 保留结构化错误码。
- 诊断接口红测：`doctor_reports_missing_custom_launch_as_unavailable` 在旧边界上把 `agent.launch-command-missing` 逃出为 `Err`，修复后返回 `available=false` 与同码诊断错误。
- 桌面流程：当前 Debug 客户端从安装目录启动，读取既有用户 settings 后进程存活并创建主窗口；验证后正常关闭。
- schema 迁移红测：`settings_v12_renames_default_codebuddy_display_name` 在旧分支上因未执行迁移而失败，同步后转绿。
- 发布流程：重新执行 `npm run build:wb`，安装生成的 NSIS 包后从安装目录直接启动并确认主窗口。

## 自评审

- 过度设计评审：未新增 aggregate、迁移版本、缓存或兜底 Catalog；只把单条损坏配置的失败边界从应用启动下沉到该 Agent 的执行/诊断边界，符合既有作者态与执行快照分层。
- 性能评审：启动期仍是一次 settings 解析；空命令检查为 O(1)，原生错误框只在致命失败路径出现，无新增 I/O、扫描或后台任务。
