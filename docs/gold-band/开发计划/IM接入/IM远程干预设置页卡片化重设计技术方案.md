- 目标：在不改变 IM 功能、后端接口和持久化结构的前提下，重组企业微信与飞书设置界面的信息层级，并将渠道详情改为默认折叠的小卡片。

## 2. 问题与根因判断

现有实现按渠道纵向展示完整设置，但渠道身份、连接状态、接入操作、配置管理和通知偏好处于同一视觉层级；两个渠道同时展开时页面过长，用户难以先判断“哪个渠道可用、是否启用”，再按需进入配置。

这不是 IM Runtime、settings canonical state 或接口模型的根本缺陷。现有 `ImSettingsVm`、connection generation、通知草稿和扫码流程已经能够表达全部功能，问题来自前端信息架构与组件呈现不够完善。因此本方案只修正消费端投影和交互结构，不复制业务状态，不增加后端字段，也不改变扫码、启停、重连、绑定、删除或通知保存语义。

## 3. 设计目标与非目标

### 3.1 目标

1. 企业微信固定展示在飞书上方，两个渠道使用单列小卡片。
2. 卡片摘要区持续展示渠道名称、连接状态、渠道启用开关和展开按钮。
3. 每次进入设置页面时，两张渠道卡片均默认折叠。
4. 用户可独立展开任一渠道；展开状态互不影响。
5. 展开内容按决策顺序排列：状态与恢复引导 → 授权、接收账号与配置管理 → 通知类型。
6. 保留现有全部业务能力、错误处理、异步中间态、七语言和无障碍能力。

### 3.2 非目标

- 不调整 `ImSettingsVm`、Rust settings schema、数据库、keyring 或 connection generation。
- 不增加折叠偏好持久化、localStorage key、后端配置项或跨页面共享 Context。
- 不改变通知种类、默认通知值、保存方式和脏草稿语义。
- 不改变扫码授权 Dialog、重连、重新绑定、更换飞书应用、重新授权和删除确认流程。
- 不在本次重做 IM Runtime、outbox、connector 或平台卡片协议。

## 4. 数据与状态设计

### 4.1 权威业务数据

业务数据继续由现有 `useImSettings()` 提供，后端 `ImSettingsVm` 与 connection generation 是权威事实源。SWR 缓存、保存结果合并和 live snapshot 的单调合并逻辑保持不变。

### 4.2 页面临时 UI 状态

每个 `ImChannelEditor` 在自身最小消费边界维护：

```ts
const [open, setOpen] = useState(false);
const [configurationMenuOpen, setConfigurationMenuOpen] = useState(false);
```

- `false` 是组件每次挂载时的固定初值，因此每次进入设置页面时默认折叠。
- 离开设置页面导致组件卸载后，展开状态自然清理；再次进入重新初始化为折叠。
- 不根据渠道是否已配置、是否异常或是否存在 binding 自动展开，避免后台 snapshot、刷新或错误状态变化打断用户当前视图。
- 渠道数据刷新不得重置当前页面会话内由用户主动选择的展开状态；`key` 继续使用稳定的 `channel.kind`。
- 两个渠道分别持有局部状态，不实现手风琴互斥，允许用户同时展开。
- 配置菜单使用受控的 `configurationMenuOpen`；卡片从展开切换为折叠时同步关闭菜单，避免 Portal 浮层遗留在已折叠卡片之外。

扫码 Dialog、删除确认和重置确认仍由现有状态管理。折叠卡片时不取消正在进行的业务请求，也不关闭用户已经明确打开的扫码或确认 Dialog。

## 5. 组件与布局方案

### 5.1 组件复用

使用项目已有 `web/src/components/ui/collapsible.tsx`，即 shadcn/ui 对 Radix Collapsible 的 copy-in 封装：

- `Collapsible`：承载单个渠道的展开状态。
- `CollapsibleTrigger asChild`：包裹独立图标按钮。
- `CollapsibleContent`：承载渠道详情。
- 继续复用现有 `Badge`、`Switch`、`DropdownMenu`、`Tooltip`、`Checkbox`、`Dialog` 和 `AlertDialog`。

不自行实现高度测量、动画状态机或新的基础折叠组件。

`CollapsibleContent` 使用 `forceMount` 并根据 `open` 设置 `hidden`，让通知草稿、局部错误和异步 busy 状态在同一次页面会话的折叠/展开之间继续存在；不得通过条件渲染卸载详情组件。离开设置页时仍按正常页面生命周期卸载并清理这些临时状态。

### 5.2 页面结构

`ImIntegrationSettings` 保持后端返回渠道数据的稳定身份，但在展示层按显式顺序投影：

```ts
const channelOrder: readonly ImChannelKind[] = ['weCom', 'feishu'];
```

业务常量集中定义，禁止依赖接口数组偶然顺序。未知渠道不在本期展示；未来新增渠道时必须显式加入顺序和 UI 设计，不静默插入。

页面结构：

```text
IM 远程干预与通知
└─ 渠道列表（单列）
   ├─ 企业微信渠道卡片
   │  ├─ 固定摘要头
   │  └─ 可折叠详情
   └─ 飞书渠道卡片
      ├─ 固定摘要头
      └─ 可折叠详情
```

### 5.3 固定摘要头

摘要头在折叠和展开状态下始终可见：

1. 渠道品牌图标。
2. 渠道名称。
3. 固定副标题“机器人 · 一对一私聊”。
4. 当前连接状态 Badge。
5. 已配置渠道的启用 Switch；未配置渠道不显示 Switch。
6. 独立的展开/收起图标按钮。

展开按钮与 Switch 必须是两个独立交互目标，整个标题行不得作为 Trigger，避免用户切换启用状态时误触折叠。按钮使用 `ChevronDown`，折叠时指向右侧、展开时指向下方；按钮最小命中区域 36×36 px。

### 5.4 可折叠详情

展开后按以下顺序显示：

1. **状态与恢复引导**：沿用 `ConnectionGuidance`；ready 且无错误时不额外占位。
2. **接入或授权信息**：未配置时显示接入说明和“扫码接入”；已配置时显示接收账号、机器人/App 标识及飞书单设备提醒。
3. **授权、接收账号与配置管理**：配置菜单位于通知类型之前，保留重新绑定、更换飞书应用、重新授权和删除。
   配置入口使用带文字的“配置管理”按钮；不得只用无文字的 `...` 图标隐藏区块核心动作。
4. **通知类型**：按“需要你处理”和“执行结果提醒”两组展示六个通知开关，保留现有显式保存/放弃草稿行为。
5. **局部错误**：显示在对应操作区域附近；无法明确归属的渠道级错误放在详情底部。

未配置渠道展开后只显示接入内容，不渲染通知偏好和配置管理。企业微信和飞书使用同一结构，渠道差异继续由现有能力与条件分支表达。

## 6. 交互与生命周期契约

| 场景 | 预期行为 |
| --- | --- |
| 首次进入设置页 | 企业微信、飞书均折叠 |
| 从其他设置 Tab 返回“通用”且组件已卸载 | 两张卡片重新折叠 |
| 页面会话内收到 SWR 或 connection snapshot 更新 | 保持用户当前展开状态 |
| 点击企业微信展开按钮 | 只展开/收起企业微信 |
| 点击飞书展开按钮 | 只展开/收起飞书 |
| 点击启用 Switch | 只执行启停，不改变折叠状态 |
| 折叠存在未保存通知草稿的卡片 | 草稿保留在已挂载组件中；再次展开继续编辑 |
| 配置菜单打开时折叠卡片 | 先关闭配置菜单，再隐藏详情 |
| 离开页面且存在未保存草稿 | 沿用当前行为，组件卸载后丢弃临时草稿，不新增离开确认 |
| 折叠时异步操作完成或失败 | 业务结果正常合并；摘要状态更新，展开后可见详情或错误 |

“每次进入设置页面默认折叠”优先于记忆上次展开状态。本期不把折叠状态定义为用户偏好。

## 7. 无障碍与文案

- `CollapsibleTrigger` 必须暴露 `aria-expanded`，由 Radix 与 `open` 同步。
- 按钮使用渠道化可访问名称：“展开企业微信设置 / 收起企业微信设置”“展开飞书设置 / 收起飞书设置”。
- 图标设置 `aria-hidden`，视觉 Tooltip 与可访问名称使用同一语义。
- 标题与详情通过稳定 `id`、`aria-labelledby`/`aria-controls` 建立关系。
- 键盘用户可使用 Tab 聚焦 Switch 和展开按钮，Enter/Space 操作；焦点环使用主题 token。
- 新增文案进入 `web/src/locales/` 七种语言，不在 JSX 中硬编码；中文语义以 `zh-CN` 为准。

建议新增 key：

```text
settings.im.channelSubtitle
settings.im.expandChannel
settings.im.collapseChannel
settings.im.configurationSection
settings.im.receiverAccount
```

已有语义相同的 key 应优先复用，不重复创建。

## 8. 响应式与视觉规则

- 渠道卡片单列排列，不在宽屏改为双列，避免两个长表单并排造成扫描和保存归属混乱。
- 摘要头使用 `min-w-0` 和可换行布局；状态、Switch、展开按钮组成尾部操作区，窄宽度时整体换到下一行，不制造横向滚动。
- 连续 Bot ID、App ID 使用 `break-all`，普通名称使用 `break-words`。
- 深色主题减少嵌套浅黑面板与强边框，以外层卡片、留白、弱分隔线和状态色表达层级。
- 展开/收起只使用 Collapsible 的轻量状态与 CSS 过渡；不测量内容高度、不引入布局监听器。

## 11. 性能影响评审

渠道数量当前固定为两个，展开状态为每卡片一个局部布尔值，切换只重渲染对应 `ImChannelEditor`。方案不增加 API 请求、全量扫描、缓存、队列、ResizeObserver 或跨页面订阅；折叠内容保持 React 生命周期可保留未保存草稿，不通过卸载/重挂制造额外请求。性能风险低，无需新增 benchmark。

## 12. 过度设计评审

现有 canonical identity、generation 和 settings VM 已足够表达业务不变量。本方案不新增 aggregate、状态机、持久字段或跨层 identity，只使用已有 shadcn/ui Collapsible 完成展示层重组。为两个固定渠道引入全局折叠 store、偏好 schema或后端字段均属于过度设计，明确不采用。
