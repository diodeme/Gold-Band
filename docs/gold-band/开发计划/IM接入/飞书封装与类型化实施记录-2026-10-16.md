# 飞书协议封装与卡片类型化（2026-10-16）

## 1. 评审结论与范围

用户确认实施[技术方案 §17.3](飞书远程干预技术方案.md#173-设计与实现偏差收口)中的两项偏差收口。根因是原设计落实不完整：协议帧被 connector 消费，出站卡片与终态控件通过动态 JSON 构造和修改。本次保留原设计目的，协议隔离按模块而非单文件验收；卡片仅覆盖项目实际使用的组件。

## 2. 数据归属与接口

- 权威事实继续由 Runtime 和 durable delivery/outcome 持有。卡片树和回填值仅是一次渲染的投影，不持久化、不增加 identity。
- 卡片根、文本、表单、按钮、单选、多选、输入框、回调意图和 toast 使用 typed 序列化；动态 schema 答案保留领域 `Value`，投影后按具体控件类型回填。
- `ws` 模块拥有 pbbp2 帧、编解码、心跳、分片、ACK 和 socket；对 connector 仅提供连接、入站 payload、回包句柄和回包时限。低层协议类型设为私有，协议测试位于模块内。
- connector 继续负责应用/操作者校验、领域动作派发、binding、generation 安装与清理；回包句柄消耗后不能再次使用。处理任务由所属连接管理。

## 4. 过度设计与性能评审

过度设计：增加的类型只对应当前实际出站协议组件；连接和回包句柄只封装已有 socket、帧、发送通道及接收时间。不建立第二套业务状态、持久字段、通用 DSL、缓存或额外队列。

性能：现有卡片规模最多五题、单选二十项、多选四项；构造和序列化仍按当前卡片大小线性处理，终态遍历仅访问 typed 子控件，不扫描动态答案或历史。ACK 队列容量与 fragment/pending response 上限沿用已有配置；不增加网络请求、后台轮询或历史读取。主要验收风险是回调预算、回包次序和连接取消，不以新增缓存或并行层掩盖问题。

验收复核：JSON 等价与 IM 接口测试验证上述风险，未发现需要新增依赖、缓存、队列或专项 benchmark 的性能变化。连接任务复用现有 `JoinSet`，卡片构建使用现有 serde；没有扩展平台能力上限。
