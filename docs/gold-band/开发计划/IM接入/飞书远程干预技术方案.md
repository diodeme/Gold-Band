### 3.4 平台行为事实（实现必须遵守）

- **回调送达方式**：卡片回调以长连接的 `event` 帧送达，端到端约 90–100ms。载荷包含 `action.value`、`action.form_value`、`action.name`、`operator.open_id`、`context.open_message_id`。
- **回调返回值**：
  - 返回 `{toast, card:{type:'raw', data}}`：卡片原地更新。
  - 只返回 toast：卡片保持可编辑。
  - 3 秒内没有返回：返回值被丢弃，也不会重投。
- **表单回传形态**：
  - 单选回传 string，多选回传 string[]。
  - **多选一项都不选时，该字段整体缺失**。
  - 空输入框回传 `""`。
  - **没选“其他”时，输入框的值仍会回传**。
- **表单校验边界**：
  - 必填由客户端拦截。
  - `max_length` 不可靠。
  - 不能按选项条件显示或必填某个输入框，所以“选了其他就必须填写”只能由服务端校验。
  - 表单外的按钮不触发必填校验。

- spike 代码、临时 worktree 与日志均不入库；spike 日志中含长连接 URL 凭据，验证后必须删除。

| 准入条件 | 结果 | 实测依据 |
|---|---|---|
| G1 协议正确性 | ✅ 通过 | 收到 `im.message.receive_v1`（p2p）和 `card.action.trigger`（以 `type=event` 帧下发）；回包 toast + `card.type=raw` 后卡片原地更新；只回错误 toast 时卡片保持可编辑，修正后再次提交得到终态卡片；`form_value` 正确回传 |

| G3 回调可控 | ❌ 未通过 | 回调是同步函数，经 `spawn_blocking` **串行**执行：5 秒慢回调期间用户发的私聊消息，等慢回调结束后才分发（延迟约 4.2 秒），存在队头阻塞；超过 3 秒的回包被平台丢弃（与 PoC 一致），后续异步 PATCH 成功 |
| G4 错误可结构化 | ✅ 基本通过 | `WsClientError` 是 thiserror 枚举，可匹配；但正常关闭也返回 `Err(ConnectionClosed)`，需要在外层区分 |
| G5 依赖与构建 | ❌ 未通过（阻断） | 首次运行即 panic：`Could not automatically determine the process-level CryptoProvider`。原因是 openlark-core 强制依赖带 rustls 的 `reqwest 0.13`，引入 aws-lc-rs provider，与依赖树中已有的 ring 冲突，必须在应用启动时手动 `install_default()`。另外：`Cargo.lock` 从 796 个包增至 819 个（+23），`cargo tree -d` 重复项从 37 增至 49；重复的有 reqwest 0.12/0.13、tokio-tungstenite 与 tungstenite 0.29/0.30、rand 0.9 系列、sha1 0.10/0.11；新增 aws-lc-sys（需要 cmake 和 C 工具链）、quinn 系列等。许可证 Apache-2.0、MSRV 1.88 满足要求 |
| G6 日志安全 | ❌ 未通过 | INFO 级别输出完整的 `wss://…?access_key=…&ticket=…`，泄漏长连接凭据；TRACE 级别输出完整 Frame（含事件正文）；DEBUG 输出 message_id 和 trace_id。App Secret、tenant_access_token、open_id 未出现。只能靠 tracing 过滤规避 |

## 4. 现状与根因

**实施前历史基线。** 本节描述飞书扩展实施前的问题及当时的修复方向；表中的“现状”不代表当前代码。当前接口见 §7–§10，已确认实施记录见 §1.1、§15，设计偏差收口见 §17.3。

| 位置 | 现状 | 问题类型 |
|---|---|---|
| `src/app/intervention.rs` 中的 `remote_elicitation_form()` 和 `MAX_REMOTE_ELICITATION_*` 常量 | 领域层直接按企微的投票/下拉能力生成表单：单题最多 20 项、最多 3 题、多题时最多 10 项、不支持自由文本 | 设计缺陷：渠道能力泄漏到了领域层 |
| `src/im/projection.rs` 中的 `enqueue_draft` | Elicitation 在 `target.channel != ImChannelKind::WeCom` 时直接跳过 | 设计缺陷：按平台名分支，违反设计文档 §5“按能力投影”的原则 |
| `src/im/projection.rs` 中的 `draft_for_event`、`remote_permission_actions` | 每个事件只生成一份草稿，所有渠道共用同一组 `allowed_actions`；Elicitation 只保留 `ElicitationFixedForm`，拒绝回答只能在桌面端操作；Permission 的降级直接使用 `WECOM_MAX_PERMISSION_OPTIONS` | 设计缺陷：投影没有按目标渠道区分，入站校验所依据的 `allowed_actions` 不一定是该渠道实际发布的内容 |
| `src/app/intervention.rs` 中的 `InterventionPrompt.requires_desktop` | 混合了两类原因：一类与渠道无关（权限选项存在歧义，即 `permission_actions_require_desktop`；schema 无法表达为远程表单）；另一类按企微上限计算（`allowed_actions.len() > MAX_REMOTE_PERMISSION_OPTIONS`，以及因企微装不下导致的 `form.is_none()`） | 设计缺陷：渠道上限混进了领域事实 |
| `src/im/connector.rs` | `ImWeComVoteSelection` 等企微专用类型放在通用层；`ImActionResponseContext` 只有 `WeCom` 变体；`ImChannelCapabilities` 只有 4 个布尔值 | 设计缺陷：缺少表单能力模型和通用回包模型 |
| `src-tauri/src/im_runtime.rs` 中的 `consume_connector_events` | 所有渠道的连接事件共用一个消费循环。处理 `InboundAction` 时，循环先 `spawn_blocking(process_inbound).await`，再 `respond_to_action().await`，处理完才取下一条事件 | 设计缺陷：入站处理全局串行。任一渠道的慢处理都会阻塞其他渠道的回调和连接状态事件，飞书的 3 秒预算无法保证；只在飞书 ws 层做并发不能解决 |
| `src-tauri/src/im_runtime.rs` 中的 `process_inbound` | 每次处理都新建 `ImInboundActionService`，它按 `action_id` 加锁的 `ActionLocks` 随实例新建；`handle_locked` 先查入站结果、再执行、最后 `record_inbound_result`（`INSERT OR IGNORE`），不提前占位。现在不出问题，只是因为消费循环串行 | 实现缺陷：幂等锁的生命周期短于它要保护的并发范围。入站改为并发后，同一事件重投会有两份同时进入领域层，后到者返回 `AlreadyApplied` 而不是重放首次结果 |
| `src-tauri/src/im_runtime.rs` 中的 `eligible_desktop_resolution_target`、`enrich_wecom_vote_context`、`enrich_wecom_form_context` | 终态目标筛选中有 `channel == ImChannelKind::WeCom` 判断；回包上下文补全直接读写企微类型 | 设计缺陷：runtime 层按平台名分支 |
| `src-tauri/src/im_runtime.rs` 中的 `process_inbound`、`inbound_failure_state` | 错误以 `anyhow` 传递，再用字符串匹配错误码，映射为卡片状态 | 设计缺陷：错误码没有结构化 |
| `src-tauri/src/im_runtime.rs` 中的 `project_desktop_intervention_resolution` | 只有桌面端处理成功后才向 IM 广播终态；在 IM 中处理后，其他 IM 渠道不会收到通知。实现分两轮：第一轮给已有源 delivery 的渠道写终态；第二轮给没有源 delivery、但 `eligible_desktop_resolution_target` 成立的 target 也写终态。第二轮兼作 tombstone：`enqueue` 写入源 Intervention 前会检查同一 identity 的终态是否存在，存在即返回 `Duplicate`，从而拦住晚于桌面端处理才到达的源投影（由测试 `desktop_resolution_wins_when_it_is_persisted_before_the_source_projection` 锁定）。但第二轮写入的终态也会对外发送，用户可能收到一条对应卡片从未发出的“已处理”，Elicitation 因此只对企微走第二轮 | 设计缺口：终态通知只覆盖了“桌面端处理”这一种来源；“写 tombstone”和“对外发送”耦合在一起，只能靠平台分支规避误发 |
| `src/im/model.rs` 中的 `InterventionResolutionNotification` | 没有“由哪一端处理”的字段，事件后缀固定为 `desktop-resolved` | 同上 |
| `src/im/repository.rs` 中的 `ensure_schema` | 只有 `CREATE TABLE IF NOT EXISTS` 和写版本号，没有按版本执行的迁移步骤 | 实现缺口：§7.5 的版本升级必须先补上迁移步骤 |

结论：问题源于设计缺陷，需要把能力模型、按渠道投影、统一提交与回包、入站并发（含幂等锁的归属）、终态互通（含发送与 tombstone 的拆分）一起修复。不在现有代码上追加 `if Feishu` 分支。

## 6. 依赖选型：飞书长连接

### 6.1 长连接需要做什么

飞书长连接（pbbp2 协议）传输的是 WebSocket 二进制帧。每一帧是一个 protobuf `Frame`，由 headers 和 payload 组成，payload 是事件 JSON。客户端需要负责：

- 获取 endpoint；
- protobuf 帧的编码和解码；
- 心跳 ping/pong；
- 大消息分片重组；
- 对每条事件回 ACK（卡片回调的响应以 base64 编码的 JSON 写回）；
- 断线重连。

### 6.2 候选对比

| 维度 | `openlark-client` 0.21.0（原 `open-lark`） | `prost` + pbbp2 消息定义 |
|---|---|---|
| 是什么 | 社区维护的 Rust 飞书/Lark 开放平台 SDK，带完整的长连接客户端 | 通用的 protobuf 编解码库，不是飞书 SDK |
| 覆盖范围 | 握手、心跳、重连、分片、事件分发，以及 `card.action.trigger` 的 3 秒回包，都已经实现 | 只负责 `Frame` 的编解码；连接、心跳、分片重组、ACK、connection generation、重连以及对应的 fixture 测试都要自己写，工作量按 P1 的一个完整子项估算，不是几百行的小封装 |
| 扫码注册（registration） | 不包含 | 不涉及；两种方案都要用 reqwest 自己实现 |
| 依赖影响 | 实测 +23 个包、重复项 +12（reqwest、tungstenite、rand、sha1 各重复一套）；强制引入 aws-lc-rs，与 ring 冲突导致启动 panic（§3.5） | 实测只新增 `prost`、`prost-derive` 2 个包，不新增重复版本；传输复用项目已有的 `tokio-tungstenite 0.30` |
| 成熟度 | 0.x 版本，迭代快（2026-10-09 发布 0.21.0），主要由一位作者维护，Apache-2.0，MSRV 1.88 | prost 被广泛使用；`lark-websocket-protobuf` 与 openlark 是同一作者，内容只有 pbbp2 的生成代码 |
| 与项目模型的契合度 | 回调走它自己的 dispatcher 抽象。连接 generation、结构化错误码、3 秒预算控制、`process::background_command` 等约束都要去适配它的模型 | 和企微 Connector 一样，是“成熟传输库 + 官方协议”的薄封装，完全遵循现有 Connector 模型 |

### 6.3 决策：prost 自研薄封装（已定案）

**结论：** 长连接采用 `tokio-tungstenite 0.30`（项目已有）+ `prost` + 项目内声明的 pbbp2 `Frame`/`Header`，不采用 `openlark`。依据见 §3.5 和 §6.4。

**实现约定：**

1. **消息定义：** 用 `#[derive(prost::Message)]` 在 `feishu/ws.rs` 内声明 `Frame` 和 `Header`，字段号与官方 pbbp2 proto 一致；依赖当前稳定版 `prost`（截至 2026-10-12 为 0.14.4），不依赖 `lark-websocket-protobuf`（单人维护且锁定 prost 0.13），不引入 protoc 构建依赖。
2. **协议基准：** 官方 `@larksuiteoapi/node-sdk` 的 WSClient（PoC 已验证）；openlark 的 `ws_client` 只作为 Rust 参考实现和测试 fixture 来源。
3. **回调并发：** 读任务只解帧、重组分片，每条事件 spawn 独立的 async 处理任务，不串行执行，避免 §3.5 G3 中的队头阻塞；卡片回调在 `FEISHU_CALLBACK_BUDGET`（小于 3 秒）内回包。
4. **生命周期：** 每次连接分配 connection generation，带“已连接”信号和 cancel token；主动关闭走 WebSocket close，旧 generation 的事件丢弃；按服务端下发的 ReconnectInterval + ReconnectNonce 随机抖动重连。
5. **日志安全：** 日志中不出现长连接 URL 的 query（access_key、ticket）和帧 payload，只记录 frame 类型、method、长度、generation 等元数据。
6. **TLS：** 沿用项目现有的 `tokio-tungstenite` 的 rustls-tls-native-roots，不新增 TLS 实现和 crypto provider。

**重新评估条件：** 只有当 openlark 同时满足以下条件时才重新评审：对齐 tungstenite 0.30；reqwest/TLS 依赖可按 feature 关闭，不再强制 aws-lc-rs；回调改为 async 并发；内置重连与生命周期信号；日志不输出 URL 凭据。协议类型封装在 `feishu::ws` 模块，允许模块内部按职责拆文件；未来切换的目标是限制协议适配范围，不能承诺替换 SDK 只改一个文件。2026-10-16 评审与实施见 §17.3。

模块边界与构建约束（2026-10-16 用户确认按职责收口，见 §17.3）：

- **协议类型不越出 `feishu::ws` 模块。** `Frame`、`Header`、`FrameKind`、分片和编解码均为模块私有；`ws/connection.rs` 管理 socket、心跳、ACK 队列及连接所属的处理任务，只暴露项目内部的入站 payload、一次性回包句柄和时限。`feishu.rs` 负责业务事件校验与派发，不导入协议帧；协议集成测试同样置于模块内。按模块隔离保证职责边界，不再以所有代码处于单一文件为验收条件。
- **HTTP 不走 SDK。** 只用到这几个接口：扫码注册、`tenant_access_token/internal`、`/callback/ws/endpoint`、`im/v1/messages`（create）、`im/v1/messages/:message_id`（PATCH），以及自检用的 `bot/v3/info` 和 `application/v6/scopes`。统一用已有的 `reqwest 0.12` 调用。
- 卡片 JSON 使用 serde typed struct/enum：`card/wire.rs` 仅定义当前实际使用的卡片、文本、表单、按钮、单选、多选、输入框、callback 意图及 toast；初始卡、终态 PATCH 和 callback 回显共用 typed 构建。动态领域答案继续由 `Value` 承载，按已发布选项投影后使用具体控件字段回填与禁用，不递归修改任意 JSON。二维码继续复用企微扫码已使用的 `qrcode`。

## 7. 数据设计

### 7.1 领域层：渠道无关的完整远程表单

```rust
pub struct RemoteElicitationForm {
    pub questions: Vec<RemoteQuestion>,     // 1..=N，领域层不限制题数
    pub decline_allowed: bool,              // 来自该 elicitation 的 allowed actions
}

pub struct RemoteQuestion {
    pub selector_key: String,               // q0、q1…，IM 回调中的字段名，不暴露 schema 字段名
    pub question: ElicitationQuestion,      // 复用领域已有的题目模型
    pub constraints: RemoteQuestionConstraints,
    pub custom_answer_key: Option<String>,  // “其他”回答写入的 schema 字段；None 表示该题没有“其他”
}

pub struct RemoteQuestionConstraints {
    pub required: bool,
    pub allows_empty: bool,                 // 只对 MultiSelect 有意义
    pub max_chars: u32,                     // FreeText 和“其他”填写内容的长度上限
    pub multiline: bool,                    // 只对 FreeText 有意义
}
```

题目模型复用：

- 领域层已有 `ElicitationQuestion`，包含 `field_name`、`title`、`description`、`question_kind`（`SingleSelect`/`MultiSelect`/`FreeText`）、`options` 和 `allows_custom_answer`，桌面端展示的就是它。远程表单直接包含它，不再另定义一套题型枚举，避免两套模型各自演化。
- `RemoteQuestion` 只补充 `ElicitationQuestion` 没有的三项：IM 回调用的 `selector_key`、远程端需要由服务端执行的约束，以及“其他”回答写入的 schema 字段 `custom_answer_key`（来自 `_meta._askUserQuestionCustomAnswer.questionId` 或 `<key>_custom` 约定，与桌面端识别规则一致）。
- `max_chars` 的来源：schema 属性声明了 `maxLength` 时取该值；未声明时取领域常量 `MAX_REMOTE_TEXT_CHARS`；两者都不超过 `MAX_INTERVENTION_CONTENT_BYTES`。`fit_form` 再与渠道的 `free_text.max_chars` / `custom_answer.max_chars` 取较小值。
- 现有的 `RemoteScalarChoiceQuestion`、`RemoteElicitationOption` 删除；后者与 `ElicitationQuestionOption` 结构相同，选项统一使用 `ElicitationQuestionOption`。
- 以后桌面端也需要这些约束时，再把 `RemoteQuestionConstraints` 并入 `ElicitationQuestion`。本期不改桌面端。

规则：

- 领域层只保留与渠道无关的约束，包括 schema 关键字白名单、字段名长度、选项值类型和大小，以及 jsonschema 可满足性校验。
- `MAX_REMOTE_ELICITATION_VOTE_OPTIONS`、`MAX_REMOTE_ELICITATION_SELECTORS`、`MAX_REMOTE_ELICITATION_SELECT_OPTIONS`、`MAX_REMOTE_PERMISSION_OPTIONS` 这四个常量从领域层移出，变成企微的能力声明。
- `InterventionPrompt.requires_desktop` 收窄为“任何渠道都无法安全远程处理”，只保留与渠道无关的原因：权限选项存在歧义（`permission_actions_require_desktop`），以及 schema 本身无法表达为 `RemoteElicitationForm`。删除按企微上限计算的部分。某个渠道能否承载，由 §7.2 的按渠道投影决定。
- **“其他”回答的 content 编码复用桌面端现有规则**：IM 和桌面端共用同一个 content 构建函数。P0 先用接口测试把桌面端现在的编码固化下来。
- `remote_elicitation_form_allows_content` 扩展为完整校验，返回结构化错误码（§13），覆盖：必答题、选项是否合法、选了“其他”必须填写、文本长度。
- 选项 ID 是选项在 `ElicitationQuestion.options` 中序号的十进制规范写法（无前导零）。领域层不限制选项数，选项数上限只来自渠道能力。
- `multiline`：自由文本的 `max_chars` 超过领域常量 `MAX_REMOTE_SINGLE_LINE_TEXT_CHARS`（200）时为多行，否则为单行。schema 没有表达多行的标准关键字，长度上限是唯一可用的事实。
- `allows_empty`：等于“非必答”。content 编码与桌面端一致，空多选会省略该字段，因此“空选是否合法”只取决于该字段是否必答。
- 自由文本可远程的条件：属性 `type` 为 `string`，且只使用白名单关键字 `type`、`title`、`description`、`default`、`examples`、`maxLength`、`deprecated`、`readOnly`、`_meta`。声明 `minLength`、`pattern`、`format` 等其他约束或类型不是字符串时，远程端无法在提交前保证满足，整个表单不可远程（`requires_desktop`）。“其他”字段同样适用该白名单；不满足时只把该题的 `custom_answer_key` 置为 `None`，“其他”只能在桌面端填写。
- “其他”与必答：“其他”回答代替配对的选择字段作答。canonical 校验（桌面端与远程端共用 `elicitation_content_is_valid`）把非空“其他”回答视为满足该选择字段的 `required`，其余约束不放宽。远程表单生成时用同一函数探测“其他”代替选项后的最小答案集，通过才发布 `custom_answer_key`，保证远程能提交的“其他”一定能被 canonical 接受。

### 7.2 渠道能力：按能力描述，不按平台名分支

```rust
pub struct ImChannelCapabilities {
    pub proactive_delivery: bool,
    pub card_actions: bool,
    pub private_chat: bool,
    pub message_update: ImMessageUpdateMode,     // 替换原来的 bool
    pub interaction: ImInteractionCapabilities,
}

pub enum ImMessageUpdateMode { None, CallbackOnly, Anytime }

pub struct ImInteractionCapabilities {
    pub permission_max_options: u16,
    pub max_questions: u8,
    pub single_choice_max_options: ImOptionLimit,    // { single_question, multi_question }
    pub multi_choice: Option<ImMultiChoiceCapability>, // { max_options, within_multi_question }
    pub free_text: Option<ImFreeTextCapability>,     // { max_chars, multiline }
    pub custom_answer: ImCustomAnswerSupport,        // Unsupported | Supported { max_chars }
    pub decline: bool,
}
```

| 能力 | 企微声明（必须与现状完全等价） | 飞书声明 |
|---|---|---|
| `message_update` | `CallbackOnly` | `Anytime` |
| `permission_max_options` | 20 | 20（PoC 已验证） |
| `max_questions` | 3（2026-10-15 官方文档与 42047 实测纠正） | 5（PoC 已验证） |
| `single_choice_max_options` | 单题 20，多题 10 | 单题和多题均为 20（PoC 已验证单题 20；多题复用同一 `select_static` 组件） |
| `multi_choice` | 最多 20 项，只能单题使用 | 最多 4 项，可出现在多题中（PoC 已验证） |
| `free_text` | 不支持 | 单行和多行，最多 500 字符（PoC 已验证） |
| `custom_answer` | 不支持 | 支持，最多 100 字符（PoC 已验证） |
| `decline` | 不支持 | 支持 |

**按目标渠道投影。** `draft_for_event` 生成领域草稿，`enqueue_draft` 对每个 eligible target 调用 `project_payload_for_channel`，后者通过纯函数 `project_for_channel(kind: ImNotificationKind, actions: &[InterventionAllowedAction], capabilities: &ImInteractionCapabilities) -> Option<Vec<InterventionAllowedAction>>` 得到该渠道实际发布的动作（`src/im/projection.rs`）。裁剪后的表单随 `ElicitationFixedForm { form }` 放入该 target 的 `reference.allowed_actions`，不另设 `ImChannelIntervention` 类型。入站只以这条 delivery 记录为准，因此企微 delivery 不接受只有飞书发布的“拒绝回答”。

- `requires_desktop` 为 true（与渠道无关的原因，§7.1）：所有渠道都沿用现状处理。
- Permission：选项数不超过 `permission_max_options` 且没有歧义时，全部投递；否则只投递安全的拒绝类选项，数量不超过上限。这就是现有 `remote_permission_actions` 的降级规则，只是把 `WECOM_MAX_PERMISSION_OPTIONS` 换成渠道能力。
- Elicitation：调用纯函数 `fit_form(&RemoteElicitationForm, &ImInteractionCapabilities) -> Option<RemoteElicitationForm>` 裁剪表单，规则见下文。`fit_form` 返回 `None` 时只是这个渠道不投递，其他渠道照常投递。

`fit_form` 的规则：

- 渠道完全支持：原样投递。
- 渠道不支持“其他”：
  - 单选题去掉“其他”入口（企微现状）；
  - 多选题整个表单不投递（企微现状）。
- 题数、选项数、题型或混合方式超出能力：返回 `None`，不给这个渠道投递，由桌面端处理。
- 不支持拒绝回答：卡片上不出现“拒绝回答”按钮。
- 企微内部选择投票卡还是下拉表单的逻辑留在 `connectors/wecom.rs` 里，通用层不关心。

### 7.3 统一入站提交

```rust
pub enum ImSubmittedAction {
    PublishedAction { index: usize },        // 按这条 delivery 发布的 allowed_actions 取动作（企微按钮只回传序号）
    PermissionOption { option_id: String },
    ManualCheck { outcome: NodeOutcome },
    ElicitationForm { answers: BTreeMap<String /* selector_key */, ImAnswer> },
    ElicitationDecline,

pub struct ImInboundEnvelope {

    pub channel: ImChannelKind,
    pub platform_event_id: String,
    pub conversation_id: String,
    pub actor_id: String,
    pub delivery_id: String,
    pub action_token: Option<String>,        // 渠道在卡片里携带签名 token 时填写，通用层统一校验
    pub action: ImSubmittedAction,
}

// IM 直接再导出领域答案类型，不定义第二份枚举。
pub use crate::app::intervention::RemoteElicitationAnswer as ImAnswer;
// 领域变体：Choice { option_ids: Vec<String>, custom_text: Option<String> }
//           Text { text: String }
```

- 各 Connector 负责把平台回调解码成 `ImSubmittedAction`。connector 解码时还没有读取 delivery，因此只回传按钮序号的渠道使用 `PublishedAction { index }`，由通用层按 delivery 发布的 `allowed_actions` 取出动作；`ElicitationFixedForm` 不能通过序号提交，表单只能走 `ElicitationForm`。
- `action_token` 存在时，通用层校验签名、过期时间以及 delivery、事件、渠道、destination 四项是否与 delivery 记录一致；不存在时只以 delivery 记录为准（企微现状）。无论是否携带 token，动作本身都必须在该 delivery 发布的 `allowed_actions` 内。
- 企微投票卡和下拉卡统一解码为 `ElicitationForm { answers }`，每题为 `Choice { option_ids, custom_text: None }`。企微的投票和下拉解码移入 `connectors/wecom.rs`；`ImWeComVoteSelection`、`ImWeComFormCardKind`、`ImWeComFormSelection` 从 `connector.rs` 删除。
- `ImActionResponseContext` 只携带平台回包句柄，只由所属 connector 解释，通用层和 runtime 只透传，不匹配其变体：
  - 企微：`req_id`、`task_id` 和原始选择；
  - 飞书：`request_id`，对应 `feishu/ws.rs` 内待回包表中的一项（§10.4）。
- 回包需要的 delivery 上下文（发布的动作、表单、`display_ref`）放进 `ImActionResponse.delivery`（§8），由 connector 自己渲染回包卡片。runtime 中的 `enrich_wecom_vote_context`、`enrich_wecom_form_context` 删除。
- 飞书解码时的规则：
  - 多选字段缺失，视为空选；
  - 没选“其他”时，丢弃对应输入框的值；
  - 空字符串文本，视为未填写。
- 从 `ImSubmittedAction` 到 `InterventionAction` 的转换和校验只在通用层实现一次，所有渠道共用。
- `ImAnswer` 是领域类型 `RemoteElicitationAnswer` 的再导出，不在 IM 层另定义一份。文本变体写作 `Text { text }`，因为 serde 内部标签不支持字符串 newtype。content 构建函数 `remote_form_content` 放在领域层，与 `RemoteElicitationForm` 同处。

### 7.4 终态与处理来源

```rust
pub enum ImResolvedBy { Desktop, Channel(ImChannelKind) }

pub struct InterventionResolutionNotification {
    pub canonical_event_id: String,      // <source_event_id>:resolved
    pub source_event_id: String,
    pub notification_kind: ImNotificationKind,
    pub locator: ImNavigationLocator,
    pub display_ref: Option<u16>,
    pub resolved_by: ImResolvedBy,       // 新增
    pub outcome: ImResolutionOutcome,    // 结构化结果；ElicitationSubmitted 携带 Accepted 的 content，不含对客文案
}
```

- 终态事件的 identity 改为 `<source_event_id>:resolved`，常量 `IM_RESOLUTION_EVENT_SUFFIX = "resolved"` 替换原来的 `desktop-resolved`。每个 target 的 delivery identity 仍按现有规则生成。
- **只有收到 `Accepted` 的那一方写入 `resolved_by`**；收到 `AlreadyApplied` 的一方不创建、也不覆盖终态。领域层的 first-writer-wins 保证同一次干预只会有一个 `Accepted`，所以 `resolved_by` 不存在竞争。也因此不需要把来源写进 ACP permission、elicitation、manual check 这三套领域存储，不新增领域持久字段。
- 崩溃窗口：如果领域层已经 `Accepted`，但终态还没写入 IM 就崩溃了，处理方式与现有的桌面端路径相同，不新增机制。残留卡片下次点击不会重复执行业务；没有 durable 赢家结果时飞书回“已处理”并禁用原卡，不承诺恢复答案（§9.4、§17.2）。
- **终态 delivery 有两种写入状态**（规则见 §9.2）：发送型以 `pending` 写入，由 worker 发送或 PATCH；tombstone 以 `expired` 写入，不发送，只用于拦截迟到的源投影。两者的 delivery identity 规则相同，`enqueue` 写入源 Intervention 前只判断该 identity 是否存在，不区分状态。tombstone 不计入 active 上限（只统计 `pending`、`sending`），随 outbox retention（`expired` 状态保留 7 天）清理，远长于源投影可能迟到的时间窗。
- 开发阶段采用破坏式更新：删除 `desktop-resolved` 常量和对应函数；旧终态 delivery 按 §7.5 在迁移时清理，不做兼容。
- P2 回显修正：`ElicitationSubmitted { content: Value }` 是 Accepted 命令结果的投递快照，受 8 KiB 上限约束；Debug 不输出正文。独立瞬态 `submission` 删除。回调和 worker 的 PATCH/另发都按源 delivery 与同一 outcome 渲染；`AlreadyApplied` 只能读取已保存的赢家结果，不能采用后到请求的答案覆盖终态；暂时没有赢家结果时回“已处理”并禁用原卡、保留控件内容；canonical 为取消时当场投影取消终态（2026-10-18）。

### 7.5 持久化版本与迁移（破坏式更新）

当前为 **payload 3 / IM schema 5**；版本常量分别位于 `src/im/model.rs` 和 `src/im/repository.rs`，与 settings schema 无关。`RemoteElicitationForm` 随 `reference.allowed_actions` 中的 `ElicitationFixedForm { form }` 序列化，不存在独立的 `ImChannelIntervention` payload 字段。

已实现的迁移分两步，定义与所有权见[实施计划 §7.2.1](客户端直连IM远程干预实施计划.md#721-im-schema-版本)：

1. **IM schema v3 → v4（P0，payload v1 → v2）**：旧表单由 tagged enum 改为 struct，`ensure_schema` 在已有版本低于 4 时删除旧 `payload_kind = 'intervention'` 行和 `:desktop-resolved` 终态行；`PRAGMA foreign_keys = ON` 保证消息绑定通过 `ON DELETE CASCADE` 删除。入站幂等表不删除，按既有 retention 清理。之后点击被清理的旧卡片按 delivery 不存在处理。
2. **IM schema v4 → v5（P2，payload v2 → v3）**：原位转换旧 JSON，将没有保存答案的 `elicitationSubmitted` 改为 `resultUnavailable`，将合法旧行的 payload version 改为 3。保留 source、resolution、tombstone、rowid/display_ref、binding 与 inbound audit，继续拦截迟到源投影；不能伪造旧答案或把旧终态重新变为可操作卡片。

两步迁移与 schema marker 写入在同一个 `IMMEDIATE` 事务内完成；v3 及更早的库依次执行两步，任一步失败整体回滚、版本号不变，下次打开时重试。新反序列化仅接受新类型，不保留运行时旧格式兼容分支；旧客户端打开高于自身支持版本的 IM schema 返回 `IM_SCHEMA_TOO_NEW`。

迁移在 IM 仓储初始化时执行，不进入每次回调的读取路径。active 上限 1000 并不等于待迁移总行数，已发送与终态行仍按各自 retention 保留；耗时取决于存量规模，当前没有独立 benchmark，不承诺毫秒级完成。

## 9. 三端终态互通

### 9.1 是否需要通知

需要。任一端处理成功后，另外两端都必须变成“已处理”，原因有三：

1. 避免用户在另一端重复处理。
2. 避免迟到的点击让用户困惑。
3. 让用户在任何一端都能看到最终结果和处理来源。

### 9.2 流程

```text
桌面端 / 企微 / 飞书提交
  → （IM）connector 解码为 ImSubmittedAction，通用层按这条 delivery 发布的动作和表单同步校验
       └─ 校验失败：Rejected(code)，只回 toast，卡片保持可编辑，不进入领域层
  → InterventionCommandService::execute（领域层 first-writer-wins，唯一权威事实源）
  → Accepted：runtime 调用 project_intervention_resolution(source_event_id, resolved_by, source_delivery)
       ├─ 对每个 eligible target（§8），逐个调用 enqueue_resolution_and_expire_pending_source
       │  （每个 target 一个事务，deterministic identity 去重，可安全重放）：
       │    ├─ outbox 中有该 target 的源 delivery（不论状态）→ 发送型终态（Send）：
       │    │    · Anytime 渠道（飞书）：一律写入，包括被点击的那张卡
       │    │    · CallbackOnly 渠道（企微）：处理来源就是本渠道时跳过，因为本渠道唯一的那张卡已在回调内更新；
       │    │      否则写入（另发文本）
       │    │    · 同时把该 target 待发送的源 delivery 标记为 expired
       │    └─ outbox 中没有该 target 的源 delivery → tombstone（TombstoneOnly）：
       │         以 expired 写入，不发送；之后迟到的源投影在 enqueue 时命中它，返回 Duplicate
       └─ 只为写入了发送型终态的渠道唤醒 worker：Anytime 渠道 PATCH 原卡；CallbackOnly 渠道另发一条消息
  → 桌面端：沿用现有 session 事件刷新
  → AlreadyApplied：不广播；飞书读取已存赢家结果回包，无结果时按 canonical settlement 回取消终态、“已处理”禁用卡或“操作已过期”；企微沿用现有回调更新
```

**发送型终态与 tombstone 的划分依据。** 某个 target 没有源 delivery 有两种情况：一是该渠道不会投递这次干预（例如 `fit_form` 返回 `None`）；二是源投影还在路上，即桌面端处理早于 lifecycle 投影写入 outbox。两种情况下用户在该渠道都没见过这张卡，发送“已处理”没有意义。第二种情况还必须拦住迟到的源投影，否则会发出一张已处理过的可操作卡片，用户点击后才收到 `AlreadyApplied`。tombstone 同时满足这两点，而且终态投影阶段不需要拿到 `InterventionSnapshot` 来判断渠道能否承载表单，平台分支因此可以完全删除。

### 9.3 通知矩阵

| 处理来源 | 桌面端 | 企业微信 | 飞书 |
|---|---|---|---|
| 桌面端 | 本地直接生效 | 另发文本“id=xxxx 已在桌面端处理”（现状） | PATCH 原卡片为“已在桌面端处理 + 结果” |
| 企业微信 | session 事件刷新（现状） | 5 秒回调内更新原卡片（现状） | PATCH 原卡片为“已在企业微信处理 + 结果” |
| 飞书 | session 事件刷新 | 另发文本“id=xxxx 已在飞书处理”（已确认接受） | 在预算内由回调直接返回终态卡片，worker 再幂等 PATCH 一次；超出预算时回调只回“处理中”toast，终态由 worker PATCH |

- 每个渠道只绑定一个机器人（一个 `authorized_actor_id`、一个私聊 destination），同一次干预在每个渠道最多只有一条 delivery。所以“排除来源 delivery”就等于：处理来源是 `CallbackOnly` 渠道时，不再给这个渠道写终态。
- `Anytime` 渠道不排除来源：被点击的卡片不论是否已在回调中更新，都写入终态 delivery，由 worker PATCH。两次写入的内容相同，重复 PATCH 没有副作用；回调超时的情况也因此不需要单独补写。
- 矩阵中的通知只发给已有源 delivery 的渠道。没有源 delivery 的渠道只写 tombstone，不收到任何消息（§9.2）。

### 9.4 并发、迟到与失败

| 情况 | 处理方式 |
|---|---|
| 两端同时提交 | 领域层只会有一方 `Accepted`。后到的一方收到 `AlreadyApplied`：飞书从已存在的终态记录读取赢家的来源与答案并渲染；记录尚不可读时只回“已处理”toast，不以后到答案替换卡片，随后由赢家终态 PATCH 收敛。企微沿用现有的 `ALREADY_APPLIED` 回调更新 |
| 飞书回调可能超过 3 秒 | 回包等待限时 `FEISHU_CALLBACK_BUDGET`（模块常量，2.5 秒）。超时只回“处理中”toast，不替换卡片，避免在校验结果出来之前就丢掉用户填写的内容。领域命令 `Accepted` 后，按 §9.2 写入的终态 delivery 由 worker PATCH 补齐；如果最终被拒绝（校验失败、过期等），卡片保持原样可编辑，connector 向同一私聊另发一条只读卡片“id=xxxx 提交未成功”并附错误原因，用户可以重新提交 |
| 某个渠道的入站处理很慢 | 每个 action 在独立任务中处理（§8），不阻塞其他渠道的回调，也不阻塞连接状态事件 |
| PATCH 失败 | 可重试的错误按 outbox 现有退避策略重试；不可恢复的错误（消息已删除、超出可更新期限）降级为另发一条终态消息 |
| 干预已过期后点击 | 返回 `IM_ACTION_EXPIRED`：飞书卡片更新为“已过期”，企微沿用现状。过期时主动广播不在本期范围，保持现状 |
| 同一事件被重复投递 | 入站幂等表按 `channel_kind + platform_event_id` 去重（现状）。入站并发后，同一事件的并发重投由 runtime 长期持有的 `ActionLocks` 按 `action_id` 串行化：领域命令只执行一次，后到者重放已记录的结果，两份响应一致（§8） |
| 源投影晚于终态到达（桌面端先处理） | 终态投影已为该 target 写入 tombstone，源 Intervention 入队时返回 `Duplicate`：不发出卡片，也不发送“已处理”（§9.2） |
| 入站任务在回包句柄失效后才完成 | 领域结果已持久化，不回滚。飞书：待回包项已随超时或连接 generation 失效被移除，回包丢弃，终态由 §9.2 的终态 delivery PATCH 补齐；被拒绝的结果没有终态 delivery，改为向私聊另发“id=xxxx 提交未成功 + 原因”；企微：向旧连接回包失败只记 warn，与现状一致，该卡片下次被点击时按 `AlreadyApplied` 收敛 |

### 10.2 扫码创建

1. 设置页显示将要授予的 3 项权限，用户确认后发起 begin 请求。参数：`action=begin`、`archetype=PersonalAgent`、`auth_method=client_secret`、`request_user_info=open_id`。
2. 在 `verification_uri_complete` 上追加 `source`、`name`、`desc` 与 `addons`（3 项权限，以及事件和回调订阅），生成二维码。`source` 与描述后缀取自 `im.feishuScanAuth`；`name` 取当前渠道 `appName`，组合描述为“渠道产品名 + 描述后缀”。
3. 按服务端返回的 `interval` 轮询 poll：
   - 收到 `slow_down` 时把间隔加 5 秒；
   - 收到 `authorization_pending` 时继续轮询；
   - 收到 `access_denied` 或 `expired_token` 时结束，返回结构化错误；
   - 发现 `tenant_brand=lark` 时切换一次域名。
4. 成功后：
   - `client_id` 和 `client_secret` 写入 keyring；
   - 设置文件只保存非敏感 app_id（`public_identity`），`open_id`、`brand` 与 secret 同存 keyring，机器人名称运行时由 `bot/v3/info` 提供；
   - 扫码人的 `open_id` 作为 `authorized_actor_id`：连接后第一条来自该 `open_id` 的私聊消息产生绑定。
5. 自检：依次检查 token、`bot/v3/info`、`application/v6/scopes`、ws endpoint，任何一项失败都返回结构化错误码。
6. 扫码命令使用类型化模式：`selectOrCreate` 不传 `clientID`、不传 `createOnly`，由飞书 launcher 展示已有应用列表并提供新建入口；`reauthorizeCurrent` 把当前 `public_identity` 作为 `clientID` 传入。首次接入和已配置后的“更换飞书应用”都走 `selectOrCreate`，尚未配置飞书应用时请求重新授权返回 `IM_CONFIG_INVALID`。

### 10.3 长连接

- 用 AppID/AppSecret 请求 `/callback/ws/endpoint`，拿到 URL 和 ClientConfig，心跳、重连间隔和随机抖动都以服务端下发的值为准。
- 只有一个读任务。读任务只负责解帧和分发，每条事件 spawn 独立的 async 处理任务，不在读任务里执行业务逻辑，也不串行等待上一条事件处理完（避免 §3.5 G3 的队头阻塞）。
- ws 层并发只解决飞书内部的队头阻塞，跨渠道的串行要由 runtime 入站调度解决（§8）。两处都必须做。
- 每条事件处理完都回 ACK。分片按 `message_id + seq/sum` 重组，并设置上限和超时，避免缓存无限增长。
- 连接 generation 和状态上报沿用实施计划 §6.2；断线时按 ReconnectInterval 加 ReconnectNonce 随机抖动重连。
- 静默检测：发出 ping 后一个 ping 间隔内没有收到任何入站帧，视为半开连接（例如休眠恢复后），按网络不可用断开并重连。
- 日志只记录 frame 类型、method、长度和 generation，不记录长连接 URL 的 query（access_key、ticket）和 payload。
- 卡片回调 `header.create_time` 的单位是微秒。

### 10.4 卡片回调（3 秒预算）

1. `ws::Connection` 收齐事件后创建 `InboundEvent` 与一次性 `EventReply`，以此时为起点计算 2.5 秒回包期限。connector 处理 `card.action.trigger` 时分配 `request_id`，在 `ws` 模块提供的待回包表中登记 oneshot，以 opaque 的 `FeishuResponseHandle{generation, request_id}` 随 `InboundAction` 发出。读任务不等待处理结果。
2. 所属连接的独立处理任务等待这个 oneshot，通过 `timeout_at(reply.deadline(), ...)` 使用同一个 `FEISHU_CALLBACK_BUDGET` 截止时间：
   - 收到回包：写 ACK（toast，加上可选的 raw 卡片）；
   - 超时：写只含“处理中”toast 的 ACK，并移除待回包项；迟到的 `respond_to_action` 找不到对应项：Handled/AlreadyHandled 丢弃（终态由 worker PATCH）；Rejected 且有 delivery 时用会话语言另发一条“id=xxxx 提交未成功 + 原因”消息，幂等键为 `<delivery_id>:rejected:<callback request id>`，不写 outbox、不改卡片。
   - 待回包表在回包或超时时就删除对应项，容量上限 128；满载时新回调直接 ACK 失败。ACK 队列容量仍为 64；通过消耗 `EventReply` 提交回包，connector 不构造帧。
3. 校验：`operator.open_id` 必须等于绑定用户，必须是私聊上下文，`action.value` 中的 delivery 引用和 token 必须有效。
4. 把回调解码为 `ImSubmittedAction`，按这条 delivery 发布的表单同步校验。这一步只读一条 delivery 记录，在毫秒级完成。校验失败返回 `Rejected(code)`，只回 toast，卡片保持可编辑，用户可以修正后重新提交。
5. 执行领域命令：`Accepted` 返回终态卡片，`AlreadyApplied` 返回“已在 X 处理”。任何情况下的最终终态都由 §9.2 的终态 delivery 兜底。
6. 卡片的 `action.value` 只放 delivery 引用和动作 token，不放业务数据。服务端始终以 delivery 记录为准。
7. **待回包表的生命周期**：待回包表归属于连接 generation。断线或 generation 切换时整表丢弃，连接持有的 `JoinSet` 取消等待任务，不向新连接补发 ACK；迟到的 `respond_to_action` 找不到对应项，直接丢弃。已经提交给 Runtime 的领域动作不随 ACK 等待任务取消；应用退出时，已进入 `spawn_blocking` 的领域命令无法取消，由领域层持久化保证结果一致。
8. **耗时打点与实测结果**：步骤 5 的领域命令在 `process_inbound` 内已按 `delivery_lookup_ms`、`workspace_resolve_ms`、`settings_read_ms`、`inbound_service_ms`、`domain_command_ms`、`total_ms` 输出结构化日志，并带全局 `sequence` 与 `cold` 标记；日志不包含 token、payload、actor 或会话内容。真实账号首笔飞书点击（冷）`total_ms=121`，后续点击（热）`total_ms=242`，均远低于 2.5 秒预算，未新增缓存或预热。

3. **重构后**：黄金测试的期望输出（卡片 JSON、解码结果、回包内容）不做任何修改，必须全部通过；现有的 `inbound.rs` 和 `projection.rs` 测试全部通过。`ImActionResponseContext::WeCom` 改为不透明句柄、`IM_PAYLOAD_VERSION` 升级后，测试中构造上下文和 fixture 的代码（`wecom.rs`、`im_runtime.rs`、`model.rs`、`worker.rs` 等）需要随之迁移，这类迁移不得修改断言。黄金测试锁定的是用户可见的卡片状态（`expired` / `handled` / `failed`），内部错误码到卡片状态的映射可以随结构化错误码迁移，映射结果不得改变。
4. **企微仅有的可见变化**：多出一条“已在飞书处理”的文本（已确认接受），并有单独测试覆盖。内部事件后缀从 `desktop-resolved` 改为 `resolved`，用户看不到。桌面端处理早于源投影写入时（竞态），企微原先会收到一条对应卡片从未发出的“已在桌面端处理”文本，改为只写 tombstone、不发送；卡片同样不会发出，与现状一致。另有一次性影响：升级时的迁移（§7.5）会清理旧格式的 delivery，升级前发出、尚未处理的企微卡片再被点击时，按 delivery 不存在收敛，需要到桌面端处理。
5. 企微的连接、扫码、凭据和设置代码都不受影响。

## 12. 安全与隐私

- App Secret 只存 keyring，所有包含它的结构在 Debug 输出时脱敏，不进入日志、SQLite、设置文件或前端状态。
- 每个渠道只绑定一个机器人和一个授权用户。入站请求必须同时满足两个条件：actor 是绑定用户（`open_id`），并且来自私聊。最小权限中没有群消息权限。
- 长连接是客户端主动发起的，没有公网入口；入站事件按事件 ID 做幂等。
- 最小权限只有 §3.1 的 3 项，产品不申请额外权限。

## 13. 结构化错误码

所有错误码都加入现有的 `ImErrorCode` 枚举，后端只返回 code，文案由前端或 IM 文案层按 code 映射。

| code | 场景 |
|---|---|
| `IM_FORM_ANSWER_MISSING` | 必答题没有回答 |
| `IM_FORM_OPTION_INVALID` | 选项不在允许的范围内 |
| `IM_FORM_CUSTOM_ANSWER_MISSING` | 选了“其他”但没有填写 |
| `IM_FORM_TEXT_TOO_LONG` | 文本或“其他”填写内容超过长度上限 |
| `IM_MESSAGE_UPDATE_UNAVAILABLE` | 原消息不可再更新，触发另发消息降级 |
| `IM_SCAN_DENIED` | 扫码人拒绝授权（与 `IM_SCAN_EXPIRED` 等现有扫码错误码并列） |
| `IM_SCOPE_MISSING` | 自检时发现所需权限没有授予 |

入站处理原先以字符串返回的结果码一并并入 `ImErrorCode`，不再做字符串匹配：

| code | 场景 |
|---|---|
| `IM_ACTION_TOKEN_INVALID` | 动作 token 签名无效，或与 delivery 记录不一致 |
| `IM_INFORMATION_NOT_ACTIONABLE` | delivery 是只读通知，不接受动作 |
| `IM_BINDING_REVOKED` | delivery 的接收方已不是当前绑定 |
| `IM_ACTION_ID_INVALID` | action 或 delivery 身份不合法、同一 delivery 存在多个表单 |
| `IM_ACTION_INVALID` | 动作不在该 delivery 发布的 `allowed_actions` 内，或领域层拒绝 |
| `IM_DELIVERY_NOT_FOUND` | delivery 不存在（包括迁移清理掉的旧卡片） |
| `IM_WORKSPACE_UNAVAILABLE` | 干预所在工作区已不可用 |
| `IM_ACTION_PROCESSING_FAILED` | 存储或领域执行失败 |

复用现有错误码：`IM_ACTOR_MISMATCH`、`IM_CONVERSATION_MISMATCH`、`IM_ACTION_EXPIRED`、`IM_CAPABILITY_UNSUPPORTED`、`IM_RATE_LIMITED`、`IM_NETWORK_UNAVAILABLE`、`IM_PROTOCOL_INVALID` 等。

## 16. 方案自评审

### 16.1 过度设计评审

结论：没有过度设计。

- 新增的只有三样东西，各自都有不可替代的作用：
  - `ImInteractionCapabilities`：用来替代平台名分支，否则两个渠道无法共存；
  - `ImSubmittedAction`：消除通用层对企微类型的依赖；
  - `resolved_by` 和 `outcome`：现有数据无法表达“由谁处理、结果是什么”。
- 远程题目直接包含领域已有的 `ElicitationQuestion`，只补充远程约束，并删除两个重复的远程类型，没有另起一套题目模型。
- 没有新增状态机、队列、缓存，也没有领域持久字段。终态复用现有的 outbox、deterministic identity 和逐 target 幂等写入，不为跨 target 原子性新增事务机制。
- 入站并发只是把现有循环里的 `await` 改成 spawn，不新增队列和信号量：每个渠道只有一个授权用户，并发量天然很小。
- 评估补充的两项修复都复用现有机制：入站幂等只改变 `ImInboundActionService` 的持有方式，复用已有的 `ActionLocks`；tombstone 复用现有终态记录和 outbox 的 `expired` 状态，只新增写入意图枚举 `ImResolutionDispatch`，没有新增表、字段或状态。
- 只有 `Accepted` 的一方写入 `resolved_by`，所以不需要改动三套领域存储。
- 长连接先对现成的 openlark 做了准入 PoC，因依赖冲突、串行回调、日志泄漏未通过，才改为自研薄封装；自研只覆盖 pbbp2 协议本身，传输和 TLS 复用项目已有的 `tokio-tungstenite`，protobuf 用 `prost`，不重复造轮子。协议类型限制在 `feishu/ws.rs` 内是原设计要求，当前跨文件使用尚待 §17.3 评审；HTTP 只调用少量固定接口（§6.3）。

### 16.2 性能影响评审

结论：识别出一项既有的性能风险，即入站处理全局串行（§4），已纳入 P0 修复，并由跨渠道慢处理回归测试锁定。除此之外没有明显的性能风险。

- **数据规模**：每个渠道只绑定一个机器人，每次干预在每个渠道最多产生 1 条 delivery 和 1 条终态 delivery，总数等于启用的渠道数（目前不超过 2）；没有全量扫描，也没有 N+1。
- **入站并发**：每个 action 独立任务，慢处理不再阻塞其他渠道和连接状态事件；并发量受单一授权用户的点击频率约束。飞书待回包表在回包或超时时删除对应项，连接 generation 切换时整表丢弃，大小不超过正在处理的回调数。同一 action 的幂等锁只覆盖单个 action；仓储是单连接加 Mutex，每次持锁只覆盖一个短事务，领域命令不在仓储锁内执行，入站并发不会在仓储层形成瓶颈。
- **额外 PATCH**：`Anytime` 渠道的来源卡片会多 PATCH 一次，每次干预最多一次额外调用，可以忽略。
- **主要风险在 3 秒回调预算**：
  - 读任务不执行业务；
  - 回包等待有限时，超时只回“处理中”toast，终态由 worker 异步 PATCH；
  - token 刷新用 single-flight，不会阻塞回调；
  - `process_inbound` 冷/热真实样本为 121ms/242ms（§10.4），无需缓存或预热；这两个样本不代表重锁争用与长期负载上界。
- **tombstone 与迁移**：每次干预每个渠道最多 1 条 tombstone，以 `expired` 写入，不占 active 配额，也不唤醒 worker；迁移一次性，不在首屏路径上；耗时取决于本地记录规模，本轮未给出独立迁移 benchmark。
- **内存**：分片重组缓存有上限和超时；token 缓存只有一份。
- **启动与 UI**：飞书连接在后台启动，不阻塞首屏；设置页按需加载二维码组件，和企微一样。
