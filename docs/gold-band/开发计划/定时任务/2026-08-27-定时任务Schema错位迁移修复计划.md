# 定时任务 Schema 错位迁移修复计划

## 1. 问题与根因

定时任务管理页加载全局定义时会打开用户级 `core.db`。当前故障库的 `core_schema` 把 scheduler 标记为 v2，但 `scheduled_occurrences` 仍是 v1 表结构，缺少 `schedule_revision`、`node_id`、`accepted_at` 和 `execution_snapshot_json`。现有升级逻辑只按版本号选择 v2 到 v3 迁移，因此在创建依赖 `accepted_at` 的索引时失败，整个列表命令返回错误。

根因属于数据库迁移契约缺陷：版本标记被当成表结构的唯一事实，但迁移没有验证该标记所声明的必要结构，也没有覆盖“版本标记领先于实际表结构”的回归 fixture。

## 2. 数据归属与迁移不变量

- `scheduled_jobs` 是定时任务 authoring definition 的权威数据，迁移必须完整保留。
- v1 `scheduled_occurrences` 不具备 immutable execution snapshot 和完整 acceptance locator，不能证明执行已被可靠接受，属于新版执行历史模型下的脏数据。
- 错位恢复必须删除全部旧 occurrence，不得伪造 `accepted_at`、snapshot 或 Run 历史，也不得新增 legacy history 表、兼容读取路径或前端旁路。
- scheduler schema 版本与必要表结构必须在同一事务内收敛；任一步失败时不得留下半迁移状态。
- 其他 `core.db` component、Task、Run、会话和 workspace 数据不属于本次写入范围。

## 3. 方案比较与决策

### 方案 A：只相信版本号

保持现状，无法恢复错位库，不采用。

### 方案 B：为旧 occurrence 补空字段

通过空值或推断值保留旧行，会把不能证明 acceptance 的诊断记录伪装为执行历史，破坏 canonical history，不采用。

### 方案 C：校验 schema capability 后收敛迁移

打开 scheduler 数据库时读取 `scheduled_occurrences` 的列集合。版本标记为 v2、且四个 v2-only 列全部缺失时，将其作为实际 v1：复用既有 v1 到 v2 重建逻辑删除旧 occurrence 并保留 `scheduled_jobs`，然后继续 v2 到 v3。只存在部分 v2 列时原样拒绝，避免误删未知半升级数据。该方案只修复已确认的错位状态，不放宽未知或未来版本，作为最终方案。

## 4. 接口与实现边界

- 在 `src/scheduler/db.rs` 的 `ensure_schema` 内增加私有表能力检查，不新增公共 API 或持久字段。
- 检查使用 SQLite `PRAGMA table_info(scheduled_occurrences)`，验证四个 v2 新增列；复杂度为固定列数的 O(1) 元数据读取。
- `Some(2)` 分支在 capability 完整时执行既有 v2 到 v3；四个 v2-only 列全部缺失时先执行既有 v1 到 v2，再执行 v2 到 v3；部分存在时保持数据不变并拒绝迁移。
- `Some(1)`、全新库、合法 v2、合法 v3 和高于支持版本的拒绝语义保持不变。
- 数据库错误继续通过现有结构化 scheduler error 边界返回，不增加后端对客文案。

## 5. 测试与验收

先增加真实 SQLite 回归 fixture：创建 v1 scheduler 表和有效 definitions，再把 `core_schema.scheduler` 人为标记为 v2。修复前打开必须以 `no such column: accepted_at` 失败；修复后必须满足：

1. scheduler schema 版本为 v3。
2. 原有定时任务 definition 完整可读。
3. 旧 occurrence 数量为 0。
4. v2/v3 必要列和索引存在。
5. 其他 `core_schema` component 保持不变。

同时复跑合法 v1 到 v2 到 v3、合法 v2 到 v3、current schema reopen、future schema rejection 和 scheduler DB 全量测试；最后执行 Rust 格式、差异检查与桌面端编译检查。

## 6. 性能与过度设计评审

每次首次打开 scheduler connection 只增加一次小型 schema 元数据读取，不扫描任务或 occurrence 数据，不增加缓存、队列、锁范围、后台线程、依赖或前端刷新。异常迁移仍复用既有事务和重建路径，成本只在检测到错位库时发生。

方案没有新增 aggregate、状态机、持久 identity 或兼容层；新增的私有 capability 判断只用于证明既有 schema version 无法表达的具体不变量，复杂度与数据损坏风险匹配，不属于过度设计。
