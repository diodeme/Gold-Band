# 定时任务全局管理与会话刷新实现计划

## 目标

管理页展示所有已登记工作区的定时任务；后台触发新 Task/Run 后，左侧会话列表自动刷新；Workflow/AUTO 重复执行复用同一 Task 并创建新的 Run。

## 数据与接口

- `ScheduledTaskVm` 增加 `workspaceName`，`projectId` 继续作为启停和筛选的稳定标识。
- `list_scheduled_tasks(projectId = null)` 聚合所有已登记工作区；传入 `projectId` 时保留局部查询能力。
- 创建、启停和调度状态保存后发布 `gold-band://scheduled-task-updated`，仅供定时任务列表和详情局部合并调度投影。
- App 根层只使用 `gold-band://conversation-run-state-updated` 维护会话侧栏。事件命中已加载 Run 时直接合并；已知 Task 出现新 Run 时读取该 Task 的首批 Run 摘要；当前或已加载过摘要的工作区出现新 Task 时读取所属工作区首批 Task 摘要。从未加载的非当前工作区保留展开后按需加载。定时任务定义变化和置顶关系未变化时均不读取置顶分页。

## 验收

- 两个工作区创建的定时任务同时出现在“全部工作区”列表，筛选只改变可见行。
- 任务副信息按模式、Direct 会话策略、窄屏计划摘要、工作空间的顺序展示；工作空间位于末尾，超长副信息单行省略且不产生横向滚动。
- Workflow/AUTO 首次触发得到 `task-001/run-001`，下一次触发得到 `task-001/run-002`。
- 后台触发后无需切换页面，左侧会话列表出现新 Task 或新的 Run。
- 管理页的状态、下次执行时间和最近运行状态通过 CRUD 返回实体或调度事件局部合并。
- 切换启用开关不会令工作区会话或置顶会话进入 loading，也不会发起对应分页请求；真正的新 Task/Run 仍通过会话运行状态事件定向出现。

## 2026-10-19 侧栏漏显修复

- 根因一：新 Task 发现仅允许当前工作区，非当前工作区即使已有摘要也丢弃事件；其 `ready` 缓存在切换或重新展开时不会重读。
- 根因二：分页 single-flight 把事件刷新作为普通重复请求合并；事件发生前已读取的旧页返回后，没有后续重读，可能永久保留空列表或缺少新 Run 的列表。
- [x] 新 Task 事件覆盖当前及已加载工作区，不改变激活项与展开意图。
- [x] 在既有 single-flight 中区分普通复用和事件刷新；每个作用域最多一个在途请求及一个最新待执行重读。失败后仍执行已请求的重读，失效后丢弃待执行项。
- [x] 接口回归先在旧实现确认两条失败：非当前已加载工作区返回 null；旧空页返回后新会话仍不可见。修复后使用同一测试确认转绿。
- [x] DOM 回归覆盖已展开非当前工作区在旧请求结束后显示定时会话，并保持展开及导航选择。
- 过度设计评审：复用既有分页、定位与协调器，不引入依赖、持久字段或第二套会话状态。
- 性能评审：保持 Task 每页 24 条、Run 每页 20 条及既有窗口上限；事件只重读受影响摘要页，突发事件合并为一次尾随读取，不增加全量历史、置顶刷新或轮询。
- 验收：12 个相关测试文件共 100 项通过，生产构建及类型检查通过，独立代码审阅无阻塞问题。既有 App 入口测试默认 Node 环境缺少 `document`（HEAD 已存在直接读取），显式使用 jsdom 后该项通过；本次未改动其环境配置。
- 浏览器验收：完整定时任务管理页正常打开；实际侧栏组件使用受控分页与事件 fixture，在旧请求挂起时连续触发 10 次变更，仅产生旧请求加一次重读，随后显示定时会话且保持展开。390 与 1440 宽度下会话可见，无横向溢出。该 fixture 验证前端消费链路，不替代用户现场 EXE 调度日志与数据核查。
