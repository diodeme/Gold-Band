# Gold Band 定时任务开发计划

## 目标

为 Direct、Workflow、AUTO 增加统一的定时触发能力，复用现有 Task/Run/ACP 生命周期，并提供 composer 创建入口和左侧定时任务管理页。

## 已确认范围

- 定时任务是触发层，不是第四种运行模式。
- 支持 `At`、重复预设、固定间隔 `Every`、自定义 Cron。
- `Every` 只支持分钟和小时；首次启用记录 `anchorAt`，暂停不补跑，重新启用或修改间隔时重新起算。
- Workflow/AUTO 只能新会话；Direct 支持新会话和持续会话。
- 默认启用队列保护；关闭后按 30 秒间隔最多重试 3 次。
- 错过执行不补跑。
- 会话使用 AlarmClock 图标标注，不增加任务名称字段。

## 2026-08-03 可靠性与 Direct 对齐修订

本修订覆盖 AionUi 当前 Direct 定时任务能力，并修正上一版计划将“启动后台执行”误认为“执行完成”的问题。Direct 必须补齐立即执行、任务详情/执行历史、诊断字段、用户执行配置透传、missed、崩溃恢复、lease/heartbeat、完成通知和保持唤醒；Workflow/AUTO 复用同一 occurrence 生命周期，但保留 Gold Band 自身的内容指纹、Task/Run、Workflow snapshot 和 AUTO authoring 规则。

定时任务不增加独立名称字段，展示标题取 instruction 第一条非空行。Scheduler source of truth 是用户级 `core.db` 中按 `project_id` 分区的 SQLite 表；不保留双写、旧数据迁移或 runtime fallback。

无人值守处理固定为：permission request 以 `failed + SCHEDULED_PERMISSION_REQUIRED` 结束；`AskUserQuestion` 以 `attention_required + SCHEDULED_USER_INPUT_REQUIRED` 结束并保留可恢复 Run。两者都必须释放 scheduler lease，不能无限等待。

## 2026-08-19 `core.db` 统一存储与 project identity 收敛

本次按开发阶段破坏式更新实施，不迁移已有定时任务：

- [x] `GoldBandPaths::scheduler_db_path()` 直接复用用户级 `core_db_path()`，删除 scheduler legacy path 和 JSON store。
- [x] `scheduled_jobs` 使用 `(project_id, id)` 主键；`scheduled_occurrences` 增加 `project_id`，使用 `(project_id, id)` 主键、`(project_id, job_id)` 级联外键和 `(project_id, job_id, scheduled_at, trigger_kind)` 唯一约束。
- [x] repository、service、coordinator、lease、heartbeat/active guard registry、recovery、retention、notification 与 attention lookup 全部显式传递 canonical `project_id`；不再使用 `workspaceKey` 或仅凭末级 ID 全局查找。
- [x] Scheduler 复用 `core_schema`，以独立 `component = 'scheduler'` 管理 schema version，并与 Runtime recovery 表共存。
- [x] 删除旧 `scheduled-tasks.db` / JSON 的 import、migration marker、schema upgrade 和 fallback 路径；旧文件即使存在或损坏也不得打开。
- [x] 增加接口层定向测试，覆盖跨项目相同 ID 隔离、definition project mismatch 拒绝、Scheduler/Runtime recovery 共库及旧文件不读取。

方案评审：问题来源于 workspace identity 与物理数据库边界耦合。当前 `project_id` 已是应用内唯一 workspace identity，因此应让约束和接口显式表达作用域，而不是继续依赖每 workspace 一个文件。实现复用现有 `core.db`、`core_schema`、SQLite 事务和 coordinator；没有新增 aggregate、缓存、队列、并发机制或迁移抽象，不过度设计。

性能评审：enabled deadline、active occurrence、history 和 status history 索引均以 `project_id` 为首列；共享数据库后的协调、恢复、分页和 retention 仍只访问单项目范围，不引入全库扫描、N+1、无界加载、额外缓存、扩大锁范围或事件线程阻塞。验收限定为 Rust 编译、scheduler/storage/scheduled runtime/service 定向测试、格式与 diff 检查，不运行全量回归或前端验证。

定向验收结果（2026-08-19）：`cargo check --lib` 与 desktop `cargo check` 通过；scheduler repository 45 项、core-state 6 项、scheduler path 1 项、scheduled runtime 87 项、scheduled service 26 项、scheduled attention 2 项全部通过；`git diff --check` 通过。Scheduler 改动文件已按 rustfmt 格式化；仓库级 `cargo fmt --all -- --check` 仅剩本任务范围外未提交文件 `src-tauri/src/image_actions.rs` 的既有枚举排版差异。按本次约定未执行全量回归、前端构建或前端/EXE 启动验证。

### Phase 23：执行历史移除与会话生命周期解耦（2026-08-27，待实施）

根因归类：Phase 22 将 Run 作为历史展示分组后，又把人工“删除历史”定义成了 Run 物理删除，导致 scheduler 历史生命周期错误地拥有会话生命周期。用户期望删除的是旧 occurrence；Run 仍应留在普通会话历史并可继续交互。该问题属于领域命令边界设计需要修订，不采用删除成功后吞掉 Run 读取错误等 UI 补丁。

- [ ] 先增加 repository RED：终态 Run 的删除只移除同一 `projectId + scheduledTaskId + taskId + runId` 下不晚于 `throughOccurrenceId` 的 accepted occurrence，保留更新水位后的并发 occurrence；重复请求幂等；错误水位、跨项目/任务/Run 水位返回结构化错误且不写入。
- [ ] 增加应用服务 RED：Running、Paused、等待用户输入等非 `Completed` Run 拒绝历史移除并完整保留 occurrence；Completed Run 删除后 Run/Task/Round/Timeline/SearchIndex 与 definition `task_id` 全部保持不变，普通会话读取和后续交互入口仍可用。
- [ ] 将 scheduler schema 升级为新的开发阶段版本，删除 `scheduled_history_deletions` 表、pending index 和映射类型；删除 `src/app/history_deletion.rs`、stop-then-delete controller、lifecycle/startup finalizer、Run trash/SearchIndex 清理等旧消费路径，不保留兼容分支或 fallback。
