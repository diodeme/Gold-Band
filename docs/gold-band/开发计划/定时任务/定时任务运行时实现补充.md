## 2026-08-12 重新启用停用的定时任务不再回填 missed 记录或发 missed 通知

- [x] 问题：Repeat/Cron 任务停用后再启用，会显示停用期间「错过的记录」并发出 missed 通知。根因是 `set_enabled` 的 enable 分支只重置了 `Every` 的 anchor，Repeat/Cron 的 `next_run_at` 仍用 `derived_next_run_at`（基准为停用前冻结的 `last_trigger_at`）算出停用期间的一个过去点；coordinator 立即当作 missed 回填（`reconcile_missed_deadlines` 每周期落一条 missed occurrence）并 `notify_missed` 发通知。Workflow/Auto 用户常配 Repeat/Cron，所以更易撞上；与 run mode 本身无关。
- [x] 修复：`set_enabled` 在 disabled→enabled 转换时，对所有 schedule 类型都用 `definition.schedule.next_occurrence_after(now)` 计算下一次（停用期间错过的点按既有「grace 外不补跑历史」语义跳过），不再用 `derived_next_run_at`。移除仅 Every 的 anchor 重置特例。disable 路径不变（derived 对 disabled 返回 None）。
- [x] 验收：新增 `reenabling_repeat_job_schedules_next_run_from_now_not_from_stale_last_trigger`（last_trigger_at 设为 30 天前 → disable → enable → 断言 next_run_at ≥ now）。scheduler 测试套件 108 用例全绿。

## 2026-08-13 deadline 毫秒精度与 revision 空转修复

- [x] 根因：`Every::next_occurrence_after` 使用整秒差计算周期，而 schedule anchor 可包含纳秒、SQLite `next_run_at` 只保存毫秒；数据库往返后的 deadline 可能被重算为同一毫秒，导致 materialize 每次成功但 deadline 不前进，coordinator 以零延迟持续重排并约每秒写入 65 次 revision。
- [x] 设计约束：scheduler 以持久化层的毫秒精度为统一时间边界；周期计算必须在该精度上严格单调前进。实现使用 checked `i128` 毫秒算术，保持 O(1)，不增加扫描、轮询或额外 I/O。
- [x] 仓储防护：相同 definition 的 `save_job_definition` 变为幂等 no-op，不为无业务变化的数据增加 revision；coordinator 遇到没有 runnable recovery 工作的 stale 过去 deadline 时至少按 `DEADLINE_FAILURE_RETRY_DELAY` 退避，防止异常路径重新形成零延迟自旋。process 失败已留下 runnable occurrence 时不叠加第二次退避，仍按原 2 秒恢复 SLA 执行。
- [x] 接口验收：`every_sequence_advances_after_a_persisted_millisecond_deadline` 固定现场纳秒/毫秒样本；`due_materialization_advances_a_millisecond_persisted_every_deadline_once` 固定一次物化推进 3 分钟、同一 `now` 再次物化返回 `NotDue` 且 revision 不再增加；`saving_an_unchanged_definition_is_revision_idempotent` 和 `stale_past_deadline_is_rearmed_with_failure_backoff` 分别覆盖两层防护。
- [x] 性能验收：消除单 job 约 65 次/秒的 SQLite 写入、CAS 干扰和 coordinator 立即唤醒；正常任务只在真实状态或 deadline 转换时写入，算法复杂度和锁范围不变。
