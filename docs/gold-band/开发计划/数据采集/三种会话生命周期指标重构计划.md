# Direct / Workflow / AUTO 生命周期指标重构计划

## 1. 目标

按 `产品设计文档/runtime/metrics-collection.md` 将 `POST /api/client-report/metrics/batch` 从节点快照协议替换为生命周期事件协议。仅 wb 渠道启用，直接删除旧的前序节点补报、开始/结束哨兵和兼容消费路径。

## 2. 数据先行

先冻结 core 数据，再修改发布点：

- `SessionMode`：Direct / Workflow / Auto。
- `ExecutionKind`：Turn / Run / NodeAttempt / OuterRun / UnitAttempt。
- 生命周期事实：started、completed、paused、resumed、intervention、acceptance completed。
- `ExecutionOutcome`、`TerminalReason`：结构化 enum，不携带对客文案。
- usage/model snapshot：按实际 resolved provider/model 分段的 token 与 ACP 净处理时间。
- terminal counters：只保留 pause、resume、permission request、elicitation、manual continue 与 follow up 六项。
- execution relation：execution、parent、node/turn/outer/unit/child run ID；删除冗余 runId/roundId，增加 roundIndex。
- `eventRevision`：run/outer/turn 按 executionId 递增，node/unit attempt 按 attemptId 递增并持久化；eventId/executionId/attemptId 全部使用 UUID。
- 指标 attempt：服务端以 attemptId 留存 Usage。Direct 的 executionId/attemptId 均等于 task UUID，attemptIndex 固定为 1，同一 task 多次输入在同一 attempt 内累加 usage/counters；Workflow/AUTO 的 executionId 标识稳定逻辑 node/unit，attemptId 标识一次真实尝试，attemptIndex 在同一 executionId 内从 1 严格递增；重试同时更换 attemptId/attemptIndex 但保持 executionId，parentExecutionId 指向 run/outer-run。

HTTP DTO `MetricsEventItem` 只在 `src-tauri` 管理，core runtime 不依赖 HTTP 协议。

## 3. 实施阶段

### Phase 1：协议与纯映射

- 新增生命周期事件 DTO、字段 enum 和序列化测试。
- 实现三种模式领域事件到 DTO 的纯映射。
- 统一 `eventId`、时间、原始 `userId/workspace`、clientVersion 的生成和快照规则。
- `reportedAt` 入队冻结，重试复用；reporter 按月份拆批。
- 删除 `billableTokens`，只保留 provider 原始 token。
- 定义完整 enum 集合、`counters` 计算器和 `modelUsages[]` 聚合器。
- 定义 outcome/terminalReason 合法组合；Workflow node attempt 快照 roleName。

完成条件：三种模式示例与字段表一致，JSON contract 测试通过。

### Phase 2：补齐领域事实

- Direct：首轮与后续追问统一发布 turn start/terminal，消除内部 Workflow 重复指标。
- Workflow：发布 run、node attempt、pause/resume、intervention 完整生命周期。
- Workflow/AUTO 的 paused/resumed/intervention.requested 中间态携带当前 node/unit 的 nodeId/attemptId/attemptIndex/roundIndex/roleName；进程中断恢复只发布 resumed，不重复当前节点 started。
- Workflow node attempt 上报 nodeId、roundIndex 和 resolved roleName，不上报 runId/roundId。
- AUTO：发布 outer run、所有 dynamic unit attempt、每次 acceptance，并补齐父子关系。
- 每次 ACP prompt 用 resolved provider/model 和 usage delta 形成 segment；模型切换后分别累计。
- counters、revision、request ID 去重集合和 model usage accumulator 由生命周期所有者统一管理。
- 独立 `observability.snapshot.json` 后台尽力持久化；业务线程只在短锁区间内更新内存并执行有界 `try_send`，序列化和跨平台原子写全部由单 writer 完成，失败不影响会话。

完成条件：每个执行单元有且仅有一个 start 和 terminal；覆盖 success/failure/cancel/kill/pause/resume。

### Phase 3：非阻塞上报

- setup 时仅 `channel == wb` 注册 `desktop.metrics`。
- subscriber 使用容量 2048 的 `tokio::mpsc` 和 `try_send`。
- reporter 按 100 条或 2 秒 flush；单条事件首次请求计入次数，总计最多 3 次 HTTP attempt，第三次失败物理删除，退出最多等待 500 ms。
- 唯一 `metrics.log` 最大 20 MB；超限清空并写 reset。每次发送/重试记录 requestId、时间、完整请求体和响应/错误，认证头不落日志。
- 删除旧 `NodeMetricItem`、sentinel、前序补报和 node-start HTTP 路径。

完成条件：慢网、断网、5xx、队列满、subscriber panic 均不改变 runtime 结果。

### Phase 4：服务端与联调

- 服务端按 `eventId` 幂等接收 `events`。
- 固化七个价值维度的聚合口径，避免 parent/child 成本双计。
- wb 构建联调三种模式，确认原始 `userId/workspace` 到达服务端。
- 删除服务端旧 `metrics[]` 节点协议，不保留双写。

完成条件：七个价值维度均可由原子事件查询或聚合。

## 4. 必须固化的测试

### Core / Rust

- Direct 首轮与后续 turn 的 completed/failed/cancelled。
- Workflow run success/failure/killed、首轮/多轮、node retry provider/model。
- Workflow pause → resume、intervention 类型、node failure 定位；中间态携带当前节点上下文，恢复不重复当前节点 started。
- AUTO outer success/failure/killed，以及四种 `unitKind`。
- acceptance 首次通过与修复后通过；outer/leaf failure 关联。
- resolved model、token、cache、ACP 时间映射和可选字段缺失。
- A → B → A 模型切换的分模型 usage、最终模型与汇总 usage；不增加模型切换次数。
- 顶层 usage 等于非 null 已知段之和，并按确认口径视为完整总量。
- pause/resume、permission、elicitation、manual continue 的去重计数和零值序列化。
- counters 只出现在 Direct turn、Workflow run、AUTO outer-run 终态，node/unit 终态不得携带。
- 队列满不 panic、不等待；subscriber/reporter 失败不影响会话。
- observability 更新入口不读取 snapshot、不执行同步磁盘 I/O；Windows 对同一路径连续写入 revision 1、2 后最终可恢复 revision 2。
- default 不注册；wb 缺 endpoint/key 时不发送。
- 队列满直接丢弃新指标并记录 queue/capacity/eventKind；HTTP 队列额外记录 eventId/executionId。snapshot 队列满或断开时记录 path/revision；所有日志失败均不影响会话。

### HTTP contract

- 字段名、全部 enum 允许值、ISO-8601、批量上限和请求头快照。
- `userId/workspace` 保持原值，workspace 切换后已排队事件不串写。
- eventId 重放幂等；网络错误、408/429/5xx、无效/不完整响应在总计 3 次内重试，普通 4xx 与本地 payload 错误第一次失败即删除。
- `metrics.log` 对每次 attempt 记录日志时间和完整请求体，响应/异常完整可对照，且无 API Key。
- 2026-08-24 验收补充：SQLite outbox uploader 的 request 日志恢复 `requestId + attempt + url + body`；attempt 复用批内最大 `metrics_outbox.attempt_count`，body 与 HTTP 实际发送的单次序列化字符串一致，接口测试覆盖混合重试批次且认证头不进入日志。
- outbox claim 原子增加单事件 attempt；混合 attempt batch 逐事件结算；应用重启不重置次数；历史超限 pending 在 claim 前删除且不得发送。

### 端到端

- wb 构建分别执行 Direct、Workflow、AUTO 的成功与停止路径。
- Workflow 制造 pause/resume 和 node failure；AUTO 制造 acceptance repair 与 leaf failure。
- 对照 runtime 与服务端事件的父子关系、终态、counters、分模型 token、ACP 时间。
- 慢响应代理下验证 UI、ACP 流和 runtime 终态不受阻塞。

## 6. 非目标

- 不引入 OpenTelemetry、Kafka、外部消息队列或 schema registry；客户端可靠边界统一使用现有 SQLite outbox，不再增加第二套持久队列。
- 不追求崩溃场景 exactly-once；先以 eventId 幂等和有界队列满足非阻塞。
- 不在客户端计算无干预率、全自动交付率等报表指标。
- 不保留新旧协议双写或旧哨兵兼容逻辑。
- 不改变三种会话的调度、暂停、恢复、停止与 ACP 行为。

## 13. 2026-08-24 Workflow 第十轮端到端验收记录

## 17. 2026-08-26 outbox 有限投递实施记录

- 根因：SQLite outbox 的 lease 只解决崩溃恢复和并发领取，旧失败路径会把请求级错误持续恢复为 pending，没有用持久化 `attempt_count` 形成终止条件，导致服务异常或永久不可达时无限重试与重复日志。这是投递状态转换合同不完整，不是日志层问题。
- 数据与接口：统一 `MAX_UPLOAD_ATTEMPTS=3`，首次请求计为第 1 次；claim 事务只领取 `attempt_count < 3` 并原子加一。失败命令携带每个事件自己的 eventId、attempt 和 nextAttemptAt，在单事务内校验 lease owner 与 attempt 后逐项结算。
- 错误策略：网络错误、408、429、5xx、无效/不完整响应可重试；普通 4xx（含 401/403）与本地 payload 错误第一次失败即删除；可重试错误第三次失败物理删除。升级时先清理历史 `pending && attempt_count >= 3`，不新增 dead-letter 表或 dropped 状态。
- 崩溃语义：claim 前计数保证绝不超过三次；claim 后、HTTP 请求前崩溃会消耗一次额度，实际发送可能少于三次。用户已接受该 at-most-three 投递的数据丢失窗口。
- 接口测试：覆盖第三次可重试失败后删除且第四次不可 claim、永久错误首次删除、历史 attempt=100 清理、混合 attempt batch 逐事件结算，以及关闭并重新打开 SQLite 后 attempt 不重置。
- 验证：`cargo test -p gold-band-desktop metrics:: --no-default-features` 通过，50 passed、0 failed；`cargo fmt --all -- --check` 与目标文件 `git diff --check` 通过。
- 性能评审：单批上限仍为 100，claim 与失败结算均为 O(batch size) 的 SQLite 点更新；HTTP 仍在事务外，writer、线程、队列、锁范围与内存上限不变。历史清理位于 claim 事务，有限重试会减少断网时的请求、日志和 outbox 积压；当前无需新增索引或 benchmark。
- 过度设计评审：复用既有 SQLite canonical outbox、lease、attempt_count、单 blocking writer 和 uploader，不新增依赖、状态机、队列、缓存或兼容层。物理删除直接满足“失败三次丢弃”，dead-letter 或 dropped 状态会增加当前不需要的存储与清理复杂度，因此不采用。

## 18. 2026-08-26 Direct 指标统一生产路径修复记录

- 根因：Direct 的 ACP prompt lifecycle 既发布 UI `AcpTurnFinished`，又绕过 core producer 投递到独立容量 512 的 `DIRECT_METRICS_SENDER`。该旁路与 Workflow/AUTO 使用不同的 worker 初始化和背压边界，`try_send` 失败又被忽略，因此出现 Direct 不产生指标日志、Workflow 仍正常的模式分化。这是一个好的 SQLite transactional outbox 设计被上游双生产路径破坏，不是 outbox 或日志实现本身缺陷。

- 实现：Direct 及 permission/elicitation 源头事实改由现有 `core.metrics-producer` FIFO worker 统一派生 `PendingMetricsFact`；删除 `DirectMetricsJob`、`DIRECT_METRICS_SENDER`、`direct-metrics-worker`、独立容量 512 队列和旧 Direct fact builder。terminal fact 构造后先清理 active/observability state 再发布，消除 terminal 已可见但旧 turn 仍可读的短暂竞态。命令错误与 join failure 也统一进入 prompt terminal callback，UI `AcpTurnFinished` 行为不变。
- 异常隔离：缺失 project/task/turn identity、重复或不匹配转换、producer 队列失败、worker 启动失败与 panic 均记录结构化诊断，不改变会话结果。Scheduled runtime 明确忽略两类 metrics 内部源头事实，避免将它们当作业务状态消费。

- 性能评审：业务热路仍为 O(1) 有界 `try_send`，Direct 改为共享容量 2048 的 FIFO 队列，删除一个常驻线程和容量 512 队列；SQLite 单 writer、单批 100、HTTP 事务外发送和单事件最多 3 次尝试均不变。共享队列在三种模式同时高压时会竞争同一容量，但总内存上限更低、顺序更可预期，且队列满只丢指标不阻塞 Runtime，风险可接受。
- 过度设计评审：复用既有 lifecycle bus、metrics producer、observability state 和 SQLite outbox，只增加两类 typed 源头事件与 turn identity 校验；没有新增持久字段、状态机、队列、缓存、线程或依赖。相比保留 Direct 专用 worker 并只补日志，该收敛直接修复了三种会话不共享生产合同的根本缺陷。
