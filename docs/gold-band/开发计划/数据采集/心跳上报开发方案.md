# 心跳上报开发方案

> 本文是 `POST /api/client-report/heartbeat` 的独立开发依据。当前改造范围是 Gold Band 客户端和协议文档；服务端已兼容六种 reason。Direct、Workflow、AUTO 的终局、token 和执行明细仍由 `POST /api/client-report/metrics/batch` 负责；heartbeat 只记录启动/活动及用户顶层模式 run、定时任务创建事实。

## 1. 目标与边界

heartbeat 只服务以下指标：

- DAU、WAU、MAU 与 DAU/MAU；
- 周活跃回访率；
- 首次观测用户次周留存；
- 人均应用启动次数；
- Direct、Workflow、AUTO 顶层 run 启动次数；
- 定时任务 durable 创建次数；
- 客户端版本与操作系统的活跃用户分布。

明确不做：

- 不统计账号、设备或 workspace 维度；
- 不上传 workspace；
- 不计算在线时长、前后台停留时长或操作强度；
- 不通过 heartbeat 统计 Direct、Workflow、AUTO 的终局状态、成功率或 token；
- 不增加新接口，不兼容旧 heartbeat 请求体；
- 不建设 durable outbox，不补发进程退出后的 heartbeat。

## 2. 现状与改造结论

旧实现曾无条件每 15 分钟轮询。当前方案改为事件驱动，并在本次扩展用户模式启动和定时任务创建事实：

1. 保留 `/api/client-report/heartbeat`。
2. 请求固定为 5 个字段。
3. 用进程级 `HeartbeatReporter` 管理启动上报、活动节流、有限重试和发送。
4. 六类信号统一发布到现有 `RuntimeLifecycleBus`，由 metrics subscriber 映射 reason 和调用 reporter。
5. `activity` 保持 15 分钟成功节流；四类业务事实独立发送和有限进程内重试。
6. 任务 producer 不读取 metrics 配置、不等待 HTTP、不感知重试结果。

## 3. 接口契约

### 3.1 请求

```http
POST /api/client-report/heartbeat
X-Maling-Report-Key: <api-key>
Content-Type: application/json;charset=UTF-8
```

```json
{
  "heartbeatId": "1f16eb74-4215-4c74-a2f3-2930f5df3c87",
  "userId": "kelvinzhou",
  "reason": "appStarted",
  "clientVersion": "0.1.0",
  "os": "windows"
}
```

| 字段 | 约束 | 作用 |
|---|---|---|
| `heartbeatId` | UUID；每个逻辑 heartbeat 创建一次 | 请求幂等键；同一逻辑事件的有限重试必须复用 |
| `userId` | trim 后 1～128 字符；规范化为小写 | DAU、留存和启动次数主体 |
| `reason` | `appStarted/activity/directStarted/workflowStarted/autoStarted/scheduledTaskCreated` | 区分应用启动、活动、三种用户顶层 run 和定时任务创建 |
| `clientVersion` | trim 后 1～64 字符 | 当天最后版本的活跃分布 |
| `os` | `windows/macos/linux` | 当天最后 OS 的活跃分布 |

不允许出现 `schemaVersion`、`accountId`、`installationId`、`workspaceId`、`workspace`、`appSessionId`、`reportedAt`、`heartbeatSeq`、`appState`、`activityState`、`activeExecutionCount` 或 `interval`。

### 3.2 响应与错误码

```json
{
  "code": 200,
  "msg": "",
  "data": {
    "accepted": true,
    "duplicate": false,
    "receivedAt": "2026-07-29T00:30:01Z"
  }
}
```

重复 heartbeatId 返回 HTTP 200，`accepted=false、duplicate=true`。receivedAt 是服务端 UTC 时间。

| HTTP | code / 常量 | 含义 |
|---|---|---|
| 400 | `400100 / REPORT_HEARTBEAT_INVALID_BODY` | JSON 失败、缺字段或有未知字段 |
| 400 | `400101 / REPORT_HEARTBEAT_INVALID_ID` | heartbeatId 不是 UUID |
| 400 | `400102 / REPORT_HEARTBEAT_INVALID_REASON` | reason 非法 |
| 400 | `400103 / REPORT_HEARTBEAT_INVALID_OS` | os 非法 |
| 400 | `400105 / REPORT_HEARTBEAT_FIELD_TOO_LONG` | 字符串超长 |
| 401 | `401000 / REPORT_AUTH_INVALID` | API Key 缺失或无效 |
| 413 | `413000 / REPORT_BODY_TOO_LARGE` | 请求体超过 8 KiB |
| 500 | `500000 / REPORT_INTERNAL_ERROR` | 事务或内部失败 |

响应始终使用包含 `code/msg/data` 的结构体。服务端只返回稳定 code，`msg` 留空，由控制台前端映射文案。

## 4. 客户端上报方案

### 4.1 模块与依赖

heartbeat 位于桌面端 Rust 层；前端只产生活动信号，不直接发送 HTTP。

heartbeat 仅在编译渠道 `wb` 下启用。`default` 及其他渠道无论本地 metrics
设置为何值，`HeartbeatSettings.enabled` 都必须为 false；渠道门禁位于 Rust
配置快照层，不能只依赖前端隐藏入口。

```text
src-tauri/src/metrics/
  mod.rs           # metrics 配置、endpoint、公共能力
  identity.rs      # 跨平台 userId 与 OS
  heartbeat.rs     # HeartbeatReporter、节流、重试、发送
```

复用 `reqwest::Client`、`uuid`、`tokio::time` 和 Tauri `WindowEvent`。新增成熟的 `whoami` crate，通过 `whoami::username()` 在 Windows、macOS、Linux 使用对应系统能力读取用户名；禁止自行维护三套 FFI，也禁止回退到环境变量或 `unknown`。

### 4.2 数据结构

```rust
#[derive(Debug, Clone, Copy, Serialize, PartialEq, Eq)]
#[serde(rename_all = "camelCase")]
enum HeartbeatReason {
    AppStarted,
    Activity,
    DirectStarted,
    WorkflowStarted,
    AutoStarted,
    ScheduledTaskCreated,
}

#[derive(Debug, Clone, Serialize)]
#[serde(rename_all = "camelCase")]
struct HeartbeatRequest {
    heartbeat_id: Uuid,
    user_id: String,
    reason: HeartbeatReason,
    client_version: String,
    os: ClientOs,
}

struct HeartbeatReporter {
    client: reqwest::Client,
    state: Mutex<HeartbeatState>,
}

struct HeartbeatState {
    app_started: AppStartedState,
    last_success_at: Option<Instant>,
    last_failed_attempt_at: Option<Instant>,
    request_in_flight: bool,
}

enum AppStartedState {
    NotReady,
    Pending { request: HeartbeatRequest, attempts: u8 },
    Delivered,
    RejectedUntilConfigChanges,
}
```

常量集中管理：

```rust
const REQUEST_TIMEOUT: Duration = Duration::from_secs(10);
const ACTIVITY_SUCCESS_INTERVAL: Duration = Duration::from_secs(15 * 60);
const ACTIVITY_FAILURE_BACKOFF: Duration = Duration::from_secs(60);
const APP_STARTED_RETRY_DELAYS: [Duration; 2] = [
    Duration::from_secs(30),
    Duration::from_secs(2 * 60),
];
```

### 4.3 userId 与 OS

```text
read userId with whoami::username()
  → trim
  → reject empty/error
  → ASCII lowercase
  → send
```

服务端再次执行 trim 和小写规范化；数据库 userId 使用大小写不敏感、重音敏感排序规则。用户名不可用时跳过上报，记录不含身份值的 `identity_unavailable`，后续触发重新读取。

OS 使用编译目标映射：Windows→`windows`、macOS→`macos`、Linux→`linux`；不发送发行版或设备信息。

### 4.4 生命周期总线

复用 `src/app/observability.rs` 的 `RuntimeLifecycleBus`，不新增第二套总线、channel 或 broker。总线协议增加四类领域事实：

- `ApplicationStarted` → `appStarted`；
- `UserActivityObserved` → `activity`；
- `ConversationRunStarted { projectId, taskId, runId, runMode }` → 按 canonical `runMode` 映射三种 `*Started`；
- `ScheduledTaskCreated { projectId, scheduledTaskId }` → `scheduledTaskCreated`。

总线中的 canonical ID 只用于进程内事实和接口测试，不进入 heartbeat 五字段请求。metrics 使用 async named subscriber；subscriber panic、配置缺失、HTTP 失败或重试耗尽均不得改变 command 返回值、Task/Run 状态或 ScheduledTask durable state。`RuntimeLifecycleBus::emit` 对 subscriber registry poison 采用 best-effort 快照，观察链路不能 unwind 任务 producer。

### 4.5 appStarted

metrics 开关、base URL 和 API Key 就绪后立即构造一次 appStarted 请求。它不依赖 workspace。

- 首次立即发送；
- 网络错误、超时、HTTP 429、5xx 或不可解析的 2xx 响应，分别在 30 秒和 2 分钟后重试；
- 三次尝试复用完全相同的 heartbeatId 和请求体；
- 400、401、413 等确定性错误不自动重试；
- metrics 配置发生有效变化时重新评估，被拒绝的 appStarted 可再次发送；同一进程仍复用原 heartbeatId 和请求体，只替换 endpoint 或认证头；
- metrics 关闭时取消待执行重试；
- 渠道不是 `wb` 时等同于 metrics 关闭，不创建请求、不执行延迟重试；
- activity 先占用共享发送槽时，先登记 appStarted 请求为首次待发送，activity 完成后立即续发，不丢弃启动事实；
- 成功或 duplicate 均进入 Delivered；
- 进程退出后不补发。

appStarted 成功后更新 `last_success_at`，随后 15 分钟内的 activity 被节流。

### 4.6 activity 来源

以下来源统一调用 Rust `record_activity()`，请求 reason 都是 activity：

- Tauri 主窗口从非聚焦变为 `WindowEvent::Focused(true)`；
- WebView 全局 `pointerdown`；
- WebView 全局 `keydown`；
- 发送 Direct prompt 或追问；
- 创建、运行、重跑、继续 Workflow；
- 创建、运行、重跑、继续 AUTO；
- 对暂停执行提交继续所需输入。

前端只发送无内容的活动信号，不上传按键、控件、页面或输入内容。前端用 60 秒轻量 debounce 减少 IPC；Rust 的 15 分钟规则是权威节流。鼠标移动、滚动、动画、repaint 和纯后台执行不算 activity。

activity 不维护 active execution 集合。Direct、Workflow、AUTO 的终局和执行明细仍全部由 metrics/batch 负责。

### 4.7 activity 节流与失败

统一规则：

1. 已有请求发送中则合并本次 activity，不排队；反向竞争时 appStarted 保留首次待发送状态，并在 activity 完成后取得发送槽。
2. 距 appStarted/activity 上次成功不足 15 分钟则跳过；四类业务事实成功不参与该时间戳。
3. 上次发送失败不足 1 分钟则跳过。
4. 条件满足时创建新的 heartbeatId 并发送 activity。
5. HTTP 2xx 且成功 envelope 可解析时更新 `last_success_at` 并清空失败时间。
6. 失败只更新 `last_failed_attempt_at`；不定时重试，等待下一次真实 activity。

不使用无界 channel，不写 SQLite outbox。被合并或节流的 activity 不补发，因为 heartbeat 表达当下采样，不是必须交付的业务事实。

延迟重试使用配置 generation 校验。配置关闭或变化会使旧 generation 失效；
重试唤醒后重新读取当前 endpoint/API Key，禁止使用任务创建时捕获的旧认证配置。
appStarted 请求对象不属于配置快照，配置变化时必须继续复用原 heartbeatId 和请求体。

### 4.8 业务事实触发与交付

`Started` 的统一语义是：用户发起的顶层 Conversation 模式运行已被 Gold Band 接受，并成功创建新的 canonical `runId`。它不表示首个 token、首个节点完成或任务成功。

- `create_conversation_run_vm`：`run_start_background` 成功返回后发布一次；
- `rerun_conversation_task_vm`：成功返回新的 `runId` 后发布一次，并使用持久化 conversation metadata 的 canonical `runMode`；
- Direct follow-up、queued prompt、continue、same-run retry 不发布；
- 旧工作台 `commands.rs::start_run` 已关闭，不发布；
- scheduled runtime、AUTO dynamic/child run 不发布；
- `ScheduledTaskService::create` 在 `persist_created_job_transactionally` 成功后、`coordinator.notify(JobCreated)` 前发布创建事实；update、enable/disable、delete 和自动执行不发布。

四类业务事实不读取或修改 activity 的 `last_success_at/last_failed_attempt_at/request_in_flight`，也不互相合并。暂时故障复用 appStarted 的 30 秒、2 分钟有限重试延迟和同一 heartbeatId；确定性错误不重试；配置 generation 变化或 metrics 关闭后取消旧重试；应用退出后不补发。

### 4.9 网络与日志

- 单个 `reqwest::Client` 复用连接池；总超时 10 秒；
- heartbeat 失败不能阻断 Direct、Workflow、AUTO；
- 客户端日志只记录 heartbeatId、reason、result、HTTP status、耗时、attempt 和 skipReason；
- 不记录 API Key、userId、完整 URL query 或请求/响应体。

## 5. 服务端处理方案

### 5.1 分层

```text
HeartbeatController
  └─ HeartbeatApplicationService
       ├─ ReportAuthService
       ├─ HeartbeatValidator
       ├─ StatDateResolver
       └─ HeartbeatRepository
            ├─ client_heartbeat_event
            └─ heartbeat_daily
```

Controller 处理 HTTP DTO、body size、认证和响应；ApplicationService 编排幂等事务；Repository 封装 insert/upsert；统计查询使用独立 QueryService。

### 5.2 接收事务

1. 限制 body 最大 8 KiB。
2. 使用现有 `X-Maling-Report-Key` 中间件认证，禁止记录 Key。
3. DTO 拒绝未知字段。
4. 校验 UUID、userId、reason、clientVersion 和 os。
5. 规范化 userId；空值或 `unknown` 拒绝。
6. 生成 UTC `receivedAt`，转换到 `Asia/Shanghai` 后得到 statDate。
7. 开启事务并尝试插入 `client_heartbeat_event`。
8. heartbeatId 已存在则提交并返回 duplicate，不更新日聚合。
9. 新事件 upsert `heartbeat_daily`；reason=appStarted 时 appStartCount 加 1；六种 reason 均保留在原始事件表供分类统计。
10. 提交并返回 accepted。

统计只使用 receivedAt/statDate，不接收客户端时间。

### 5.3 原始事件表

```sql
CREATE TABLE client_heartbeat_event (
    heartbeat_id CHAR(36) NOT NULL,
    user_id VARCHAR(128) COLLATE utf8mb4_0900_as_ci NOT NULL,
    reason VARCHAR(32) NOT NULL,
    client_version VARCHAR(64) NOT NULL,
    os VARCHAR(16) NOT NULL,
    received_at DATETIME(3) NOT NULL COMMENT 'UTC',
    stat_date DATE NOT NULL COMMENT 'Asia/Shanghai',
    PRIMARY KEY (heartbeat_id),
    KEY idx_heartbeat_user_date (user_id, stat_date),
    KEY idx_heartbeat_received_at (received_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_as_ci;
```

原始表用于幂等、排障和 90 天内重算，不承载报表查询。按 receivedAt 索引分批清理超过 90 天的数据，不做物理分区，以保持 heartbeatId 全局唯一约束简单可靠。

### 5.4 用户日聚合表

```sql
CREATE TABLE heartbeat_daily (
    stat_date DATE NOT NULL COMMENT 'Asia/Shanghai partition key',
    user_id VARCHAR(128) COLLATE utf8mb4_0900_as_ci NOT NULL,
    latest_client_version VARCHAR(64) NOT NULL,
    latest_os VARCHAR(16) NOT NULL,
    app_start_count INT UNSIGNED NOT NULL DEFAULT 0,
    first_received_at DATETIME(3) NOT NULL COMMENT 'UTC',
    last_received_at DATETIME(3) NOT NULL COMMENT 'UTC',
    PRIMARY KEY (stat_date, user_id),
    KEY idx_heartbeat_daily_user_date (user_id, stat_date),
    KEY idx_heartbeat_daily_version_date (latest_client_version, stat_date),
    KEY idx_heartbeat_daily_os_date (latest_os, stat_date)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_as_ci
PARTITION BY RANGE COLUMNS(stat_date) (
    PARTITION p202608 VALUES LESS THAN ('2026-09-01'),
    PARTITION p202609 VALUES LESS THAN ('2026-10-01'),
    PARTITION p202610 VALUES LESS THAN ('2026-11-01'),
    PARTITION p_future VALUES LESS THAN (MAXVALUE)
);
```

分区名和边界由 migration 按实际上线月份生成。维护任务每月提前创建未来 3 个月分区，通过 `REORGANIZE PARTITION p_future` 保留兜底分区；缺少未来分区时告警。heartbeat_daily 长期保留。

`latestClientVersion/latestOs` 必须来自该用户当天 receivedAt 最大的 heartbeat。并发 upsert 使用 lastReceivedAt 条件更新，不能让较早请求覆盖较新值。

### 5.5 幂等与并发

```text
BEGIN
  rawInserted = INSERT IGNORE client_heartbeat_event
  if !rawInserted:
    COMMIT; return duplicate

  UPSERT heartbeat_daily:
    app_start_count += (reason == appStarted ? 1 : 0)
    first_received_at = MIN(old, receivedAt)
    if receivedAt >= old.last_received_at:
      latest_client_version = incoming.clientVersion
      latest_os = incoming.os
    last_received_at = MAX(old, receivedAt)
COMMIT
```

幂等必须依赖数据库唯一键，禁止“先查再写”。任一步失败整体回滚，不能出现原始事件已写入但日聚合未更新。

## 6. 统计口径

所有日期按 `Asia/Shanghai`，自然周为周一至周日。

```text
DAU(D) = heartbeat_daily 中 statDate=D 的行数
WAU(D) = [D-6,D] 内 distinct userId
MAU(D) = [D-29,D] 内 distinct userId
DAU/MAU(D) = DAU(D) / MAU(D)
周活跃回访率(W→W+1) = W 与 W+1 都活跃的 userId 数 / W 活跃 userId 数
首次观测用户(W) = 全部 heartbeat_daily 中 MIN(statDate) 落在 W 的 userId
首次观测用户次周留存(W→W+1) = 首次观测用户中 W+1 活跃人数 / W 首次观测用户数
人均应用启动次数(D) = SUM(appStartCount) / DAU(D)
版本活跃用户(D,V) = statDate=D 且 latestClientVersion=V 的行数
系统活跃用户(D,OS) = statDate=D 且 latestOs=OS 的行数
```

规则：

- 次周留存只发布 W+1 已完整结束的 cohort；观察中不进入趋势，分母为 0 返回 null；
- “首次观测”直接从正式上线后的数据计算；存量用户少，接受其首次出现被视为新用户；
- userId 是 WB 模式用户主体，按不区分大小写处理；
- 版本和 OS 使用用户当天最后值，每个用户每天只进入一个版本和一个 OS；
- appStartCount 只统计服务端成功接收的 appStarted；
- heartbeat 不表达在线时长或活动强度。

## 7. 可观测性

客户端日志字段：`heartbeat_id/reason/result/http_status/latency_ms/attempt/skip_reason`。

服务端指标：

- `heartbeat_requests_total{result}`；
- `heartbeat_duplicates_total`；
- `heartbeat_validation_errors_total{code}`；
- `heartbeat_transactions_total{result}`；
- `heartbeat_request_duration_ms`；
- `heartbeat_transaction_duration_ms`。

userId 和 API Key 禁止作为 metrics label。服务端 5xx 五分钟超过 1%、数据库事务持续失败或当日 accepted 较七日同小时均值下降 50% 时告警。

## 8. 测试与验收

### 8.1 客户端单元测试

1. payload 严格只有 5 个 camelCase 字段。
2. heartbeatId 每个逻辑 heartbeat 新建；appStarted 和四类业务事实重试保持不变。
3. whoami 在 Windows/macOS/Linux 的适配由 provider mock 验收；空值、错误、unknown 不发送。
4. userId trim、小写化正确。
5. 配置就绪立即发送 appStarted，不依赖 workspace。
6. 暂时故障按 30 秒、2 分钟重试，确定性错误不自动重试。
7. 配置变化可重新发送 pending/rejected appStarted；关闭 metrics 取消重试。
8. appStarted 成功后 15 分钟内 activity 被节流。
9. focus、pointerdown、keydown 和 Direct/Workflow/AUTO 业务命令均触发 activity。
10. 鼠标移动、滚动、后台执行不触发。
11. activity 成功后节流 15 分钟；失败后退避 1 分钟并等待下次真实操作。
12. in-flight 合并、不写 outbox、不阻断业务。
13. 日志不含 API Key、userId 和请求正文。
14. default/其他渠道不发送，只有 wb 渠道可进入 Reporter。
15. 配置关闭或变化后，旧 generation 的延迟重试不发送；新配置复用原 appStarted 请求。
16. 2xx 必须解析成功 envelope；畸形 2xx 按暂时故障处理。
17. 六类生命周期事实经总线唯一映射为六种 reason，producer 不直接调用 reporter。
18. Conversation 新建和 rerun 创建新 runId 时按 canonical runMode 各发布一次；follow-up、continue、retry、旧工作台、scheduled runtime 和 AUTO child run 不发布。
19. 定时任务 durable create 在 coordinator notify 前发布；notify 失败不撤销已经形成的事实。
20. 业务事实并发发送和有限重试不改变 activity 节流、退避或 in-flight 状态。
21. subscriber panic、配置错误和网络失败不改变任务接口结果或 canonical state。
22. activity 先占用共享发送槽时，appStarted 保持首次待发送，并在 activity 完成后自动发送且只发送一次。

所有时间测试使用可注入 Clock，不得真实 sleep。

### 8.2 服务端单元测试

1. 认证、未知字段、UUID、枚举、空 userId 和长度错误码正确。
2. userId 大小写规范化后落入同一日聚合行。
3. receivedAt 保存 UTC，statDate 按 Asia/Shanghai 跨日正确。
4. 首次请求写 raw 和 daily；重复 heartbeatId 不改变聚合。
5. appStarted 使 appStartCount 加 1，activity 不增加。
6. 并发相同 heartbeatId 最终只聚合一次。
7. 较早 receivedAt 不能覆盖当天 latest version/OS。
8. 任一写入失败全部回滚。
9. 月分区裁剪、未来分区创建和 p_future 重组正确。
10. 90 天原始表清理不影响长期 daily。
11. 周活跃回访率和完整 cohort 次周留存查询正确，空分母返回 null。

### 8.3 接口验收

真实 HTTP 与测试数据库固化六种 reason、重复 heartbeatId、跨日 receivedAt、大小写 userId、认证和非法请求；Direct、Workflow、AUTO 新建/重跑产生对应 Started，继续只产生 activity。

## 10. 发布、回滚与完成定义

当前为开发阶段破坏式升级：先部署服务端 migration 和新 DTO，再发布客户端；不接受旧请求，不保留兼容 DTO。出现服务端故障时回滚服务和 migration；临时止损使用现有 metrics 总开关，不新增 heartbeat 专用开关。

完成标准：请求严格 5 字段和六种 reason；客户端无周期 heartbeat；Started 只表达用户顶层新 runId，定时任务只在 durable create 后记录；全部信号经现有总线投影，上报失败不影响任务；跨平台 userId、有限重试、activity 15 分钟节流和接口边界均有回归测试；日志和监控不泄露身份或请求正文。
