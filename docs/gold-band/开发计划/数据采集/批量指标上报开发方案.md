# 批量指标上报开发方案

> 本文是 `POST /api/client-report/metrics/batch` 的独立开发依据，覆盖 Gold Band 客户端事件采集、SQLite outbox、批量上传、崩溃恢复，以及控制台服务端接收、幂等、原始存储和事实物化。用户活跃由 heartbeat 负责，不在本文重复设计。

## 1. 目标与边界

### 1.1 目标

- 使用同一接口承载 Direct、Workflow、AUTO 三种处理模式。
- 明确每种模式的产品统计主单位。
- started 提供可信分母，finished 提供终局。
- token 按真实计费执行单元归属且全局去重。
- 网络失败、应用重启和响应丢失不造成事件丢失或重复累计。
- 服务端允许同一批次部分接受、部分重复、部分拒绝。
- 原始事件与物化事实解耦，支持重放、修复和指标演进。

### 1.2 不做

- 不新增 `/events` 等第三个指标端点。
- 不继续上传 V1 NodeMetricItem 节点快照。
- 不上传 RUNNING、前驱重复记录或开始/结束 sentinel。
- 不把 Direct 首轮内部单 Worker 壳统计为 Workflow run。
- 不把 AUTO outer container、dynamic node 和 child workflow 的 token 重复计费。
- 不上传 task title、prompt、回复、工具输入输出、附件路径或正文。
- 不在客户端计算成功率、留存率、自动化率或 token 效率。
- 不使用 heartbeat 承载 execution 状态。

## 2. 当前实现与根因

当前 `src-tauri/src/metrics/mod.rs`：

- 只处理 `NodeStarted/NodeCompleted`；
- 将节点状态转换为 `NodeMetricItem`；
- 在 NodeStarted 时构造前驱记录、RUNNING 和开始 sentinel；
- 在 NodeCompleted 时构造节点结果和结束 sentinel；
- lifecycle subscriber 直接创建 `reqwest::Client` 并发送 HTTP；
- 网络失败只写日志，不持久化、不重试；
- `RunPaused/InterventionRequested/RunCompleted/AcpTurnFinished` 没有进入批量指标；
- canonical UUID 缺失时回退展示 ID，服务端无法稳定 JOIN；
- token 读取 ACP session 累计值，存在同 session 多轮重复计算风险。

根因是数据模型仍以“节点快照”而不是“领域事实”为中心。V2 必须先建立 execution、unit、transition、intervention、usage 五类事实，再实现可靠投递。

## 3. 统计主单位

| 模式 | 产品主 execution | 内部 unit | finished 含义 |
|---|---|---|---|
| Direct | 每次 ACP prompt turn | 不上报首轮内部单 Worker 壳 | 本轮回复 completed/failed/cancelled |
| Workflow | runtime product run | workflow node attempt | run success/failure/killed |
| AUTO | outer runtime run | dynamic node attempt、需要下钻的 workflow node attempt | outer run success/failure/killed |

约束：

- Direct 首轮只产生一个 turn execution。
- Workflow/AUTO 完成后的手动追问产生新 turn，mode 继承上下文，但不修改既有 run。
- AUTO child workflow 是下钻 execution，携带父关系，不进入 outer run 产品成功率分母。
- `execution.started` 是完成率和成功率的唯一分母来源。
- `unit.finished` 只表达已定局的内部执行单元，不承担产品主分母。

## 4. 接口契约

### 4.1 请求

```http
POST /api/client-report/metrics/batch
X-Maling-Report-Key: <api-key>
Content-Type: application/json;charset=UTF-8
```

```json
{
  "schemaVersion": 2,
  "batchId": "a4c480b7-6acc-43dc-8051-da759d4e58c6",
  "sentAt": "2026-07-30T02:20:00.000Z",
  "client": {
    "clientVersion": "0.1.0",
    "os": "windows"
  },
  "events": []
}
```

批次级 client 只保留传输客户端元数据。userId 和 workspace 必须固化在每个事件中，因为 outbox 可能同时重试多个 workspace 的历史事件。

约束：

- `schemaVersion` 固定为 2。
- `batchId` 是本次 HTTP 尝试 UUID，只用于链路追踪，不参与事件幂等。
- `sentAt` 是本次 HTTP 尝试的 UTC RFC 3339 时间，用于区分本地排队和网络延迟。
- 单批最多 200 个事件。
- 未压缩 JSON 最大 512 KiB。
- 单事件序列化后最大 64 KiB。
- uploader 按 `createdAt/eventId` 稳定顺序选择事件。
- 客户端同一时间最多一个 metrics/batch 请求 in-flight。

### 4.2 统一事件信封

```json
{
  "eventId": "f116359e-a402-4af5-8144-a9a4408f8da0",
  "idempotencyKey": "sha256:...",
  "type": "execution.started",
  "occurredAt": "2026-07-30T02:19:40.000Z",
  "mode": "direct",
  "userId": "kelvinzhou",
  "workspace": "D:\\IdeaProjects\\Gold-Band",
  "taskId": "task uuid",
  "execution": {
    "executionId": "turn uuid",
    "executionKind": "turn",
    "origin": "followUp"
  },
  "refs": {
    "runId": "run uuid",
    "turnId": "turn uuid",
    "roundId": null,
    "nodeId": null,
    "nodeKey": null,
    "attemptId": null,
    "parentExecutionId": null,
    "parentUnitId": null,
    "dynamicRunId": null,
    "outerNodeId": null,
    "outerAttemptId": null
  },
  "payload": {}
}
```

| 字段 | 约束 | 作用 |
|---|---|---|
| `eventId` | UUID；一次真实事件一个 | outbox 主键和服务端原始事件主键 |
| `idempotencyKey` | `sha256:` 前缀固定摘要 | reconciliation 重建同一事实时仍能幂等 |
| `type` | 受控枚举 | 决定 payload DTO |
| `occurredAt` | UTC RFC 3339 | 业务事实发生时间 |
| `mode` | `direct/workflow/auto` | 处理模式 |
| `userId` | 规范化 userId | WB 用户身份 |
| `workspace` | 1～255 字符 | execution 所属 workspace |
| `taskId` | canonical UUID | 任务关联 |
| `execution` | 强类型结构 | 主 execution 关联 |
| `refs` | 强类型可选引用 | run/turn/unit/AUTO 父子关系 |
| `payload` | 按 type 解析 | 事件专属事实 |

公共枚举：

```text
executionKind = turn / run
origin = initialPrompt / followUp / newRun / rerun / runtimeContinue
eventType =
  execution.started
  execution.finished
  execution.paused
  execution.resumed
  unit.finished
  intervention.requested
```

### 4.3 eventId 与 idempotencyKey

两者不能合并：

- eventId 表示客户端实际记录的一次事件。
- idempotencyKey 表示领域中的同一事实。
- 正常网络重试复用完整 outbox 行，因此两者都不变。
- 领域状态已落盘但 outbox 写入前崩溃时，reconciliation 可以生成新 eventId，但必须得到相同 idempotencyKey。

idempotencyKey 使用版本化命名空间拼接 canonical ID 后计算 SHA-256：

```text
v2|execution|{mode}|{executionId}|started
v2|execution|{mode}|{executionId}|finished
v2|unit|{attemptId}|finished
v2|transition|{transitionId}
v2|intervention|{requestId}
```

禁止把 task title、node label、workspace 路径或错误文案放入幂等键。

### 4.4 成功响应

合法批次统一返回 HTTP 200；单事件错误不让其他事件回滚。

```json
{
  "code": 200,
  "msg": "",
  "data": {
    "requestId": "server request uuid",
    "batchId": "a4c480b7-6acc-43dc-8051-da759d4e58c6",
    "acceptedEventIds": ["event-a"],
    "duplicateEventIds": ["event-b"],
    "rejected": [
      {
        "eventId": "event-c",
        "error": {
          "code": 422103,
          "params": {
            "field": "payload.outcome"
          }
        }
      }
    ],
    "receivedAt": "2026-07-30T02:20:01.000Z"
  }
}
```

`acceptedEventIds`、`duplicateEventIds`、`rejected[].eventId` 必须覆盖请求中全部 eventId，且互不重叠。客户端发现响应缺失或出现未知 eventId 时，将整个选中批次恢复为 pending，按暂时性故障重试。

### 4.5 请求级错误

| HTTP | code / 常量 | 处理 |
|---|---|---|
| 400 | `400200 / REPORT_BATCH_INVALID_BODY` | 暂停 uploader，记录客户端契约错误 |
| 400 | `400201 / REPORT_BATCH_INVALID_SCHEMA_VERSION` | 暂停 uploader，等待客户端升级 |
| 401/403 | `401000 / REPORT_AUTH_INVALID` | 暂停，配置变化后恢复 |
| 413 | `413200 / REPORT_BATCH_TOO_LARGE` | 客户端二分批次；单事件仍超限则 rejected |
| 429 | `429000 / REPORT_RATE_LIMITED` | 按 Retry-After 或退避重试 |
| 500/503 | `500000 / REPORT_INTERNAL_ERROR` | 全批恢复 pending 并退避 |

### 4.6 事件级错误

| code / 常量 | 含义 |
|---|---|
| `422100 / REPORT_EVENT_INVALID_ENVELOPE` | 公共信封非法 |
| `422101 / REPORT_EVENT_INVALID_ID` | canonical ID/UUID 非法 |
| `422102 / REPORT_EVENT_INVALID_REFS` | 引用关系不满足 type/mode 约束 |
| `422103 / REPORT_EVENT_INVALID_PAYLOAD` | type 专属 payload 非法 |
| `422104 / REPORT_EVENT_TOO_LARGE` | 单事件超过 64 KiB |
| `422105 / REPORT_EVENT_PRIVACY_VIOLATION` | 出现禁止字段 |

服务端只返回 code 和可机器处理的 params，不返回对客文案。

## 5. 事件模型

客户端必须使用 Rust enum + typed payload，禁止用任意 `serde_json::Value` 在业务代码中拼事件。

```rust
    ExecutionFinished(ExecutionFinishedPayload),
    ExecutionPaused(ExecutionPausedPayload),
    ExecutionResumed(ExecutionResumedPayload),

}
```

## 6. 客户端开发方案

### 6.1 模块划分

纯领域模型：

```text
src/analytics/
  mod.rs
  event.rs
  identity.rs
  idempotency.rs
  projection.rs
  usage.rs
```

桌面端可靠投递：

```text
src-tauri/src/analytics/
  mod.rs
  recorder.rs
  outbox.rs
  uploader.rs
  response.rs
  reconciliation.rs
  diagnostics.rs
```

原 `src-tauri/src/metrics/mod.rs` 只保留共享配置并逐步迁移：

- heartbeat 继续使用独立 heartbeat 模块。
- V1 NodeMetricItem、NodeMetricBatch、sentinel 和直接 HTTP subscriber 全部删除。
- base URL、API Key、endpoint 和共享 reqwest client 放入 `client_report.rs`。

### 6.2 领域状态先行

先补齐持久化数据，再投影事件：

- TaskState、RunState、RoundState、NodeState 使用 canonical UUID。
- 每次真实 attempt 创建并持久化 attemptUuid。
- 每次 ACP prompt 接受前创建并持久化 turnId、startedAt、usageBaseline。
- run 创建时持久化 startedAt、origin、mode。
- pause/resume/intervention 在 runtime 领域状态中追加最小 lifecycle history，包含 transitionId/requestId、occurredAt、refs 和结构化原因。
- AUTO dynamic node、outer attempt、dynamic run 和 child workflow 父子 ID 持久化。

禁止为 analytics 单独维护一套与 runtime 生命周期竞争的状态。analytics 只投影已成功持久化的领域事实。

### 6.3 生命周期投影

需要新增或扩展 RuntimeLifecycleEvent：

```text
AcpTurnStarted
AcpTurnFinished
RunStarted
RunPaused
RunResumed
RunCompleted
UnitFinished
InterventionRequested
```

投影规则：

| 领域事件 | analytics event |
|---|---|
| AcpTurnStarted | execution.started(turn) |
| AcpTurnFinished | execution.finished(turn) |
| RunStarted | execution.started(run) |
| RunPaused | execution.paused |
| RunResumed | execution.resumed |
| RunCompleted | execution.finished(run) |
| terminal node/dynamic attempt | unit.finished |
| InterventionRequested | intervention.requested |

Direct 首轮内部 NodeStarted/RunStarted 必须标记 `internalShell`，projection 不生成 Workflow execution/unit。

### 6.4 usage baseline

- turn/attempt 开始时读取 ACP usage counter，保存 baseline。
- 结束时读取 counter，计算 `max(end-start, 0)`。
- counter 回退、session 更换或字段缺失时不上报负数，记录 `analytics.usage.counter-reset`。
- requestedModel 只表示请求值；resolvedModel 必须来自 provider/session 实际结果。
- usageScopeId 在领域状态中稳定保存，不能在 serializer 临时生成。

### 6.5 专用 SQLite outbox

使用独立 `analytics.sqlite3`，不与可重建的搜索索引数据库共用生命周期。

初始化：

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
PRAGMA busy_timeout = 5000;
```

```sql
CREATE TABLE analytics_outbox (
    event_id TEXT NOT NULL,
    idempotency_key TEXT NOT NULL,
    schema_version INTEGER NOT NULL,
    event_type TEXT NOT NULL,
    mode TEXT NOT NULL,
    occurred_at TEXT NOT NULL,
    payload_json TEXT NOT NULL,
    status TEXT NOT NULL,
    attempt_count INTEGER NOT NULL DEFAULT 0,
    next_attempt_at TEXT NOT NULL,
    lease_owner TEXT,
    lease_until TEXT,
    created_at TEXT NOT NULL,
    acked_at TEXT,
    last_error_code INTEGER,
    PRIMARY KEY (event_id),
    UNIQUE (idempotency_key),
    CHECK (status IN ('pending','in_flight','acked','rejected'))
);

CREATE INDEX idx_analytics_outbox_ready
ON analytics_outbox(status, next_attempt_at, created_at);

CREATE INDEX idx_analytics_outbox_lease
ON analytics_outbox(status, lease_until);
```

Recorder 只做规范化、序列化和 SQLite `INSERT OR IGNORE`，不得执行网络请求。写入失败不能阻断业务主流程，但必须记录结构化诊断。

### 6.6 claim 与批次构造

Uploader 单实例运行：

1. 开启 SQLite 事务。
2. 选择 pending 或 lease 已过期的 in_flight 行。
3. 按 createdAt/eventId 排序。
4. 逐条加入，直到达到 200 条或下一条会超过 512 KiB。
5. 设置 `status=in_flight`、leaseOwner、leaseUntil=当前时间+60 秒。
6. 提交后发送 HTTP。

单事件超过 64 KiB 时不进入网络批次，直接标记 rejected，错误码 `REPORT_EVENT_TOO_LARGE`。禁止为满足大小限制截断 payload。

### 6.7 响应处理

在一个 SQLite 事务内：

- accepted、duplicate → acked。
- rejected → rejected + lastErrorCode。
- 响应缺项、未知 eventId 或响应不可解析 → 本批恢复 pending。
- 网络错误、超时、429、5xx → 本批恢复 pending 并设置退避。
- 401/403 → 本批恢复 pending，暂停 uploader。
- 413 → 恢复 pending，下次将批次上限减半；单事件仍 413 时 rejected。

acked 保留 7 天，rejected 保留 30 天；清理任务不得删除 pending/in_flight。数据库达到软阈值时先清理 acked/rejected 并 checkpoint；不得静默淘汰 pending。

### 6.8 重试

暂时性失败使用 full jitter：

```text
cap = min(5s × 2^attemptCount, 30min)
delay = random(0, cap)
```

429 优先使用合法 Retry-After，并限制在 1 秒～1 小时。配置变化后恢复 401/403 暂停。正常退出最多等待 2 秒 flush，但正确性不依赖退出 flush。

### 6.9 reconciliation

文件领域状态与 SQLite 无法原子提交，流程固定为：

1. 领域状态先落盘。
2. 同步写 outbox。
3. 再发进程内 UI/通知 lifecycle event。

启动后后台 reconciliation：

- 只扫描 analytics 启用后的领域状态。
- 为 execution.started/finished、unit.finished 重新计算确定性 idempotencyKey。
- 从持久化 lifecycle history 重建 pause/resume/intervention。
- `INSERT OR IGNORE` 补齐 outbox。
- 使用持久化 watermark 分页扫描，不阻塞应用启动。

如果 metrics 从关闭变为开启，从开启时刻建立采集边界，不回溯开启前的数据。关闭时停止新事件记录和 uploader。

### 6.10 隐私与日志

允许结构字段：

- canonical IDs；
- userId、workspace；
- mode、origin、kind、outcome、reason code；
- provider/model ID；
- token、耗时和受控计数。

禁止字段：

- task/node title；
- prompt、回复、goal；
- system prompt、profile 正文；
- tool input/output；
- attachment path/content；
- API Key。

客户端日志只记录 batchId、eventId、type、结果、HTTP status、attempt、延迟和错误码；不记录 payload_json、userId、workspace 或 API Key。

## 7. 服务端处理方案

### 7.1 分层

```text
MetricsBatchController
  └─ MetricsBatchApplicationService
       ├─ ReportAuthService
       ├─ BatchValidator
       ├─ EventValidatorRegistry
       ├─ RawEventRepository
       └─ MaterializationScheduler

AnalyticsMaterializer
  ├─ ExecutionProjector
  ├─ UnitProjector
  ├─ TransitionProjector
  ├─ InterventionProjector
  └─ UsageProjector
```

Controller 不计算业务指标。写接口只校验并追加原始事实；物化器异步、可重放、可按事件类型独立升级。

### 7.2 接收流程

1. 限制 body 512 KiB，认证 API Key。
2. 校验 schemaVersion、batchId、sentAt、client 和 events 数量。
3. 检查 batch 内 eventId/idempotencyKey 是否自重复。
4. 每个事件分别执行公共信封、type payload、mode/refs 和隐私校验。
5. 非法事件加入 rejected，不参与 raw 事务。
6. 对合法事件开启数据库事务，批量 `INSERT IGNORE analytics_event_raw`。
7. 根据 eventId/idempotencyKey 唯一约束区分 accepted/duplicate。
8. 提交 raw 事务。
9. 发布物化任务。
10. 返回覆盖全部 eventId 的 accepted/duplicate/rejected 响应。

如果合法事件的 raw 事务失败，返回 5xx，不返回部分 accepted，客户端整批重试。

### 7.3 原始事件表


### 7.9 物化流程

物化器按 raw receivedAt/eventId 拉取：

1. claim pending 或过期 processing 行。
2. 按 eventType 反序列化 typed payload。
3. 在事务内 upsert 对应 fact，并按 usageScopeId 插入 usage_fact。
4. 成功后 raw 标记 materialized。
5. 暂时性 DB 错误退避重试。
6. 事件已通过接收校验却无法物化时标记 failed，触发告警，不静默跳过。

重放时先清理目标日期/ID 范围的派生 fact，再从 raw 重建；原始事件不可被物化器修改。

### 7.10 时间与乱序

- occurredAt 和 receivedAt 均以 UTC 存储。
- 指标按 occurredAt 归属业务日期，receivedAt 用于接收延迟和排障。
- 客户端时钟偏差超过 24 小时的事件仍保存 raw，但物化标记 clockSkew，默认不进入实时看板，等待校正策略。
- materializer 必须允许 started/finished、parent/child 乱序。
- 同一 execution 多个冲突 finished 不能后写覆盖；保留首个终局并告警 `REPORT_EXECUTION_TERMINAL_CONFLICT`。

## 8. 三种模式处理方案

### 8.1 Direct

首次 prompt：

1. 生成并持久化 turnId、startedAt 和 usage baseline。
2. 记录 `execution.started(mode=direct, origin=initialPrompt)`。
3. 内部单 Worker run 标记 internalShell，不投影 Workflow execution/unit。
4. ACP 本轮结束后读取 usage delta。
5. 记录 `execution.finished`。

后续 prompt 每次新建 turnId。completed/failed/cancelled 均生成 finished；运行中的 prompt 因崩溃未完成时，reconciliation 至少能补 started，服务端将其识别为 unclosed。

### 8.2 Workflow

1. run/round/首节点状态持久化后记录 run started。
2. 每个 terminal node attempt 记录 unit.finished。
3. retry 必须创建新的 attemptUuid。
4. pause/resume 使用持久化 transitionId。
5. intervention 使用稳定 requestId。
6. run 终局记录 execution.finished。
7. run 完成后的手动追问记录 turn started/finished，mode=workflow、origin=followUp。

new round 仍属于同一 run execution；是否首过通过 `newRoundsOpened=0` 计算。

### 8.3 AUTO

1. outer run 是产品主 execution。
2. AI-DYNAMIC outer attempt 是 container。
3. worker/merge/acceptance/workflowInvocation 是 dynamic unit。
4. child workflow run 带 parentExecutionId 和 parentUnitId。
5. child run 不进入 outer run 成功率分母。
6. workflowInvocation 与 child run token 只归一个 billable usageScopeId。
7. outer run finished 从持久化 DynamicGraphState 读取受控计数。

AUTO goal、proposal、acceptance 文本和动态节点 task 不上传。

## 9. 指标物化口径

```text
终局覆盖率 = 有 finished 的 eligible started execution / eligible started execution
unclosed 率 = 超过 terminalGracePeriod 仍无 finished / eligible started

Direct 回复完成率 = completed turn / eligible started turn
Direct 失败率 = failed turn / eligible started turn
Direct 取消率 = cancelled turn / eligible started turn

Workflow 成功率 = success product run / eligible started workflow run
Workflow 首过率 = success 且 newRoundsOpened=0 / eligible started workflow run

AUTO 成功率 = success outer run / eligible started AUTO outer run
AUTO 全自动率 = 无 intervention 的成功 outer run / eligible started AUTO outer run

token 效率 = SUM(usage_fact.total_tokens) / 对应成功 execution
```

terminalGracePeriod 配置化。未超过宽限期的无终局 execution 标为 inProgressOrLate，不立即算失败。任何成功率看板必须同时展示终局覆盖率和样本量。

## 10. 可观测性

客户端：

- `analytics_record_total{type,result}`
- `analytics_outbox_rows{status}`
- `analytics_upload_batches_total{result}`
- `analytics_upload_events_total{result}`
- `analytics_reconciliation_total{result}`
- `analytics_oldest_pending_age_seconds`

服务端：

- `metrics_batch_requests_total{result}`
- `metrics_batch_events_total{result,type}`
- `analytics_materialization_total{result,type}`
- `analytics_materialization_lag_seconds`
- `analytics_terminal_conflicts_total`
- `analytics_clock_skew_total`

高基数 ID、userId、workspace、provider/model 不作为 metrics label。

告警：

- oldest pending 超过 30 分钟；
- uploader 连续暂停或认证失败；
- 服务端 5xx 五分钟超过 1%；
- materialization lag 超过 10 分钟；
- failed materialization 或 terminal conflict 大于 0。

## 11. 测试方案

### 11.1 领域与 serializer

1. 六类 event 的 JSON snapshot。
2. payload 与 type 不匹配时不能构造。
3. canonical UUID 缺失时 recorder 拒绝，不回退展示 ID。
4. idempotencyKey 对同一事实稳定，不同 transition/request 不碰撞。
5. 禁止字段不会进入 payload。
6. 单事件 64 KiB、批次 200 条/512 KiB 边界。

### 11.2 Direct

1. 首轮只有一个 Direct turn execution。
2. 后续每次 prompt 有新 turnId。
3. 内部单 Worker 不生成 Workflow execution/unit。
4. 同 ACP session 连续 turn 的 usage 按 baseline 增量计算。
5. completed/failed/cancelled 正确投影。
6. 崩溃后的未完成 turn 可补 started 并形成 unclosed。

### 11.3 Workflow

1. 首节点完成前退出仍存在 run started。
2. retry attemptUuid 不覆盖旧 attempt。
3. pause/resume transitionId 唯一且可重建。
4. new round 不新建 run execution。
5. 完成后 follow-up 不改 run outcome。
6. unit usageScopeId 防重。

### 11.4 AUTO

1. outer run 只有一个产品主 execution。
2. dynamic kind、depth、groupId 和 parentUnitId 正确。
3. workflowInvocation 正确关联 child run。
4. child run 不进入 outer run 分母。
5. outer container、dynamic unit、child run token 不重复。
6. acceptance/rejected proposal 只上传计数，不上传文本。

### 11.5 outbox/uploader

1. 相同 idempotencyKey 重复 record 只保留一行。
2. claim 事务和 lease 过期恢复。
3. 200 条、512 KiB 双重切批。
4. accepted/duplicate/rejected 部分响应原子更新。
5. 响应缺项恢复整批 pending。
6. 413 自动二分，单事件超限 rejected。
7. 429 Retry-After、5xx/full jitter、401 暂停正确。
8. 崩溃遗留 in_flight 可恢复。
9. acked/rejected 清理不删除 pending。

### 11.6 reconciliation

1. 状态已落盘、outbox 缺失时补写。
2. 重建事件使用相同 idempotencyKey。
3. pause/resume/intervention 从 lifecycle history 恢复。
4. analytics 开启前数据不回溯。
5. 大量状态分页扫描不阻塞启动。

### 11.7 服务端

1. 请求级认证、schema、大小错误。
2. 单个坏事件不影响其他合法事件。
3. eventId/idempotencyKey 重复只保存一次。
4. 响应完整覆盖请求 eventId。
5. raw 事务失败整批 5xx。
6. finished 先于 started 最终能补齐 execution_fact。
7. 冲突 finished 不覆盖首个终局并产生告警。
8. usageScopeId 跨 execution/unit 全局防重。
9. pause/resume 保留历史，不覆盖。
10. raw 重放得到相同 facts。

### 11.8 接口验收

使用真实 HTTP、测试 MySQL 和客户端测试 SQLite 固化：

- Direct 首轮与 follow-up；
- Workflow started/unit/pause/resume/intervention/finished；
- AUTO outer/dynamic/child hierarchy；
- 部分 accepted/duplicate/rejected；
- 网络失败、重启、lease 恢复和 reconciliation；
- token 防重、乱序物化和终局冲突。

## 13. 发布、回滚与完成定义

当前为开发阶段破坏式升级：

1. 先部署服务端 V2 schema、raw 接收和事实表。
2. 再发布客户端 V2 serializer/outbox/uploader。
3. 不兼容 V1 `metrics` 请求体，不做双写或 404 fallback。
4. 客户端 migration 删除 V1 pending 数据，不把节点快照转换成 V2 事实。
5. 服务端故障时客户端 outbox 持续保留 pending；回滚客户端前必须确认 V2 outbox 的处置方案，不能静默删除未确认事件。

完成标准：

- Direct、Workflow、AUTO 主统计单位正确；
- started/finished 分母和终局完整；
- V1 节点快照、sentinel 和直接 HTTP 已删除；
- outbox 在断网、重启和响应丢失下不丢不重；
- 服务端逐事件接受并全局幂等；
- 五类事实表可从 raw 重放；
- usageScopeId 跨 execution/unit 全局防重；
- 隐私字段不进入 payload、日志或监控标签；
- 客户端和服务端接口验收全部固化。
