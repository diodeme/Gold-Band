# 批量指标上报生命周期与统计口径优化方案

> 状态：客户端已实现并完成接口级验收；服务端仅交付实施合同，待服务端仓库执行
>
> 适用接口：`POST /api/client-report/metrics/batch`
>
> 关联设计：[WB 会话指标采集与批量上报设计](../../产品设计文档/runtime/metrics-collection.md)
>
> 本文统一收敛 `runId/roundId`、定时任务来源、task 代码变更行数、task 级 `eventRevision`、节点级中间态与 counters 口径。实现后，本文替代[指标运行定位与定时任务来源优化方案](./指标运行定位与定时任务来源优化方案.md)中的开发合同；正式产品契约仍以同步更新后的 `metrics-collection.md` 为唯一真源。

## 1. 目标与结论

本次优化不是给六个字段分别打补丁，而是统一指标事件的三个作用域：

1. **事件流作用域**：同一 task 的 `executionId` 不变；`eventRevision` 在 `(projectId, executionId)` 内统一、持久、严格递增，不因新 Round、新 Run、节点重试或进程恢复而重置。
2. **事件主体作用域**：`runId/roundId/nodeId/attemptId` 定位当前事件实际描述的 Run、Round 和 attempt；`executionKind` 必须与主体一致。
3. **统计快照作用域**：节点终态携带当前 attempt 的 counters；task 交付终态携带整个 task 从创建至当前终态的累计 counters 和代码变更行数。

最终合同：

- 所有 lifecycle event 必须携带 `runId` 和 `roundId`，使用 `run-001`、`round-001` 形式的 Runtime 本地 ID，不使用 UUID。
- 定时任务相关事件逐条携带 Task 创建来源和本次 execution 触发来源。
- Workflow/AUTO 的 `execution.paused`、`execution.resumed`、`intervention.requested` 分别属于 `node-attempt`、`unit-attempt`，不再伪装成 `run`、`outer-run`。
- Workflow node 和 AUTO unit 的 `execution.completed` 携带本 attempt counters；`run/outer-run/turn` 的交付终态携带 task 累计 counters。
- task 交付终态携带 `codeChanges`，报告 Gold Band 已捕获的 task 累计文本变更行数。
- `manualContinueCount` 与 `followUpCount` 由不同的领域动作产生，一次用户动作只能命中一个计数分支。

## 2. 根因判断

### 2.1 根本设计缺陷

当前 `executionId` 已统一为 `taskId`，但采集状态和服务端投影仍混合了 task、run 与 attempt 三种生命周期：

- revision 由 run/attempt 局部状态分配，切换 `round-002` 或 `run-002` 后可能重新从 1 开始。
- `executionKind=run/outer-run` 的中间态同时携带 node/unit 字段，主体身份自相矛盾。
- counters 只放在交付终态，无法判断某个节点产生了多少暂停、权限请求和人工恢复。
- task counters 若通过节点终态求和，会被重试、重复事件或最新快照覆盖造成重复统计。
- `manualContinueCount` 曾被用来表达人工追问，混淆了“恢复当前执行”和“发起后续目标”。
- task 完成时没有代码变更快照，服务端只能事后扫描 workspace 或猜测 Git 差异，既不可靠也会串入非本 task 变更。

根因是事件流 identity、事件主体 locator 和统计 scope 没有分层，不是 HTTP 批量发送器缺少几个可选字段。

### 2.2 不采用的补丁式方案

- 不在 serializer 发送前查询“当前 Run/Round”。迟到事件会被绑定到更新状态，并增加 I/O。
- 不按 `runId` 重置 revision。`executionId` 未变化时，这会制造同一事件流的 revision 冲突。
- 不把 node counters 相加得到 task counters。attempt 重试和快照重发会重复累计。
- 不把 `followUpCount` 当作所有人工输入次数，也不根据 prompt 文本猜测动作类型。
- 不在 task 终态执行 `git diff`、`cloc` 或全仓扫描。工作区可能预先 dirty，且外部命令会阻塞终态热路径。

## 3. 数据归属与权威事实源

| 数据 | 领域与权威来源 | 生命周期 | Wire 作用域 |
|---|---|---|---|
| `executionId` | Task canonical identity，即 `taskId` | Task 全生命周期不变 | 每事件 |
| `runId` | 已持久化 `RunState.id` | 当前 Run | 每事件 |
| `roundId` | 已持久化 `RoundState.id` | 当前 Round | 每事件 |
| `eventRevision` | `TaskMetricsState` 单调序列 | 跨 Run/Round/attempt | 每事件 |
| Task 来源 | durable Conversation metadata | Task 创建后不变 | 每事件 |
| execution 触发来源 | scheduler occurrence 或用户触发快照 | 当前 Run/Turn | 每事件 |
| attempt counters | `TaskMetricsState.activeAttempts[attemptId]` | attempt started 至 terminal | attempt terminal |
| task counters | `TaskMetricsState.taskCounters` | Task 创建至当前交付终态 | task terminal |
| 代码变更 | 现有 turn file diff 捕获结果 | Task 创建至当前交付终态 | task terminal |

内部状态使用完整作用域键：

```rust
struct TaskMetricsKey {
    project_id: ProjectId,
    execution_id: TaskId,
}

struct AttemptMetricsKey {
    run_id: RunId,
    round_id: RoundId,
    node_id: NodeId,
    attempt_id: AttemptId,
}
```

服务端不得按 `runId`、`roundId`、`nodeId` 或 `attemptId` 的末级值进行全局反查。事件流分区键固定为 `(projectId, executionId)`，具体事实键至少包含 `(projectId, executionId, runId, roundId, attemptId)`。

`projectId` 使用 workspace 已有 canonical `project_id`。若当前 metrics wire 尚未携带该字段，本次破坏式合同升级必须补为公共必填字段；原始 `workspace` 继续用于诊断和展示，但不得作为 state、唯一约束或 JOIN 的业务身份。

## 4. 统一事件输入

producer 不再自行创建 `eventId/eventRevision/reportedAt`，只提交不可变领域事实：

```rust
struct PendingMetricsFact {
    key: TaskMetricsKey,
    event_type: LifecycleEventType,
    occurred_at: DateTime,
    session_mode: MetricsSessionMode,
    subject: MetricsSubject,
    runtime_locator: MetricsRuntimeLocator,
    task_origin: MetricsTaskOrigin,
    execution_trigger: MetricsExecutionTrigger,
    transition: MetricsTransition,
    payload: MetricsPayload,
}

struct MetricsRuntimeLocator {
    run_id: RunId,
    round_id: RoundId,
}
```

`RunId/RoundId` 使用 Runtime 已有解析与生成规则，禁止在各 producer 散落正则或字符串拼接。`runId/roundId` 只在所属 task 中唯一；完整关联至少包含 `executionId`。

### 4.1 事件主体

```rust
enum MetricsSubject {
    DirectTurn {
        attempt_id: AttemptId,
        attempt_index: u32,
    },
    WorkflowRun,
    WorkflowNodeAttempt {
        node_id: NodeId,
        attempt_id: AttemptId,
        attempt_index: u32,
        round_index: u32,
        role_name: String,
    },
    AutoOuterRun,
    AutoUnitAttempt {
        node_id: NodeId,
        attempt_id: AttemptId,
        attempt_index: u32,
        round_index: u32,
        role_name: String,
        unit_kind: UnitKind,
    },
}
```

`executionKind` 由 `MetricsSubject` 唯一映射，producer 不接受裸字符串，也不能同时传入互相矛盾的 kind 与 node 字段。

### 4.2 Run/Round 约束

- `runId = RunState.id`，示例 `run-001`。
- `roundId = RoundState.id`，示例 `round-001`。
- 两者对全部 lifecycle event 必填，包括 Direct 内部映射出的 Run/Round。
- `roundIndex` 是统计序号，不替代 `roundId`。
- 新 Round：`runId` 不变，`roundId/roundIndex` 更新，revision 继续递增。
- 新 Run：`runId` 更新为 `run-002`，`roundId` 从该 Run 的真实本地 ID 开始，revision 仍继续递增。

## 5. 定时任务来源

保持“Task 创建来源”和“本次触发来源”两个不同事实：

```rust
enum MetricsTaskOrigin {
    User,
    ScheduledTask {
        scheduled_task_id: ScheduledTaskId,
    },
}

enum MetricsExecutionTrigger {
    User,
    ScheduledOccurrence {
        scheduled_task_id: ScheduledTaskId,
        scheduled_occurrence_id: ScheduledOccurrenceId,
        trigger_kind: ScheduledTriggerKind,
        scheduled_at: DateTime,
        session_policy: ScheduledSessionPolicy,
    },
}
```

字段含义：

| 对象 | 字段 | 取值/格式 | 含义与生命周期 |
|---|---|---|---|
| `taskOrigin` | `kind` | `user` / `scheduled-task` | Task 最初如何创建。Task 一旦创建即冻结，不随新的 Run、用户追问或 occurrence 改变 |
| `taskOrigin` | `scheduledTaskId` | stable ID | 创建该 Task 的定时任务定义 ID，取 `ScheduledTaskDefinition.id`。仅 `kind=scheduled-task` 时存在；不能用标题、instruction 或 cron 文案代替 |
| `executionTrigger` | `kind` | `user` / `scheduled-occurrence` | 当前这次 Run/Turn 是由普通用户动作还是 scheduler occurrence 发起。它描述本次执行，不描述 Task 的历史来源 |
| `executionTrigger` | `scheduledTaskId` | stable ID | 生成本次 occurrence 的定时任务定义 ID，取 `ScheduledOccurrence.job_id`。仅 `kind=scheduled-occurrence` 时存在 |
| `executionTrigger` | `scheduledOccurrenceId` | stable ID | 本次计划点或“立即执行”记录的唯一 ID，取 `ScheduledOccurrence.id`；在 `(projectId, scheduledOccurrenceId)` 内定位一次调度生命周期，恢复、重试和最终完成始终沿用同一值 |
| `executionTrigger` | `triggerKind` | `scheduled` / `manual` | occurrence 的创建方式。`scheduled` 表示 timer 到达计划点；`manual` 表示用户对定时任务执行“立即执行”。`manual` 仍是 scheduled occurrence，不等于普通 Task 的用户 follow-up |
| `executionTrigger` | `scheduledAt` | UTC RFC 3339 | occurrence 的目标时间，取 `ScheduledOccurrence.scheduled_at`。计划触发时表示原计划点，可与 `occurredAt/startedAt` 比较调度延迟；“立即执行”时为该 occurrence 的即时目标时间，不推进定时任务的下一计划点 |
| `executionTrigger` | `sessionPolicy` | `new` / `continuous` | occurrence 被领取时冻结的会话策略。Direct `new` 每次创建新 Task/Run/ACP session；Direct `continuous` 复用已有 Task/session chain 并发送新 prompt。Workflow/AUTO 只允许 `new`，内容未变化时可复用 Task，但每次 occurrence 创建新 Run |

两个 `scheduledTaskId` 表面相同，但不能合并成 batch 或事件顶层字段：`taskOrigin.scheduledTaskId` 解释“这个 Task 从哪里来”，`executionTrigger.scheduledTaskId` 解释“这次执行由哪个 job 触发”。当两个对象都是 scheduled 类型时，两者必须相等；定时 Task 后续接受普通用户输入时，只保留前者。

Wire 示例：

```json
{
  "taskOrigin": {
    "kind": "scheduled-task",
    "scheduledTaskId": "scheduled-task-001"
  },
  "executionTrigger": {
    "kind": "scheduled-occurrence",
    "scheduledTaskId": "scheduled-task-001",
    "scheduledOccurrenceId": "occurrence-001",
    "triggerKind": "scheduled",
    "scheduledAt": "2026-08-20T10:00:00Z",
    "sessionPolicy": "continuous"
  }
}
```

规则：

- scheduler handoff 时一次性冻结 occurrence，所有后续事件沿用，不在 reporter 发送时回查。
- “立即执行”使用 `triggerKind=manual`，仍属于 scheduled occurrence。
- 定时任务创建的 Task 后续接受用户新输入时，`taskOrigin` 保持 `scheduled-task`，`executionTrigger` 改为 `user`。
- 不上传 instruction、标题、cron 文案等可变或敏感字段。

典型组合：

| 场景 | `taskOrigin` | `executionTrigger` |
|---|---|---|
| 普通用户创建并执行 Task | `user` | `user` |
| 计划时间到达并创建/复用 Task | `scheduled-task` | `scheduled-occurrence + scheduled` |
| 用户点击定时任务“立即执行” | `scheduled-task` | `scheduled-occurrence + manual` |
| 定时 Task 完成后用户继续提出新目标 | `scheduled-task` | `user` |
| attention 恢复原定时执行 | 原值不变 | 沿用原 `scheduledOccurrenceId` 和原 `triggerKind` |

## 6. eventRevision 与可靠批量写入

### 6.1 序列不变量

对任意已接受的两个事件 `a`、`b`：

```text
a.key == b.key 且 a 先于 b 被采集器接受
=> a.eventRevision < b.eventRevision
```

revision 的唯一作用域是 `(projectId, executionId)`：

- 不按 `executionKind`、`runId`、`roundId`、`nodeId` 或 `attemptId` 分序列。
- Round、Run、attempt 终态都不释放 task revision cursor。
- revision 允许因采集前队列丢弃而出现缺口，但绝不重复或回退。
- `occurredAt` 表示事实发生时间；`eventRevision` 表示采集器接受顺序。乱序发生时间不能倒置 revision。

### 6.2 单一后台采集器

复用批量上报方案中的 SQLite outbox 与现有 SQLite 依赖，由一个后台 collector 串行处理 `PendingMetricsFact`：

```text
Runtime producer
  -> bounded try_send(PendingMetricsFact)
  -> metrics collector
  -> SQLite transaction:
       1. load/update TaskMetricsState
       2. allocate next eventRevision
       3. apply typed counter/code-change transition
       4. validate and build immutable wire event
       5. insert metrics_outbox
  -> batch uploader claim/send/ack
```

同一 SQLite 事务同时提交 state cursor 和 outbox event，避免：

- revision 已递增但事件未落盘；
- 事件已落盘但 counters 仍是旧快照；
- 应用重启后重新使用已经上报过的 revision。

producer 热路径继续只执行有界 `try_send`。数据库、JSON 序列化和 HTTP 均不在 Runtime 事件线程执行。若前置内存队列已满，该事实按现有指标降级策略丢弃且不分配 revision；已经被 collector 接受的事实必须持久化或返回结构化内部失败，不得静默部分提交。

### 6.3 TaskMetricsState

```rust
struct TaskMetricsState {
    last_revision: u64,
    task_counters: TaskCounters,
    active_attempts: HashMap<AttemptMetricsKey, AttemptCounters>,
    code_changes: TaskCodeChangeAccumulator,
}
```

- `TaskMetricsState` 以 `(projectId, executionId)` 唯一持久化。
- attempt terminal 生成 counters 快照后，从 `active_attempts` 移除，避免无界增长。
- task 交付终态不删除 state，因为同一 task 后续可能进入 `run-002` 或新 Round。
- 只在 Task 被明确删除/归档且 outbox 无未确认事件后，按统一保留策略清理 state。

## 7. 中间态与 executionKind

合法矩阵：

| sessionMode | eventType | executionKind | 必填上下文 |
|---|---|---|---|
| Direct | paused/resumed/intervention | `turn` | `attemptId/attemptIndex` |
| Workflow | paused/resumed/intervention | `node-attempt` | `nodeId/attemptId/attemptIndex/roundIndex/roleName` |
| AUTO | paused/resumed/intervention | `unit-attempt` | `nodeId/attemptId/attemptIndex/roundIndex/roleName/unitKind` |

Workflow/AUTO 不再产生 `executionKind=run/outer-run` 的 paused、resumed 或 intervention 事件。事件必须绑定造成暂停、接受恢复或发起干预的真实 attempt：

- 正常运行时使用 canonical current node/unit。
- 进程恢复时使用 durable current attempt locator，不根据最后一条 timeline 或名称反查。
- 找不到合法 active attempt 时，不构造伪造节点事件；记录稳定内部错误码 `METRICS_ACTIVE_ATTEMPT_MISSING`，不影响业务恢复。
- 同一 attempt 恢复时只发布 resumed，不重复 started。

## 8. counters 分层与精确定义

### 8.1 两级快照

`counters` 字段名保持不变，但由 `executionKind + eventType` 决定作用域：

| 事件 | counters 作用域 | 规则 |
|---|---|---|
| Workflow `node-attempt execution.completed` | 当前 attempt | 必填 |
| AUTO `unit-attempt execution.completed` | 当前 attempt | 必填 |
| Direct `turn execution.completed` | 整个 task | 必填 |
| Workflow `run execution.completed` | 整个 task | 必填 |
| AUTO `outer-run execution.completed` | 整个 task | 必填 |
| started/paused/resumed/intervention | 无 | 禁止携带 |

attempt counters 不能反向汇总成 task counters。每次合法领域转换由 collector 在同一事务中同时更新当前 attempt 和 task 累计值；task 终态直接读取 `task_counters` 快照。

节点终态示例：

```json
{
  "eventRevision": 27,
  "eventType": "execution.completed",
  "executionKind": "node-attempt",
  "executionId": "task-uuid",
  "runId": "run-002",
  "roundId": "round-001",
  "nodeId": "node-uuid",
  "attemptId": "attempt-uuid",
  "attemptIndex": 1,
  "counters": {
    "pauseCount": 1,
    "resumeCount": 1,
    "permissionRequestCount": 0,
    "elicitationCount": 1,
    "manualContinueCount": 0,
    "followUpCount": 0
  }
}
```

`followUpCount` 在 node/unit attempt 中必须为 `0`，因为 follow-up 是 task 级新目标，不属于某个已结束 attempt。保留同一 DTO 可避免新增两套几乎相同的 wire schema；客户端与服务端用作用域矩阵校验非法非零值。

### 8.2 manualContinueCount 与 followUpCount

| 字段 | 唯一触发条件 | 明确不计入 |
|---|---|---|
| `manualContinueCount` | 当前 runtime 已 paused，用户显式执行 continue/manual check/分支决策，使**同一 attempt** 从 paused 转为 running | permission/elicitation 的答复、自动恢复、task 终态后的新输入 |
| `followUpCount` | 同一 `executionId` 已完成一次交付后，用户提交新的目标并被接受，开始新 Round/Run/Direct follow-up | 首轮输入、paused 状态下的继续、permission/elicitation 答复、scheduler 自动触发 |

使用受控领域动作分类，而不是从 UI 按钮、prompt 文本或 `PauseReason` 推断：

```rust
enum UserExecutionAction {
    ManualContinue,
    PermissionResponse,
    ElicitationResponse,
    FollowUp,
}
```

映射规则：

- `ManualContinue`：`resumeCount += 1`，`manualContinueCount += 1`。
- `PermissionResponse`：若形成真实 paused -> running，仅 `resumeCount += 1`。
- `ElicitationResponse`：若形成真实 paused -> running，仅 `resumeCount += 1`。
- `FollowUp`：仅 task `followUpCount += 1`，不增加 resume/manualContinue。
- 重复 command、重复 request ID 或未产生状态转换的点击不计数。

## 9. task 终态代码行数

### 9.1 Wire 结构

仅 `turn/run/outer-run execution.completed` 携带：

```json
{
  "codeChanges": {
    "addedLines": 128,
    "deletedLines": 37,
    "changedFiles": 9,
    "completeness": "complete",
    "limitationCodes": []
  }
}
```

定义：

- `addedLines/deletedLines`：从 Task 创建到当前交付终态，Gold Band 已捕获文本 diff 的累计新增/删除行数。
- `changedFiles`：至少发生一次已捕获文本变更的去重 logical path 数。
- 同一路径在多个 turn 中多次编辑时，行数按实际 edit churn 累加；它表达本 task 的代码修改工作量，不声称是最终 workspace 的净 diff。
- 服务端需要总变更行数时计算 `addedLines + deletedLines`，wire 不重复传派生字段。
- 二进制文件不计行数；存在捕获上限、非线性 mutation、缺失 diff 或无法解析文件时使用 `completeness=partial` 并返回稳定 `limitationCodes`。
- 完全没有文件变更且采集完整时三个数均为 `0`；无法建立任何可信统计时使用 `completeness=unavailable`，数值字段为 `null`，禁止猜测为 0。

### 9.2 数据来源

复用 `TurnFileStore`、`TurnFileChangeSet`、`FileComparisonStats` 和现有 `similar::TextDiff`：

- 每个 turn finalize 时，把已经计算出的 `addedLines/deletedLines` 增量提交给 task metrics collector。
- 该增量附着到对应 attempt/turn terminal 的 `PendingMetricsFact` 内部 payload，与 terminal event 在同一事务中累计；不创建无 revision 的第二条旁路消息。
- collector 只累计数值、去重 logical path、合并 limitation code，不保存或上传源码内容。
- task terminal 读取 O(1) 数值快照，不启动 `git.exe`，不扫描仓库，不读取全部源码。
- 外部命令未产生标准 ACP diff 时明确标记 partial；不使用当前 Git dirty 状态冒充 task 归因。

该口径优先保证“属于这个 task”而不是伪造一个看似完整的仓库净差异。若以后需要最终净 diff，应单独设计 task baseline 与 worktree 隔离，不能修改本字段语义。

## 10. 完整 task 终态示例

```json
{
  "eventId": "event-uuid",
  "eventRevision": 28,
```

## 11. 服务端合同与投影

### 11.1 校验

服务端逐事件执行：

1. `runId/roundId` 必填并通过共享格式合同。
2. `(projectId, executionId, eventRevision)` 唯一；同 revision 不同 eventId 返回 `METRICS_REVISION_CONFLICT`。
3. `executionKind`、eventType、node/unit 上下文符合第 7 节矩阵。
4. counters 只出现在第 8 节规定的 terminal 事件，且全部为非负整数。
5. node/unit 的 `followUpCount` 必须为 0。
6. `codeChanges` 只出现在 task 交付终态；`complete` 时数值必填，`unavailable` 时数值必须为 null。
7. scheduled 来源联合类型字段必须成组出现；两个来源都是 scheduled 类型时 `scheduledTaskId` 必须相等；普通用户来源不得夹带 scheduled 字段。
8. `sessionPolicy=continuous` 只允许 Direct；Workflow/AUTO 的 scheduled occurrence 必须为 `new`。
9. batch 中单条非法事件返回结构化逐项错误，不影响其他合法事件落库。

### 11.2 投影键

raw event 保留完整原文；物化层分开保存：

- task stream cursor：`(project_id, execution_id) -> last_event_revision`。
- run delivery：`(project_id, execution_id, run_id)`。
- attempt：`(project_id, execution_id, run_id, round_id, attempt_id)`。
- task aggregate：`(project_id, execution_id)`，由最高合法 revision 的 task terminal 快照覆盖 counters/codeChanges。

服务端不得再把 `(executionId, executionKind)` 当成唯一业务主体，也不得因为 `run-001` 已 terminal 就拒绝同一 task 的 `run-002`。attempt 终态只更新 attempt fact；task terminal 只覆盖 task aggregate，不将 node counters 二次累加。

## 12. 实施顺序

1. 同步正式产品设计、客户端/服务端 OpenAPI 或 JSON Schema、fixture 和结构化错误码。
2. 定义 `PendingMetricsFact/MetricsSubject/UserExecutionAction/TaskMetricsState` 强类型数据结构和校验。
3. 把 revision 分配、两级 counters 更新和 outbox insert 收敛到单一 collector 事务。
4. 将 task state 持久化键从 run/attempt 路径迁移为 `(projectId, executionId)`；删除 run terminal 释放 revision cursor 的旧路径。
5. 修改 Direct、Workflow、AUTO producer，逐事件固化 Run/Round 与 scheduled 来源。
6. 把 Workflow/AUTO paused/resumed/intervention 映射为 node/unit attempt。
7. 在 node/unit terminal 注入 attempt counters，在 task terminal 注入 task counters。
8. 将 turn file diff 统计接入 task code change accumulator，并在 task terminal 输出 `codeChanges`。
9. 输出服务端 raw schema、唯一约束、attempt/run/task 投影与批次逐项校验的可执行实施合同；本仓库不实现服务端代码。
10. 使用接口级测试和真实 batch HTTP 验收后，删除旧 revision scope、旧 run 中间态和旧 counters 消费路径。

当前处于开发阶段，合同采用破坏式更新，不双写旧字段、不为缺失 `runId/roundId` 增加 fallback，也不保留两套 revision allocator。

## 13. 接口级回归测试

### 13.1 身份与 revision

- 同一 task：`run-001/round-001 -> round-002 -> run-002/round-001` 的 revision 全程严格递增。
- Workflow run、node attempt、AUTO outer/unit、intervention 并发到达 collector 时 revision 唯一且按接受顺序递增。
- 应用在 outbox 已落盘后崩溃并恢复，新事件 revision 大于恢复前所有已接受事件。
- 两个 workspace 使用相同本地 `run-001/round-001` 不串 state、outbox 或服务端投影。
- 重复上传同 eventId 幂等；同 task/revision 的不同 eventId 返回 `METRICS_REVISION_CONFLICT`。

### 13.2 来源与事件主体

- 普通 Task、定时新 Task、continuous occurrence、立即执行、定时 Task 用户 follow-up 的来源字段分别正确。
- scheduled task ID 不一致、Workflow/AUTO 使用 continuous、user 来源夹带 occurrence 字段时逐项返回稳定合同错误。
- Workflow paused/resumed/intervention 均为 `node-attempt`；AUTO 均为 `unit-attempt`。
- 中间态缺少 active attempt 时不产生伪造指标，业务流程仍正常推进。
- 进程恢复只产生 resumed，不重复 started，且沿用原 attempt locator 和 scheduled occurrence。

### 13.3 counters

- 单节点的 permission、elicitation、pause/resume/manual continue 在 node terminal 快照中准确。
- 多节点、多 Round、多 Run 后 task terminal counters 是 task 累计值，且不因重试或事件重发重复增加。
- permission/elicitation 答复可增加 resumeCount，但不增加 manualContinueCount。
- task 完成后的用户新目标只增加 followUpCount，不增加 resumeCount/manualContinueCount。
- 重复 continue command、重复 request ID 和无状态转换操作不计数。
- node/unit terminal 的 followUpCount 非零时客户端校验失败；服务端收到时逐项拒绝。

### 13.4 代码行数

- 单文件新增、删除、修改得到正确 added/deleted 行数。
- 同一路径跨多个 turn 的 edit churn 累加，changedFiles 仍只计 1。
- 二进制、capture limit、non-linear mutation 产生 partial 和稳定 limitation code。
- 无文件变更得到 complete + 0/0/0；无可信采集得到 unavailable + null。
- task terminal 不执行 Git 命令或全仓扫描；上报内容不包含路径、diff 或源码。

### 13.5 批量与失败隔离

- 单批 100 条混合多个 workspace/task/run/round 时，各事件定位、来源、revision 和 counters 不串联。
- collector 事务失败不留下“cursor 已前进但 outbox 无事件”或相反的半状态。
- batch 部分拒绝只处理对应 outbox item，合法 item 正常 ack。
- producer 队列满、SQLite 慢和网络重试均不阻塞 Runtime 事件线程。

## 14. 方案自评审

### 14.1 开源组件与行业实践

- revision/state/outbox 使用项目已有 SQLite 能力和 transactional outbox 模式，不自研数据库或消息队列。
- 代码行统计复用现有 `TurnFileStore` 与 `similar::TextDiff`，不引入 `cloc/tokei` 或额外 Git 子进程。
- 接口使用现有 OpenAPI/JSON Schema 与客户端、服务端 contract test 固化，不引入第二套协议框架。
- OpenTelemetry/CloudEvents 的 trace context 和 envelope 思路可参考，但不能替代本项目 task/run/attempt 的业务身份，不为本需求迁移事件总线。

### 14.2 过度设计评审

新增 `TaskMetricsState` 和单 collector 事务是表达以下现有模型无法保证的不变量所必需：

1. revision 跨 Run/Round 严格递增且崩溃后不复用；
2. 同一动作原子更新 task 与 attempt counters；
3. task terminal 输出累计统计而不扫描全部历史事件。

除此之外不新增 aggregate、状态机、缓存、队列或外部依赖。attempt state 终态即释放，task state 随 task/outbox 保留策略清理；不为假设性报表预建字段或索引。

### 14.3 性能影响评审

- producer 热路径仍为 O(1) 的有界 `try_send`，无文件 I/O、网络、Git 命令或长锁。
- collector 单事件执行一次短 SQLite 事务；revision、counters 和 outbox 同写，避免多次往返。使用现有 batch 上限 100 和有界队列形成背压。
- task state 仅保存固定 counters、revision、active attempts 和代码统计；attempt terminal 后移除，无界增长风险受控。
- `changedFiles` 去重集合的上限沿用 turn file capture entry limit；不扫描 workspace，不产生 N+1。
- 服务端只增加真实查询所需的 task stream、run 和 attempt 组合索引，不为任意字段组合建索引。

验收目标：现有 Runtime lifecycle 延迟基线不得回退；collector 在单批 100 条和连续事件压力下不阻塞 producer，SQLite 锁不覆盖 HTTP，outbox/active attempt/state 大小均有明确上限。实现前记录现有 collector 吞吐与队列丢弃基线；若生产构建压力测试显示风险，再针对事务批量化优化，不先增加缓存或并发 writer。

## 16. 实施与验收结果

### 16.1 客户端实现

- `PendingMetricsFact` 只表达领域事实；producer 不再分配 eventId、revision 或 counters。
- SQLite collector 以 `(projectId, executionId)` 原子更新 task revision、task/attempt counters、代码变更累计与 outbox。
- uploader 通过 collector actor claim/apply/retry；HTTP await 不持 SQLite transaction 或锁，单批最多 100 条且不混月份；401/403 释放 lease 后暂停 uploader，普通网络/429/5xx 有界退避。
- Direct、Workflow、AUTO 和 scheduler 来源均已迁移到 typed subject/origin/trigger；中间态缺少 canonical active attempt 时拒绝伪造指标。
- task 代码变更只读取已持久化的 `TurnFileChangeSet`，Direct 按 terminal `turnId` 过滤，Workflow/AUTO 只读取 terminal attempt；不调用 Git、不扫描 workspace、不上传路径或源码。
- 旧 in-memory reporter、producer-side revision/counters、直接 POST retry、payload 日志与旧 lifecycle fact 已删除。

### 16.2 验证结果

- core metrics 相关测试：12 passed；TurnFileStore 按 turn 结构化读取和 Direct terminal 代码变更过滤另有专项回归。
- desktop metrics 相关测试：42 passed，包含 collector 6 项、uploader 3 项以及 Workflow/AUTO intervention 主体测试。
- 真实本地 HTTP batch fixture 验证 `accepted=1, duplicate=1, rejected=1`，客户端要求响应精确覆盖全部 claimed eventId。
- `cargo check -p gold-band-desktop` 与 `cargo fmt --all -- --check` 通过。
- desktop 全量串行测试：495 passed、3 failed；失败位于 permission signal、legacy task path、agent branch semantic page，均不经过 metrics 代码路径。
- core 全量测试曾因新增测试夹具缺少 completed usage 记录导致首个失败并 poison 共享环境锁；夹具修复后该测试及 metrics 相关测试全部通过。并行全量中仍有仓库既有 Git/MCP 长时集成测试不稳定，不作为本需求通过项。

### 16.3 完成复审

过度设计：只新增 task collector state、attempt state 与 outbox 三类为原子 revision/counters 和可靠上传所必需的数据；未增加第二套 canonical lifecycle、消息队列、并发 writer 或兼容层。服务端只输出合同，没有越界实现。

性能：producer 热路径保持 O(1) 有界 `try_send`；collector 单事件一次短事务；HTTP、JSON 网络处理不位于 DB 锁内；active attempt terminal 后删除；batch=100；代码变更不做 Git/全仓扫描。相关功能测试完成，当前无热点证据，不做猜测性缓存或并行化；release 基线由发布阶段按产品文档补齐。
