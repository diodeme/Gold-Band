# 指标上报服务端处理实施计划

## 1. 目标

实现 `metrics-server-processing.md`：完整 batch API、按 report_date 月分区的事件事实表、attempt 基础表、logical execution 投影表和 delivery 统计表，以及由服务端计算的七类指标固定统计口径。客户端只提供事实与终态快照，不提供最终报表指标。

## 2. 实施阶段

### Phase 1：API DTO 与校验

- 实现 `events[1..100]`、API Key、UUID 32/36 位输入规范化、五种 executionKind 完整枚举和 ID 组合矩阵。
- 增加 attemptIndex：Direct 的 executionId/attemptId 等于 task UUID 且 attemptIndex 固定为 1；Workflow/AUTO 在 executionId 内从 1 严格递增，校验 attemptId 与 attemptIndex 的稳定映射。
- 客户端前置已完成：attemptIndex 已进入 lifecycle fact 与 HTTP DTO，Direct/Workflow/AUTO attempt 事件全链路上报，run/outer-run 不携带。
- 校验 outcome/terminalReason 组合、成功/失败/取消定义、Usage 按字段合计、firstPass 公式、六个 Count、reportedAt 24 小时偏差。`failedAttemptId` 本期仅做 UUID 格式校验并留存在 raw event，不做关联处理。
- 第一条 reportedAt 选择分区，批内跨月整批拒绝。
- 固化结构化错误码和成功响应的七个业务 Count。

### Phase 2：四表月分区

- 创建 `ml_metric_event`、`ml_metric_attempt`、`ml_metric_logical_execution`、`ml_metric_delivery_stat`。
- 四表只保留 `report_date` 一个 DATE 字段并直接月分区；workspace 长度本期不修改。
- attempt 表以 UUID attempt_id 为 Usage 留存主粒度。Direct 的 attempt_id 等于 execution_id；Workflow/AUTO 的 execution_id 标识逻辑 node/unit，重试保持 execution_id 并生成新 attempt_id。delivery 表集中保存 `*_count` 且不保存 Usage。
- attempt 表增加 `(report_date, execution_id, attempt_index)` 唯一键及 execution/parent/node/unit/role 查询索引；logical execution 表增加 parent、node、unit、role 统计索引。
- 创建当前月、未来两月与 pmax；暂不删除历史分区。

### Phase 3：事件事实与投影

- 事实表在目标月及前一个月范围内实现 eventId 幂等；服务端正式写入 `revision_subject_kind/id`，attempt 事件取规范化 attemptId，run/outer-run 取规范化 executionId，客户端不能覆盖计算结果。同 eventId 或同 revision 主体/revision 命中即按 duplicate success，本期不比较 payload 差异。
- 所有事件依次查目标月与前一月。
- 按事件更新矩阵投影 attempt、logical execution 与 delivery stat；logical 最终结果始终取最大 attemptIndex 的 terminal attempt。
- terminal 快照覆盖 outcome/reason、usage/model 或 counters，不做增量累加。
- revision 必须大于等于 1，允许从大于 1 开始、允许缺口、乱序和 terminal-first；建立 terminal 吸收态，任何非 terminal 事件均不得回退终态。
- 增加不可变字段矩阵和统一 `running/paused/terminal` state 枚举；低 revision started 仅补充白名单内的空开始快照字段。
- terminal counters 直接作为权威快照覆盖写入，本期不做 Count mismatch 重算、校验或质量标记。
- acceptance 增加 `(report_date, parent_execution_id, acceptance_attempt)` 唯一约束。

### Phase 4：指标查询

- 分别实现执行覆盖、终局、产物质量、效率成本、自动化、可靠性、模型质量查询，所有 numerator/denominator/rate 均由服务端计算。
- attempt 是 usage/model 原始事实来源；logical execution 是 node/unit 最终结果、重试率和重试恢复率来源；delivery stat 是交付和 Count 来源。
- JSON_TABLE 展开 modelUsages，区分参与模型与最终模型。
- Usage 聚合输出 known/unknown attempt count，全部未知时 SUM 为 NULL；success/failure/cancelled/killed 分列并同时提供 attempt/logical/delivery 三层口径。
- 输出 start missing、counter mismatch、attempt index gap、failed attempt missing、投影冲突等采集质量指标。
- 所有 SQL 带 report_date 范围并验证 partition pruning。

## 3. 单元与接口测试

- batch 大小、鉴权、UUID 双格式及规范化、枚举、ID 组合、字段适用、outcome/reason、跨月和时钟偏差。
- 四表 DDL 只有一个 DATE；目标/前月定位和分区缺失。
- 目标月及前一个月内 event 重放、revision 缺口/乱序、terminal-first、终态不可逆、迟到低 revision started 白名单更新。
- attempt retry 不覆盖、attemptIndex 唯一/缺口、logical final attempt、nodeId/roundIndex/roleName 投影。
- firstPass 一致性、acceptance 序号唯一性、Usage null 与逐字段 sum 规则；`failedAttemptId` 不进入 delivery 投影。
- Count 只写 delivery stat，usage/model 只写 attempt。
- 固定数据集验证文档统计维度表中的每个公式。

## 4. 完成定义

- API 文档、服务端 DTO、DDL、Repository 和统计 SQL 一致。
- 四表迁移与未来月份分区任务上线。
- 在线更新最多访问目标月和前一月。
- 所有接口、投影和统计测试通过。
- 客户端接入指南删除旧 `metrics[]` 节点 upsert 协议。

## 5. 已确定边界与后续待办

- 幂等范围限定为目标月及前一个自然月，不承诺跨全部历史分区全局幂等。
- 不处理任务长期暂停后跨越两个以上自然月的定位问题。
- 不处理相同 eventId 携带不同 payload；移除 `METRICS_REVISION_CONFLICT`。
- API 时间统一解析为 UTC，数据库 `DATETIME(3)` 按 UTC 保存，只有 `report_date` 按 Asia/Shanghai 计算。
- `failedAttemptId` 的关联、乱序回填、失败归因和统计延期；本期不建立 delivery 投影列。
- Direct 同时写 attempt、logical execution、delivery stat 的简化方案待定；当前不得跨表重复汇总。
- 分区维护 DDL、UUID 紧凑存储、并发锁顺序与死锁重试、raw payload 规范、数据保留与隐私治理、统计查询 API 契约暂不纳入本期，作为后续优化待办。

## 6. 2026-08-03 设计文档实施加固

评估发现 `metrics-server-processing.md` §6 数据写入与更新的插入/更新机制对模型直接实施不够明确，主要问题是投影算法散落在 §6.1—§6.7 六个独立规则块，缺少端到端 trace 示例。已补充以下三部分：

- §6.8 logical execution 重算算法：给出 attempt INSERT/UPDATE 后按 executionId 重算投影的完整步骤，覆盖 attempt_count、terminal_attempt_count、latest/final_attempt、state 和 attempt_index_gap 的计算规则。
- §6.9 端到端 trace 示例：用 Direct turn 成功、Workflow node 重试、AUTO acceptance 首次拒绝后修复通过三个固定数据集，展示事件序列到 event/attempt/logical/delivery 四张表快照的逐步映射。
- §6.10 单事件投影决策流程：将 §6.2—§6.7 的幂等、不可变字段、state 吸收态、terminal 覆盖和 missing-start 合并为 attempt 和 delivery 两套伪代码决策树，显式标注 revision 比较、INSERT vs UPDATE、terminal 吸收态例外和 Direct turn 双写路径。
- §6.1 末尾增加交叉引用指针。
