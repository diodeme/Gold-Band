# 会话优化

## 0. 当前实现状态

当前 ACP 会话链路已经能工作，并已从轮询刷新切到事件级 push；后续重点是继续压实 timeline / snapshot 作为会话主路径，降低历史读取和检索成本。

当前 Gold Band 现状：

- 会话主数据文件为：`acp.session.json`、`acp.events.jsonl`、`acp.raw.jsonl`、`acp.diagnostics.jsonl`。
- `acp.raw.jsonl` 记录完整 ACP inbound / outbound raw frame，见 `src/acp/events.rs:48-52`、`src/acp/client.rs:303`、`src/acp/client.rs:931`。
- `acp.events.jsonl` 当前仍以逐帧归一化 event 为主，`normalize_session_update` 会把整份 `update.clone()` 塞进 `event.raw`，见 `src/acp/events.rs:165-199`。
- 会话详情读取时，后端会再次扫描 `acp.events.jsonl`，把连续 text / thought delta merge 成窗口，再计算 usage、permission 和 session elapsed，见 `src-tauri/src/view_models.rs:3160-3329`、`src-tauri/src/view_models.rs:3595-3616`。
- 前端打开 ACP 会话后常驻订阅 Tauri `gold-band://acp-session-updated`；活跃会话每个后端聚合 timeline item 以单事件 payload 推送到当前窗口，完整 session 快照只用于首次打开、历史查询和命令完成后的最终同步，不再用轮询或每帧重建完整 session 批量刷新。父级 conversation run 订阅通过统一 update plan 分类事件：当前已选中 session 的普通增量事件只进入 ACPChatDialog 局部合并；已存在于 session tree 的后台 session 普通 live event 不触发完整 run refresh；后台非终态 session snapshot 只做轻量运行态 patch；新 session 缺锚点、terminal snapshot、权限/暂停/等待输入等交互态仍必须刷新 run VM，让 activeSessions 与 lifecycle 收敛。前端 text/thought live 合并必须以后端聚合 timeline item 为事实，保证同一 stream 不被旧短帧、空帧或乱序 session hydrate 覆盖；interaction quiet window 只延迟普通 trailing stream flush，边界事件和 `sync` flush 必须先提交 pending text/thought，再进入后续 tool、permission、lifecycle 或 session 状态。
- 会话式运行页在 run 已 running 但首个 attempt 尚未出现在 session tree 前展示 `Agent 调起中`；attempt 已创建但尚无可见 timeline item 时展示 `处理中...`，首个 thought 到达后切换为 `思考中...`。ACPChatDialog 必须消费当前选中 attempt 的 runtime status：选中 attempt 运行中时锁定输入、显示底部运行状态和停止按钮；选中 attempt 已结束时恢复正常追问输入且不显示停止按钮。运行状态标签使用轻量 CSS 圆环旋转，避免 SVG spinner 在高频状态刷新时卡顿。
- run 启动路径已调整为在 `prepare_run` 阶段同步写入首个 `node.json`，保证首个 `round/node/attempt` 在 agent/provider 启动前就能作为稳定 session key 锚点被 conversation VM 读取；无显式 `selectedSessionKey` 时，后端默认选择 current attempt，其次选择 active/running attempt，再回退到最近历史 session。前端仍保留 `activeSessions` 临时兜底，避免极短竞态下首屏缺少运行态、停止按钮和输入锁定。
- 前端完整 `ConversationRunVm` 快照已收口到 `mergeConversationRunSnapshot`：创建、初始加载、live refresh、workflow save、stop refresh、continue refresh、rerun 都经同一入口合并；局部标题编辑、删除置空、手动 session switch 只做局部 patch。合并规则禁止同 run 内的 `unknown` ACP 快照覆盖当前 running/cancelling selected leaf，并保留当前 selected key。`selectedSessionKey` 与 `selectedSession / artifacts / attachments` 必须作为原子一致的 session payload 处理：当 live refresh 或手动切换返回的 payload 不属于最终选中的 key 时，必须丢弃旧 payload，等待当前 key 的切换结果或下一次按 key 拉取，防止不同 attempt 的 timeline 被合并到同一个 ACPChatDialog 窗口。手动 session switch 已先更新 selected key 再异步回填目标 session，因此 ACPChatDialog 在首次补拉目标 session 完成前必须显示 loading shell；补拉完成后仍没有 session/live shell 时才展示 missing ACP session 错误，避免把正常切换竞态误报成 ACP 会话失败。
- ACP 会话壳层新增 `interrupted` 终态：当后端 lifecycle 已为 `paused + process-interrupted`，且当前 attempt 没有 `sessionId`、可展示 metadata 或 timeline item 时，判定为 ACP 初始化从未成功。该状态优先于 initial loading，立即展示无图标单行文案“会话发起中断，请重跑该任务”，停止 readiness 补拉并隐藏 composer；已经建立过 ACP session 的 `process-interrupted` 仍沿用既有可继续会话语义。
- 新 UI 的暂停态分为两类：`waiting-for-user-input` 继续显示 continue 按钮；`process-interrupted`（用户 stop 后）在 ACP session 非 active 后恢复输入框，但发送不会走普通 ACP follow-up，而是仍走原来的 runtime continue 链路，只把默认“继续”替换成用户输入文本。若 run 已暂停但 ACP session 仍 active/cancelling，则 composer 必须继续显示 stopping 并锁定输入。当前状态解释已收口为后端 leaf `lifecycle` 与前端纯 `deriveAcpRuntimeComposerState`：session tree、activeSessions、placeholder、输入禁用、停止按钮、submit target 都从同一套派生结果读取，不再在页面和组件里重复拼接 `runtimeStatus/sessionStatus/pauseReason`。
- Round 详情/会话式运行页首次进入活跃 attempt 时，system prompt 入口不能依赖 conversation attempts 聚合快照已经补齐；只要当前 attempt 详情或首次 session 快照已拿到 `systemPromptAppend`，按钮就应立即可点击，后续再与 conversation 聚合结果合流，避免首节点运行中短暂置灰。
- 历史分页请求已切到 `beforeCursor / afterCursor` 主路径，同时兼容旧 `beforeSeq / afterSeq`；前端聊天列表使用原生滚动容器触发顶部/底部分页，prepend 旧页前捕获当前可见 timeline item 的 DOM 锚点，合并后按同一锚点的新旧 top 差值保位。
- 会话式运行页的 auto-follow reset 需要只在 `runId` 切换时触发；如果 effect 依赖父组件每轮重建的 `onAutoFollowChange` 回调，会在 live refresh 后误重置为 follow=true，导致用户手动查看已完成 session 时被运行中的 session 抢占。
- ACP 会话运行态已补齐三类回归约束：测试/验收节点的 workflow outcome failure 不再触发 runtime-error composer 面板；runtime attempt 已 completed 时会压过 stale ACP `running`、stale local awaiting response 和 stale `provider.pid`，避免“回复生成中”残留；若最后节点的 ACP session 已自然 `completed` 但父级 run snapshot 仍短暂保留 stale `runtime.active=true`，前端 composer 会以选中 ACP session 终态压制该 active 态并主动刷新父级 run；session 选择所有权改为 `auto/manual` 显式模式，手动查看历史 attempt 后 live refresh 只能后台更新，不能抢回最新 running attempt；只有当前选中 session 仍是 active session 且消息列表 pin 在底部时，滚回底部才恢复 session auto-follow。
- Gold Band 主题滚动条已从 ACP 会话主滚动区扩展为全局滚动规范：原生 `overflow-auto / overflow-y-auto` 容器默认使用 `--gold-scrollbar-*` token，prompt-kit 聊天容器保留 `gold-themed-scrollbar` 显式类，shadcn/Radix `ScrollArea` 的 track/thumb 也改为同一组 token，并统一为 10px 交互轨道、约 4px 可见 thumb，避免运行模式管理、设置页、弹层和 ACP 会话出现多套滚动条颜色或胖瘦不一致。
- 会话输入卡顿排查发现旧 Workbench 的后台刷新仍会在 Conversation 模式注册 10 秒/30 秒 interval，周期性触发旧任务/工作流/round detail 数据刷新并与输入主线程竞争；当前已约束该后台刷新只在 Workbench 模式启用，切回 Conversation 时清理 interval，Conversation 模式的数据更新继续由会话侧栏加载与 ACP/live run 事件驱动。
- 会话主页 composer 草稿状态已从 App 顶层移入局部 `ConversationComposerDraftBoundary`，App 只通过 `reset` handle 清理草稿；输入按键只更新 composer context 消费者，避免每个字符驱动 App、Shell、侧栏和运行页参与 render。
- session token / cost 既在 runtime 内存里跟踪，也在读取 `acp.events.jsonl` 时重算一遍，见 `src/acp/client.rs:859-880`、`src-tauri/src/view_models.rs:3215-3231`。
- session 净处理耗时依赖 `AcpSessionElapsedState` 在读 timeline/events 时重建，包含 permission wait 扣减逻辑。会话累计只统计每个 Gold Band prompt turn 内的处理时间，多次 continue/resume 之间的空闲墙钟间隔不计入；`available_commands_update`、`current_mode_update`、`session_info_update` 等元数据事件不推进本轮最后处理时间；前端 event-only live shell 也使用同一口径，避免在完整 session 尚未 hydrate 时退回 `createdAt -> updatedAt` 跨度。

当前方案的主要问题：

1. `acp.events.jsonl` 与 `acp.raw.jsonl` 重复偏重，`events` 没有真正成为“UI 已加工时间线”。
2. 活跃会话已改为事件级 push，但 session 状态、usage 和检索索引仍需要继续压实权威来源。
3. 读取详情、分页、统计仍有部分逻辑依赖重新扫描和 merge，history 链路仍需要继续从 legacy event 迁到 timeline / snapshot 主路径。
4. ACP stop 的运行态与 provider 退出时机必须解耦：停止请求发出后 UI 先进入 `stopping / cancelling` 中间态，provider 再走优雅退出，超时后 kill fallback；只有当前 attempt 已有 ACP session 时，前端才需要等待 ACP session 非 active 终态后再视为停止完成并刷新 run/session。对于尚未建立 ACP session 的启动阶段停止，应以 runtime 不再 active 作为完成信号，并进入无 composer 的“会话发起中断，请重跑该任务”终态，不再视为可继续会话。会话树 leaf 在 graceful stop 期间必须优先消费 ACP stopping 事实：`cancel-request` 仍存在且 `provider.pid` 未消失、或 session 为 `cancelling/cancel_requested` 时，即使 snapshot 已出现 `cancelled` 也仍展示停止中，避免过早显示“已停止”；一旦 provider 真正退出且 runtime 已落盘为 `paused + resumable`、pause reason 属于 `process-interrupted / waiting-for-user-input / error-blocked`，最终展示必须优先区分 ACP session 是否真正建立：已建立的 session 回归 runtime 的可继续暂停态，从未建立的 session 进入无图标中断终态，不能被 ACP `cancelled` 或空 `unknown` 快照覆盖。后续所有 stop/continue 状态变更必须补充 lifecycle 与前端 session shell 状态矩阵测试，禁止只在组件里局部追加 if。
5. token / elapsed 的权威来源仍需继续压实到 snapshot；elapsed 展示口径已明确为 prompt turn 净处理耗时，禁止用 ACP session 生命周期跨度作为会话累计。
6. 后续跨 session 搜索如果继续纯扫文件，复杂度和性能都会快速恶化。

## 1. 核心方向

本次会话优化的核心目标：

1. **活跃会话从 polling 改为 push。**
2. **会话时间线从逐帧 event 改为聚合后的 timeline item。**
3. **token / elapsed 从读时重算改为 runtime 聚合 + snapshot 持久化。**
4. **文件仍然是会话事实源，SQLite 只用于辅助检索。**
5. **旧会话可继续打开，通过 legacy reader / lazy migration 兼容。**

目标分层：

```text
ACP raw frame
  -> live session aggregator
  -> timeline final item
  -> push to UI
  -> rewrite timeline / update snapshot
  -> optional SQLite search index
```

这里必须明确三个边界：

- `raw`：协议排障事实源。
- `timeline`：UI 聚合时间线事实源。
- `SQLite`：辅助检索索引，不承担会话恢复和详情展示的唯一事实源。

## 2. 设计原则

### 2.1 会话详情优先服务 live UX

会话主路径必须优先服务：

- 文本流顺滑增长
- tool call 原地刷新
- permission 状态即时切换
- 历史向上翻页不抖动
- 会话恢复后可继续增长

因此主详情链路不能继续依赖“轮询文件 + 再 merge”。

### 2.2 timeline 必须是 UI 已加工结果

`acp.timeline.jsonl` 不再保存 raw-ish event 镜像，而应保存：

- 一条用户消息
- 一条 assistant 文本块
- 一条 thought 块
- 一条 tool call
- 一条 completed plan 块
- 一条 permission 块
- 必要的 system / error / compaction 块

即：一个逻辑 UI item 在内存中可以被多次更新，但落盘后只保留当前最终态，不能退回成 ACP chunk 日志。

### 2.3 文件优先，数据库旁路

当前项目 runtime 已按 attempt 目录组织，会话与 task / run / round / node / attempt 绑定紧密；因此本期不引入“DB 作为会话主存储”。

本期约束：

- `raw / timeline / snapshot` 为主数据。
- SQLite 仅承担跨 session prompt / timeline 检索索引。
- 没有 SQLite 时，详情、恢复、排障都必须继续工作。

### 2.4 破坏式升级，但保留旧会话可读

开发阶段允许替换旧方案，但不能让已有会话不可打开。

因此策略为：

- 新会话走 V2。
- 旧会话走 legacy reader。
- 必要时按首次打开或后台任务做 lazy migration / backfill。

## 3. 目标文件结构

每个 ACP attempt 的目标文件结构：

```text
attempt/
  worker-ref.json
  acp.raw.jsonl
  acp.timeline.jsonl
  acp.snapshot.json
  acp.agents.jsonl
  acp.diagnostics.jsonl
  agents/
    agent-<stable-id>/
      timeline.jsonl
      snapshot.json
  provider.pid
```

说明：

- `worker-ref.json`：继续承载 session id、continue 信息、provider handoff 信息，是 session identity 的事实源。
- `acp.raw.jsonl`：完整 ACP inbound / outbound raw frame，只用于协议排障与极端恢复。
- `acp.timeline.jsonl`：根会话规范 timeline；Agent 工具、思考、TODO、权限和正式文字不重复写回根分支。
- `acp.snapshot.json`：当前会话聚合快照、metrics、游标与恢复锚点；用于取代现有 `acp.session.json`。
- `acp.agents.jsonl`：稳定 Agent execution 关系、状态、attention、统计和 latest cursor 物化索引。
- `agents/<stable-id>/timeline.jsonl`：单个 Agent 分支规范 timeline；目录名只使用 Gold Band 生成的稳定 ID。
- `agents/<stable-id>/snapshot.json`：分支状态、统计和分页恢复锚点。
- `acp.diagnostics.jsonl`：adapter / protocol diagnostics。

本期不再把 `acp.events.jsonl` 作为 V2 会话主路径。旧会话首次访问时执行一次性分区迁移，之后所有 runtime/query/interaction 路径只使用 branch timeline；旧文件原样保留为审计来源，不维持长期兼容双读或双写。

## 4. 目标架构

### 4.1 live session aggregator

后端新增 ACP 会话聚合器（以下简称 aggregator），负责：

1. 接收 ACP raw session updates。
2. 将 update 聚合进内存中的 session state。
3. 生成稳定的 timeline final item。
4. push 给前端。
5. 同步重写 `acp.timeline.jsonl`。
6. 同步更新 `acp.snapshot.json`。
7. 异步更新 SQLite 检索索引。

aggregator 是活跃会话的唯一 live 聚合层。前端不再直接解释 ACP 原始 frame，也不再依赖扫描 timeline 来获得最新 UI 状态。

### 4.2 前端改为 push 消费

活跃会话改为：

- 前端打开会话时订阅该 attempt 的 live channel，订阅生命周期跟随抽屉会话而不是发送按钮锁定状态，避免漏掉调起后的早期帧。
- 后端对每个聚合后的 timeline item 直接推送单事件 payload：新增 item、更新 item、权限请求和工具/文本流状态变化；手动 `send_acp_prompt` 与自动工作流 provider 执行路径都必须接入同一个 live event sink，不能只在命令完成后靠完整 session 快照刷新。
- 前端只 merge 对应 event；命令返回、节点完成或重新打开时再用完整 session 快照做最终同步，不在每个 ACP frame 上全量重拉；后端保留向前端推送完整 session snapshot 的基础通道，当前自动 workflow 只在 run completed 完成态落盘后推送 terminal session snapshot，不能只依赖手动命令返回路径，否则最后节点没有下一跳 event 时父级 run VM 无法收敛；如果 live event 早于完整 session 快照到达，前端用最小 live session shell 承载当前窗口事件，避免首个流式片段因 `session` 为空而不可见；抽屉关闭再打开同一 attempt 时先恢复本地事件窗口并建立订阅，再主动补拉最新 session window，避免等待快照期间空白或旧快照覆盖 live tail。

历史加载和首次打开仍然走 branch 命令查询，但活跃期间的新增变化由 push 主导。ACP Chat 主列表以语义块为最小视觉单元，使用浏览器原生滚动；assistant/user 消息、Activity 摘要和 Agent link 都保持稳定单行/单块身份。Activity 折叠时不构造 thought/tool 审计详情，展开后使用独立局部 cursor；Agent transcript 通过右侧只读 Tab 查询，不进入父消息流或父分页窗口。

### 4.3 history 读取改为 snapshot + timeline

打开会话详情时：

1. 先读 `acp.snapshot.json`，获得摘要、metrics、active 状态、游标。
2. 再从 `acp.timeline.jsonl` 读取最近一页已聚合 item。
3. 如果会话仍活跃，再建立 live subscription。

历史翻页时：

- 基于 timeline cursor / checkpoint 向前或向后读取。
- 不再对 `acp.raw.jsonl` 或逐帧 event 做窗口 merge。

## 5. `acp.timeline.jsonl` 设计

### 5.1 设计目标

`acp.timeline.jsonl` 必须满足：

- 支持一行一个最终逻辑 item。
- 支持同一逻辑 item 在内存中多次更新，但文件中只保留当前最终态。
- 支持会话恢复时快速重建最终时间线。
- 支持历史分页。
- 支持与 live item model 保持一致。

### 5.2 item 粒度

timeline item 粒度固定如下：

- `userMessage`
- `assistantMessage`
- `assistantThought`
- `toolCall`
- `plan`
- `permissionRequest`
- `systemNotice`
- `sessionError`
- `contextCompaction`

### 5.3 final item 模型

`acp.timeline.jsonl` 推荐每行一个最终 item，示意：

```json
{
  "item": {
    "id": "assistant-msg-12",
    "kind": "assistantMessage",
    "status": "streaming",
    "content": "我先检查当前工作流节点配置...",
    "startedSeq": 120,
    "endedSeq": 127,
    "startedAt": "1717612345Z",
    "endedAt": "1717612348Z",
    "meta": {
      "attemptId": "..."
    }
  }
}
```

约束：

- `id` 是稳定标识，同一逻辑消息 / thought / tool call 在整个 turn 中保持不变。
- `startedSeq` 表示逻辑 item 首次出现时关联的 source seq。
- `endedSeq` 表示该 item 当前最终覆盖到的最新 source seq。
- `startedAt / endedAt` 用于展示、耗时、恢复和分组。
- 旧 patch log 仅作为 legacy reader 兼容输入，新写入统一采用 final item 结构。

### 5.4 文本 / thought 聚合策略

文本与 thought 必须在写时聚合，而不是读取时 merge：

- 第一帧 `AgentMessageChunk` 到来时，新建一个 `assistantMessage` item。
- 后续属于同一稳定流的 chunk 到来时，更新该 item 的 content / endedSeq / endedAt。
- `AgentThoughtChunk` 同理写入 `assistantThought` item。
- `usageUpdate`、`modeUpdate`、`availableCommandsUpdate` 这类隐藏状态帧不能打断同一文本 / thought 流。
- 只有跨 turn、跨类型、跨 stable stream 时才新开 item。

### 5.5 tool call 聚合策略

tool call 必须按 `toolCallId` 原地聚合：

- `ToolCall` 创建时建立 `toolCall` item。
- `ToolCallUpdate` 到来时按 `toolCallId` 更新同一 item。
- terminal / diff / locations / raw input / raw output 等详情作为该 item 的字段或子结构更新。
- 不能把 `toolCall` 和 `toolCallUpdate` 分裂成多张卡。

### 5.6 permission / plan 聚合策略

- `permissionRequest`：pending -> selected / rejected 更新同一 item。
- `plan`：允许增量更新，但最终 UI 只投影为所属生命周期内的单个 Todo 列表；主会话和每个 Agent 分支分别维护最新快照，不保留 plan 消息卡消费路径。
- `systemNotice` / `sessionError`：一条逻辑提示一个 item，不复用 raw error 行。

### 5.7 前端 Plan/Todo 面板（2026-06-08）

- 主会话顶层 plan 事件不再渲染为消息流中的独立卡片，而是聚合为 composer 上方单一可折叠面板：
  - 默认收起，展开后展示条目列表与状态 Badge。
  - 收起状态显示完成数/总数及进行中任务摘要。
  - 每次 plan 更新实时刷新面板内容，不再在消息流中重复追加块。
- Agent 内部 plan 只写入对应 branch timeline，并在右侧只读 Agent 会话中复用同一 Todo 面板；plan 本身不渲染为大卡片。
- branch 路由在 ACP 归一化边界完成，并为 plan 固化通用 `planOwnership = branch | unscoped`。只有明确 provider relation 或内部 branch 定位可以形成 `branch` ownership；前端不得用 `parentToolUseId`、内容血缘、Agent 名称或事件邻近猜归属。
- 没有 Agent execution 的普通根会话继续展示最新 `unscoped` plan；存在 Agent execution 时根投影必须隐藏 `unscoped` session-wide plan。Agent 分支只消费明确归属本分支的 plan，历史 Agent timeline 中已有稳定非 root branch ID 的 plan 视为明确归属。
- 面板每次 render 读取当前 branch 投影的最新 entries，稳定 branch key 与展开状态不随快照更新变化。
- 顶层 plan 事件仍写入 timeline 文件（保留完整性），但在前端消息流中被过滤。

### 5.8 前端工具调用参数展示（2026-06-08）

- 工具调用卡片展开后以有序参数列表展示输入：
  - 参数来源优先级：rawInput > title 解析 > locations fallback。
  - 同标签参数保留多个不同值，不再用 `Object.fromEntries` 去重。
  - 无结构化参数但有原始 input payload 时回退展示 JSON。
  - 扩展 `toolDetails` 提取来源：增加 `toolCall.input`、`toolCall.fields` 回溯。

## 7. live push 设计

### 7.1 推送内容

后端向前端推送的消息类型：

- `timelinePatch`
- `sessionStatusPatch`
- `usagePatch`
- `metricsPatch`
- `permissionPatch`
- `sessionErrorPatch`

推荐统一成：

```json
{
  "attemptKey": "...",
  "patchType": "timelinePatch",
  "payload": { ... }
}
```

### 7.2 推送节流

文本流不能按 token 级频率直接刷前端。建议：

- 文本 / thought patch：50~150ms 内合并后推一次。
- tool call / permission / status / error：即时推送。
- snapshot 写盘频率可略低于 UI push，但不得太慢，避免崩溃丢失恢复锚点。

### 7.3 断线恢复

前端重新订阅后：

1. 先取最新 `snapshot + timeline window`。
2. 再接入 live push。
3. 如果服务端保存了最近 patch revision，可在必要时从某 revision 之后补拉。

## 8. 历史分页设计

### 8.1 不再使用 `beforeSeq / afterSeq`

V2 不再把 raw frame 数量或规范事件数量作为历史分页单位。cursor 由稳定语义块的 seq 范围编码，但对前端保持不透明。

原因：

- seq 是协议帧粒度，不是 UI item 粒度。
- 一个语义块可能覆盖多个规范事件和 raw seq；连续工具/思考无论展开与否都只算一个活动摘要。
- 活跃会话中 seq 会持续增长，作为 UI 分页 anchor 不稳定。

### 8.2 使用 timeline cursor

历史分页改为：

- `beforeCursor`
- `afterCursor`
- `pageSize`（单位为语义块）

cursor 推荐编码：

- semantic block ordinal / seq range
- byte offset checkpoint
- revision / updatedAt

实现上允许 cursor 是不透明字符串，不向前端暴露内部结构。

### 8.3 checkpoint / index

文件方案下，为避免从头扫描 timeline：

- 每 N 个 timeline item 生成一个 checkpoint。
- checkpoint 可内嵌在 `acp.snapshot.json` 尾部摘要，也可独立为 `acp.timeline.index.json`。

index 最小信息：

- checkpoint item ordinal
- file byte offset
- timestamp
- itemId

这样打开最新页、向上翻历史都不需要全量扫描。

### 8.4 无感丝滑分页

前端分页交互要求：

- 前端会话历史分页的单次加载条数由 `configs/app-config.toml` 的 `acpChatEventPageSize` 控制，默认 96，单位是语义块；一个活动摘要或 Agent link 始终只计一块。内存与原生 DOM 中保留的页数由 `acpChatEventWindowPageCount` 控制，默认 3，窗口上限由两者相乘派生为 288，避免跨页裁剪时滚动跳变。
- 向上翻页只 prepend timeline item，不触发底部自动滚动。
- 保持 scroll anchor，避免闪跳。
- 活跃会话只有在用户位于真实最新窗口、`hasNewer=false` 且没有分页请求时，timeline live patch 才进入页面 latest-wins buffer、合入当前窗口并保持吸底。用户正在读旧历史、`hasNewer=true` 或 older/newer 请求进行中时，cached/paged `loadedEvents` 是可见窗口唯一事实；text/thought/tool/plan 等 live item 完全不进入页面 buffer，只标记 newer，并保留在 Router 的有界 branch replay 与后端 canonical timeline，不创建历史 DOM 或待渲染队列。界面维持“有更新 / 返回最新”，待返回最新或分页收敛后再按稳定 identity、revision 和 cursor 追平。
- 历史阅读期间仍由统一 control reducer 即时投影 timing、usage、Agent branch result、permission/elicitation、terminal lifecycle 与 prompt admission；这些更新不得改变当前 timeline item 集合、制造 seq 缺口、触发相反方向裁剪或破坏 DOM scroll anchor。同会话 prop/session refresh 也不得把 live head 混入 historical window。活跃会话的 live patch 与历史分页最终使用同一 timeline item 模型无缝收敛，不建立第二套消息事实源。
- Activity 展开详情使用独立局部 cursor 和“显示更早活动”，不得改变会话 `beforeCursor/afterCursor/hasOlder`；单条工具 raw output 继续按需读取。

## 9. token / cost / elapsed 设计

### 9.1 token / cost

切到 V2 后，不再依赖扫 timeline 全量重算 session usage。

权威来源改为 runtime aggregator + snapshot：

- `usedTokens`
- `contextWindowSize`
- `inputTokens`
- `outputTokens`
- `cachedReadTokens`
- `cachedWriteTokens`
- `totalTokens`
- `totalCostUsd`

规则：

- `usage_update` 先进入 runtime usage state：正数更新确认后的 `usedTokens`，瞬时 `used=0` 只作为 raw 采样或 compact reset 边界，不覆盖 snapshot/UI；`contextWindowSize / totalCostUsd` 独立更新。
- prompt response 结束时补齐 `inputTokens / outputTokens / cached* / totalTokens`。
- 删除 `accumulatedUsedTokens`；上下文占用是 gauge，不能通过正向 delta 推导累计 Token 消耗。累计消耗只采用 Provider 返回的 `inputTokens / outputTokens / cached* / totalTokens`。
- UI 直接读 snapshot 中的 usage，live 期间通过 `usagePatch` 刷新。

timeline 只在需要消息级 token 展示时，给最终 assistant message item 写入：

- `usedTokensAtStart`
- `usedTokensAtEnd`
- `tokenDelta`

### 9.2 elapsed

V2 下 session 净处理耗时必须改为 runtime 维护，不再以“详情页读文件重算”为主路径。

建议 runtime 维护：

- `sessionElapsedMs`
- `currentTurnElapsedMs`
- `activeTurnStartedAt`
- `activeTurnLastActivityAt`
- `permissionWaitStartedAt`
- `permissionWaitAccumulatedMs`
- `pendingPermissionIds`

规则保持与当前口径一致：

1. Gold Band 用户 prompt accepted 时开启新 turn。
2. assistant / thought / tool / plan 的有效活动刷新 `lastActivityAt`。
3. permission pending -> selected 期间不计入净耗时。
4. session active 时 `currentTurnElapsedMs` 可按 now 实时增长。
5. turn 结束时把净耗时累加进 `sessionElapsedMs`。

历史读取时：

- 优先读 snapshot 中的 metrics。
- 仅在 legacy 会话、snapshot 缺失或调试校验时，从 timeline / events 回放重建。

## 10. SQLite 辅助检索方案

### 10.1 原则

SQLite 在本方案中**只用于辅助检索**，不承担：

- 会话详情渲染主存储
- 活跃会话 live state
- raw frame 排障
- timeline 恢复的唯一来源

文件仍然是权威事实源。

### 10.2 使用场景

SQLite 只承担两类检索：

1. **跨 session 用户 prompt 搜索**
2. **可选的 final timeline item 搜索**

### 10.3 最小表设计

建议最小化为：

- `sessions`
  - `session_id`
  - `attempt_path`
  - `task_id / run_id / round_id / node_id / attempt_id`
  - `created_at`
  - `updated_at`
  - `title`

- `session_prompts`
  - `id`
  - `session_id`
  - `prompt_id`
  - `timestamp`
  - `text`
  - `normalized_text`

- `session_prompts_fts`（FTS5）
  - 对 `text` 建立全文索引

可选：

- `timeline_items`
  - 只存 final timeline item
  - 不存中间流式 revision

### 10.4 写入策略

- 文件写入成功后，再异步写 SQLite 索引。
- DB 写失败不影响会话详情与恢复。
- 可通过后台 backfill 为旧会话补索引。

### 10.5 兼容策略

- 新 V2 会话：写文件 + 写 SQLite 索引。
- 旧 V1 会话：首次命中搜索范围时可 lazy backfill。
- 搜索优先走 SQLite，详情优先走文件。
- 若 `sessions` / `session_prompts` 索引 schema 落后，则启动时只重建这组会话索引表并从文件回填，不做逐列迁移，也不影响 `tasks` 索引。

## 11. 旧会话兼容与迁移

### 11.1 版本定义

- **V1**：`acp.session.json` + `acp.events.jsonl` + `acp.raw.jsonl`
- **V2**：`acp.snapshot.json` + `acp.timeline.jsonl` + `acp.raw.jsonl`

### 11.2 兼容读取

读取逻辑：

1. 若存在 `acp.snapshot.json`，按 V2 打开。
2. 否则若存在 `acp.events.jsonl`，按 V1 legacy reader 打开。
3. 若用户显式打开旧会话，可在后台生成 V2 timeline / snapshot。

### 11.3 lazy migration

推荐 lazy migration，而不是强制一次性全量迁移：

- 第一次打开旧会话时：
  - 读取 V1 `events + session + worker-ref`
  - 生成 V2 `timeline + snapshot`
  - 后续优先走 V2

- 正在运行中的旧会话不强切：
  - 已启动的 V1 attempt 继续按旧链路跑完
  - 新建会话统一走 V2

## 14. 风险与权衡

### 14.1 风险

1. live push + history page 混合后，前后端状态同步复杂度上升。
2. timeline item 边界若定义不好，可能出现消息合并错误或 tool call 错位。
3. snapshot 与 timeline 若一致性处理不好，恢复链路会出现偏差。
4. SQLite FTS 对中文 prompt 的检索效果需要单独评估 tokenizer 与标准化策略。

### 14.2 权衡

- 本方案刻意不把 SQLite 升格为主存储，换来较低改动和更稳兼容，但历史查询高级能力会受限于“旁路索引”模式。
- 文件优先意味着仍需做好 checkpoint / index，否则 timeline 超大后历史读取仍会变慢。
- 相比当前方案，本方案实现复杂度上升，但会显著改善流式体验、职责边界与后续搜索扩展性。

## 15. 最终结论

本期推荐的会话优化方案是：

1. **以 `acp.timeline.jsonl` 取代 `acp.events.jsonl` 作为 V2 会话主时间线。**
2. **以 `acp.snapshot.json` 取代 `acp.session.json` 作为 V2 会话快照与恢复锚点。**
3. **保留 `acp.raw.jsonl` 作为协议排障事实源。**
4. **活跃会话从轮询改为 push，timeline item 采用写时聚合。**
5. **token / elapsed 改为 runtime 聚合 + snapshot 持久化，不再以读时重算为主路径。**
6. **SQLite 仅用于辅助检索，尤其是跨 session 用户 prompt 搜索，不承担会话主存储。**
7. **旧会话通过 legacy reader 与 lazy migration 继续可打开。**
