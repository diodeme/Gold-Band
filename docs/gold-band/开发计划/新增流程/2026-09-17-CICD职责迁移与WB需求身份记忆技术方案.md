# CICD 职责迁移与 WB 需求身份记忆技术方案

日期：2026-09-17。
状态：核心契约与专项接口测试完成；真实模型和 WeTest 端到端验收待补。

产品行为后续以以下文档为真源：

- [工作空间与任务记忆及 WB CICD 工作流](../../产品设计文档/runtime/workspace-task-memory.md)

## 1. 结论

本次不是四个互不相关的文案修改，而是三类职责边界未收敛：

1. 代码产出与提交属于开发测试节点，代码推送属于 CICD 发布前检查。当前提交和推送都放在 CICD，职责落在错误的生命周期阶段。
2. `storyId` 和 `storyName` 是开发测试节点生成提交消息所需的任务级规范输入，当前没有固定 key、初始化时机和缺失值策略。
3. CICD 共享参数当前只有“默认写任务、用户明确要求才写项目”的通用规则，没有逐 key 作用域表，也没有执行后的记忆写入核验。

因此应调整职责和记忆契约，不增加新的工作流节点、数据库、缓存、队列或第二套状态机。

## 2. 现状评估

### 2.1 CICD 提交与推送

当前 `src/prompts/zh-CN/profile/cicd.md` 和英文版本都包含完整的“代码提交前置条件”：

- 检查相关未提交改动。
- 向用户确认三行提交消息。
- 执行 `git add` 和 `git commit`。
- 检查未推送提交并执行 `git push`。
- 任一提交或推送门禁失败时停止构建部署。

问题：

- 开发测试节点完成后不保证存在提交，CICD 才能发现和补提交，形成职责倒置。
- CICD 承担代码内容整理和提交确认，扩大发布角色的业务责任。
- push 是远端构建输入是否正确的关键事实，不能与 commit 一起被简单删除。

### 2.2 采访与拷问节点

当前采访和拷问角色只负责需求澄清：

- 采访角色产出 `interview-spec.md`。
- 拷问角色产出 `grill-consensus.md`。
- 两者均支持现有 `AskUserQuestion` / elicitation 结构化提问。

当前没有 `storyId`、`storyName` 的任务记忆检查和补问，也没有 WB 渠道专属行为。

### 2.3 开发测试节点

当前开发测试角色完成实现和自动化验证，但不负责提交，报告也没有提交 OID。默认轻量工作流和 WB CICD 工作流关闭可选入口后，会直接从 `dev-test` 开始，此时没有采访或拷问节点提供需求身份。

因此仅在采访和拷问提示词中增加补问仍不完整，开发测试必须具有缺省兜底，才能满足“每次执行完毕必须提交”。

### 2.4 CICD 共享参数记忆

当前实现保证的边界只有：

- `memory_write` 成功后，记忆领域服务会通过逐 key CAS 和原子写入可靠落盘。
- 任务作用域覆盖工作空间同 key，任务空值不回退。
- `subSysId*` 位于工作空间记忆。

当前不能保证：

- CICD 一定调用了 `memory_write`。
- 每个已确认参数一定写到了预期作用域。
- 14 个 CICD key 的写入完整性与当前执行参数一致。

原因是这些内容目前只存在于角色提示词，没有逐 key 作用域表、执行后刷新核验或 runtime 工具调用审计。

## 3. 目标行为

### 3.1 调度职责

```text
采访 / 拷问
  -> 解析并保存 storyId / storyName

开发测试
  -> 实现、验证
  -> 自动提交本次任务相关改动
  -> 报告 commit OID

验收
  -> 独立验证

CICD
  -> 只读检查任务相关提交是否已推送
  -> 必要时询问并执行 push
  -> 构建、物料 / 镜像推送、部署
```

CICD 不再执行 `git add`、`git commit`，不再生成或确认提交消息。

### 3.2 WB 需求身份

仅在 WB 渠道的采访、拷问节点增加需求身份前置检查，且优先于拓扑枚举或拷问 Round 0：

1. 调用 `memory_read`。
2. 只检查 `snapshot.task`，不把工作空间同 key 当作已有任务身份。
3. 仅当任务作用域同时存在非空、非纯空白的 `storyId` 和 `storyName` 时复用。
4. 任一 key 缺失、为空或不成对时，提一个问题，语义选项固定为：
   - `不存在`
   - `其他（用户自行输入）`
5. 有结构化提问工具时使用 `AskUserQuestion` / elicitation；无结构化工具时用纯文本，但选项语义不变。
6. 选择“不存在”时：
   - `storyId = "0"`。
   - `storyName` 从需求内容提取简短名称。
   - 提取优先级：明确标题或首行摘要、需求目标中的核心名词短语、`系统需求` 兜底。
   - 名称必须为单行，去除模板标签和无关标点，最多 40 个 Unicode 字符。
7. 选择“其他”时，用户必须同时提供需求 ID 和需求名称；ID 和名称均按去首尾空白后的单行字符串保存。
8. 使用 `memory_write` 将两个 key 写入任务作用域：
   - 缺失 key 使用 `expectedRevision = null`。
   - 已有但需纠正的 key 使用 `memory_read` 返回的该 key revision。
9. 两次写入后重新 `memory_read`，确认任务作用域中的两个值完全一致。
10. 工具不可用、写入失败或核验失败时继续身份前置检查，向用户说明未持久化，并使用用户已确认或补充提供的值继续，不假装已经保存。

开发测试节点执行提交前也必须读取任务身份：

- 已存在完整任务身份时直接使用。
- 采访或拷问被关闭导致身份缺失时，不提问，按 `storyId=0` 和同一名称提取规则补齐任务记忆，再提交。

### 3.3 开发测试自动提交

WB 渠道的开发测试节点在实现和测试完成后执行以下收尾：

1. 先识别本次任务相关改动，排除执行前已存在或明显无关的用户改动。
2. 若本次没有任务相关改动，记录“无需提交”及判断依据；不得创建空提交。
3. 若存在任务相关改动，读取或补齐 `storyId`、`storyName`。
4. 根据实际差异自动选择 Conventional Commits 类型和简短中文描述。
5. 只 stage 本次任务相关路径，禁止 `git add -A`。
6. 每次节点成功执行生成一次逻辑提交，消息严格为三行：

```text
--story=[{storyId}] {storyName}
{type}: {中文描述}
#AI COMMIT#
```

7. 提交后复查 commit OID、提交消息和任务相关路径状态。
8. 将 commit OID、提交消息、纳入路径和未纳入路径写入开发测试报告，供验收和追踪使用。

该过程不向用户询问提交消息或请求确认格式。现有 ACP 命令权限门仍独立生效，不为自动提交绕过或关闭全局权限。

若提交失败，开发测试不得声称完成；应保留失败输出并交给现有节点失败、人工恢复或验收失败路径处理。

### 3.4 CICD 推送提醒

CICD 只保留简单推送检查：

1. 构建前检查当前分支是否存在未 push 的提交；没有时直接继续。
2. 存在时提醒用户并询问是否 push。用户确认后执行普通 `git push`，成功后继续构建。
3. 用户不 push 或 push 失败时，说明远端可能不包含本地提交，并询问是否继续构建。继续则按远端现状推进，停止则不触发构建。
4. 禁止 force push。

## 4. 记忆与作用域契约

### 4.1 固定作用域

| Scope | Key | 生命周期与写入方 |
| --- | --- | --- |
| workspace | `subSysId1`、`subSysId2` 等 | 项目子系统清单；由项目记忆设置维护；CICD 只读，不隐式改写 |
| task | `storyId` | 当前任务需求 ID；采访、拷问或开发测试兜底写入 |
| task | `storyName` | 当前任务简短需求名称；采访、拷问或开发测试兜底写入 |
| task | `cicd.build.jobId` | 本次任务唯一构建的已核实 Job ID |
| task | `cicd.build.branch` | 本次任务实际构建分支 |
| task | `cicd.build.appList` | 本次任务的构建与推送应用范围 |
| task | `cicd.build.appCoverage` | 构建产物证据确认覆盖的子系统 |
| task | `cicd.deploy.<S>.*` | 当前任务对各子系统的部署选择、模板和目标参数 |

本方案不新增 CICD 专用项目默认 key。若后续要求 Job 或部署模板跨任务复用，应新增明确的 `.default` key 和覆盖规则，不能把任务生效值直接写入项目记忆。

### 4.2 CICD 写入核验

CICD 在触发外部写操作前必须完成一次参数持久化 checkpoint：

1. `memory_read` 获取最新快照和 revision。
2. 对本次阶段实际使用的参数逐 key `memory_write`，所有 CICD 参数使用 `scope = task`。
3. 全部写入成功后再次 `memory_read`。
4. 按 key 比较任务作用域值和本次确认的生效值。
5. 核验成功时进入构建、物料 / 镜像推送或部署；工具不可用、写入失败或核验失败时，向用户询问或确认本次参数并继续，不阻断执行，同时明确数据未持久化。
6. 报告列出已写入 key、scope、写入结果和最终 revision；不把报告当作第二事实源。

只写当前阶段需要的字段，不用示例值填满全部字段。执行 ID、授权、运行状态和终态证据继续写入 runtime 附件，不进入记忆。

## 5. 实现方式

### 5.1 Prompt

- 修改 `src/prompts/zh-CN/profile/cicd.md` 和 `src/prompts/en/profile/cicd.md`：删除提交职责，保留 push 提醒与作用域核验。
- 修改 `src/prompts/zh-CN/profile/dev-test.md` 和英文版本：增加 WB 自动提交、需求身份兜底和报告字段。
- 新增双语 WB 需求身份补充提示词，供 interview / grill 复用。
- 所有新增或修改提示词继续放在 `src/prompts/<language>/...` 对称目录。

### 5.2 WB 渠道组合

复用现有编译期 `RELEASE_CHANNEL` / `WB_CHANNEL` 真源，在构造内置 interview、grill、dev-test 内容时，仅在 WB 渠道追加对应补充提示词。

不扩展 Profile 动态模板上下文，不复制完整角色正文，不让非 WB 渠道获得行为。

### 5.3 现有能力复用

- 提问复用现有 ACP elicitation / `AskUserQuestion`。
- 记忆读写复用 `gold-band-memory` MCP、逐 key CAS 和原子写入。
- Git 操作复用现有 `process::background_command()`，不引入 Git 库。
- 工作流拓扑不变，CICD 节点仍为人工 check，单次提交和人工恢复语义不变。

## 6. 测试计划

### 6.1 先建立失败契约

1. WB CICD Profile 仍包含 `git commit` 或三行提交格式时，新契约测试失败。
2. WB interview / grill 内容缺少 `storyId`、`storyName`、`memory_read`、`memory_write` 或两个提问选项时失败。
3. WB dev-test 内容缺少自动提交、`git add` 具体路径、三行格式或 OID 报告时失败。
4. WB CICD 缺少逐 key 任务作用域和写入后刷新核验时失败。
5. default 渠道 interview / grill / dev-test 意外包含 WB 补充规则时失败。

### 6.2 接口级回归

- Profile list / show 固定 WB 与 default 渠道内容差异。
- `memory_domain` 固定 `storyId` / `storyName` 任务级写入、空值不回退、revision 冲突和跨节点读取。
- `memory_invocation` 固定节点启动时能读取前序已写入的需求身份。
- `cicd_profile_contract` 固定 CICD 不再提交、仍可 push、所有 CICD key 写任务、`subSysId*` 属于工作空间。
- `default-lightweight` / `wb-development-cicd` 模板接口测试固定角色 ID 和拓扑不变。

### 6.3 行为验收

- WB 采访开启且任务身份缺失：只补问一次；选择“不存在”后写入 `0` 和提取名称，后续节点不再重复提问。
- 任务身份完整：采访、拷问和开发测试均不重复提问。
- WB 可选入口关闭：开发测试仍可兜底补齐身份并提交。
- 开发测试产生相关改动：自动生成三行提交并报告 OID，不询问提交消息。
- 无任务相关改动：不创建空提交，报告说明原因。
- CICD 发现未推送提交：询问 push；确认后推送并核验；拒绝或 push 失败时继续询问“继续构建 / 停止”，只有用户明确选择继续后才按远端现状推进。
- CICD 写入阶段参数后刷新：所有目标 key 在任务作用域值与确认值一致。

### 6.4 强保证边界

上述接口测试能保证交付给 Agent 的角色契约、渠道组合和记忆服务行为，不能证明任意模型一定执行了工具调用或 Git 命令。

若后续要求 runtime 级强保证，需要另行设计：

- 基于 ACP tool-call 结果审计 `memory_write` 成功性。
- 在节点结束边界读取 canonical 记忆和 Git HEAD 校验提交。
- 为失败结果映射现有节点失败 / 人工恢复，不新增旁路状态机。

该增强工作量和跨 provider 兼容风险明显高于本次职责迁移，不在本方案默认范围内。

## 8. 自评审

### 8.1 根因与方向

- CICD 提交职责属于生命周期职责错位，应把 commit 移回开发测试，把 push 保留在发布前检查。
- 需求身份缺失属于任务级数据契约不完整，应补齐固定 key、补问和缺失兜底，不通过 CICD 补提交掩盖。
- 记忆作用域不清属于已有共享记忆契约的实现不完整，应增加逐 key 作用域表和写后核验，不新增存储层。

### 8.2 过度设计

复用现有 Profile、渠道常量、AskUserQuestion、记忆 MCP、原子写入、工作流节点和 Git CLI。不新增节点、状态机、数据库、缓存、队列、后台同步或 CICD 专用项目默认键。

### 8.3 性能

- 提示词增量固定有界，不随历史增长。
- 每次身份读取仍是两个最多 100 条的本地记忆文件，合并复杂度 O(P + T)。
- Git 检查只判断当前分支是否存在未 push 提交，不扫描全部历史或展开完整提交清单。
- 无新增网络轮询、N+1 读取或长时间锁。

## 9. 已确认决策

本方案采用以下口径：

1. 项目记忆只保存 `subSysId*` 等项目清单；`story*` 和全部 `cicd.*` 生效参数保存到任务记忆。跨任务 Job / 模板默认值若需要，另设 `.default` key。

已确认：CICD 发现未推送提交且用户拒绝 push 或 push 失败时，必须提示用户选择是否继续构建；选择继续后按远端现状推进。
