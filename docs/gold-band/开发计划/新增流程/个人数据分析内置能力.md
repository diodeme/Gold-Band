## 4. 实现顺序

### 阶段 A：数据与 schema

1. 定义 `AnalyticsOperation`、`AnalyticsProjection`、`ContentManifest`、`SemanticBatchManifest`、`AnalyticsReport` 和 `MetricDefinition`。
2. 明确每个字段的 canonical 来源、缺失语义、schema version 和迁移策略。
3. 固化三个 metric ID：
   - `direct.reply_completion_rate`
   - `workflow.run_terminal_success_rate`
   - `auto.outer_run_terminal_success_rate`
4. 定义结构化错误，仅返回 `code + params`。

### 阶段 B：读取与投影接口

1. 从配置化 Gold Band home 解析 projects root，前端不提交绝对路径。
2. canonicalize root 和候选路径，拒绝越界、symlink/reparse point 和排除源。
3. 按 project/task/run/attempt 流式解析 canonical 文件，局部坏数据写入 coverage。
4. 默认跳过 `acp.raw.jsonl`、doctor/、诊断、DB/WAL、ZIP、PID、class 和二进制。
5. 生成确定性全历史投影、evidence locator 清单和内联有界语义批次；客户端不按 Agent 返回的 locator 回读原文件，prompt 约束 Agent 不主动扫描原始目录。通用 ACP/provider 已有文件能力不做技术隔离，按“永不修复的风险接受项”处理。
6. 使用 project/task 完整 locator 关联 task、conversation、run、node 和 usage；标题只用于展示。
7. 最近任务过滤 Direct；Workflow 使用 run 终局，AUTO 只使用 outer run 终局。
8. 使用完整 run/attempt locator 读取 `acp.snapshot.json.timing.sessionElapsedSeconds`；任务和终局 Run 累计全部节点 attempt，AUTO 并行节点求和表示累计 Agent 执行时间。
9. Direct 的 `run.json` 表示会话容器；回复完成率使用 attempt usage journal 中按 `turn_id` 去重的 started/completed 事实，不使用旧 `turn.json`。

### 阶段 C：后台 operation 与 Agent

1. 实现 `start_personal_analytics({ agentType })`、`get_personal_analytics()`、`cancel_personal_analytics(...)`。
2. 同一用户只允许一个 active operation，返回稳定 operationId 和单调 revision。
3. 复用现有后台 Agent run，使用本计划已落地的中英文固定 prompt。
4. Agent 只输出 `PersonalAnalyticsNarrative`；客户端校验并与确定性投影组装最终报告。失败时 repair 一次，再失败返回 `analytics.report-invalid`。
5. 新执行失败时保留上一次成功报告。
6. 附件投影遵循 runtime 配置的有界策略；洞察 JSON 只从最新有界 ACP 消息按稳定身份契约提取。

### 阶段 D：原生页面

1. 在帮助菜单新增与用户反馈同级入口。
2. 帮助菜单直接导航到独立页面，在标题操作区使用 shadcn `Select` 和 `Button` 放置 Agent 选择与开始分析。
3. accepted 后在当前页面展示 scanning/analyzing/validating/terminal 状态；运行中锁定 Agent 选择并禁止重复启动。
4. 使用聚合 DTO 和原生页面组件渲染使用概览、最近任务、质量、效率、Token 消耗、上下文与技能使用，末尾展示数据覆盖；覆盖字段名称通过 shadcn Tooltip 提供精简含义。最近任务和耗时 TOP10 同时展示累计执行耗时与 Token，所有 Token 使用 K/M。
5. 实现取消、失败恢复、保留旧报告的重新生成、窄窗口和浅色/深色主题。

## 7. 性能影响评审

- 算法和 I/O：每次 O(total eligible canonical bytes) 流式扫描；始终分析全部历史，不维护增量缓存。节点 snapshot 已在既有扫描中读取，本次耗时关联不增加第二次目录扫描。
- 内存：JSONL 逐行解析、有界 channel 和语义批次；不保留完整 timeline/附件集合。
- 报告：最近任务和任务排行固定 TOP10，节点/工具/Agent/Skill 固定 TOP12，不向 React 传递全量历史明细。
- 调用频率：用户主动触发；active operation 去重，避免并发重复扫描。
- UI：只订阅当前 operation 和聚合 DTO；Agent 注册表复用 App 已有权威状态，不为页面重复请求或建立缓存。
- 存储：先复用现有数据库，不建立第二个索引或无界缓存。

2026-08-17 release 实测：`3334` 文件、`374,130,152` bytes，投影耗时 `6.032s`，峰值工作集 `8.2 MiB`，解析 `1509`、跳过 `1822`、语义样本 `82`。该结果低于 10 秒/32 MiB 的 MVP 验收目标，因此不增加数据库索引、并行扫描或无界缓存。

## 8. 过度设计复核

- 必要新增：一个跨扫描、Agent attempt 和报告校验的 `AnalyticsOperation`，因为现有 conversation run 无法表达该专用生命周期。
- 明确不新增：通用 BuiltIn Skill 平台、第二套 Agent runtime、第二个数据库、报表历史中心、服务端同步、金额模型和 HTML viewer。
- 页面内选择与启动复用既有 shadcn 控件和 App Agent registry；删除无独立确认价值的 Dialog，不新增第二套表单或导航状态。
- 在真实性能基线证明有需要前，不增加额外队列、并行扫描或缓存层。

## 9. 2026-08-18 优化实施计划（实施中）

本节记录已批准设计的实施进度。E-H 代码主体已落地，I 阶段测试、性能与页面验收完成后更新最终验收结果；不做兼容旧入口的旁路。

### 阶段 E：SQLite 分析索引

1. 在现有 `gold-band.sqlite` 中增加 8 张 `analytics_*` 物理表、必要索引、迁移记录和逻辑视图，由独立 `AnalyticsIndex` 模块管理。
2. 定义源文件 fingerprint、解析状态、稳定 locator 和 `index_revision`；所有派生写入使用事务和幂等 upsert。
3. 项目字段冗余在任务表、Token 汇总归属 attempt、事件计数进入带 CHECK 约束且保存自身 `activityEpoch` 的通用 counter 表；timeline 按单条事件时间写入，项目、usage、事件计数和洞察明细只用视图重建，不建立第二份物理事实。
4. schema 7 延续 schema 6 的 `analytics_attempts` 来源与 identity 口径，并把 `analytics_insight_runs` 替换为纯 completed `analytics_insight_cache`。普通节点使用物理 attempt 目录，AUTO dynamic leaf 使用 `dynamic/nodes/<leaf-id>` 权威目录，固定的 ACP attempt 子目录不单独形成统计身份。Dynamic Node 按 `id/provider/outcome` 解析，sibling leaf 按各自 locator 分组。Node 贡献身份、outcome 和 workflow invocation 的完整 child run locator，Snapshot 贡献耗时，attempt usage 的 `promptCompleted` 贡献 Token 与去重 prompt 数。`promptStarted/promptCompleted + turn_id` 先投影为模式中立的 `prompt-status` counter，报告查询再按 canonical `runMode=direct` 生成 Direct reply 指标；usage-only 行不计入执行 attempt。旧 `turn.json`、task 根目录 usage、无 `kind` usage 和 baseline totals 不进入事实表。
5. 首次执行全量扫描；后续枚举 canonical 文件，仅重新解析新增或变化文件，并删除消失文件的派生事实。
6. 单文件损坏、未知版本或解析失败记录结构化状态，不阻断其他文件；索引版本不匹配支持整体重建。
7. 保留 `.maling/projects` 文件作为唯一权威事实源，SQLite 始终可删除重建。

### 阶段 F：日期范围报告接口

1. 将确定性统计入口拆分为 `sync_personal_analytics` 和 `query_personal_analytics_report(range)`。
2. 报告查询只读取 SQLite 聚合，不重新解析历史文件；state、事实聚合和 coverage 在同一读事务中取得，并携带该 snapshot 的 `indexRevision`、source coverage 和 range。
3. 使用本地时区包含起止日的自然日范围；Workflow run、AUTO outer run、AUTO child run 和 Direct session 保存在 `analytics_runs` 并按 `unitType` 区分，AUTO child run 由 canonical `childRunId` 转换出的完整 locator 识别且不进入 outer 可靠性、终局汇总或最近任务状态。Direct reply 状态与其他 counter 均按自身活动时间筛选，attempt 不跨日期拆分；历史起止对范围内 run 执行 min/max。任务 `lastActivityAt` 批量聚合范围内 conversation/run/attempt/counter；全局 task 活动和范围外最新导航 run 不得参与当前范围时间与排序。
4. Timeline counter 按稳定 `itemId` 的最高 revision 生成紧凑计数投影，同一逻辑事件的 processing/completed patch 只计一次；`conversationCount` 按范围内任务存在 `conversationSourcePath` 统计，不绑定任务模式。
5. 复用三个准确指标名称、累计执行耗时口径、Token 口径和 TOP10/TOP12 有界输出。

### 阶段 H：Agent 洞察独立生命周期

1. “开始分析”改为只同步索引并生成确定性报告，删除开始分析即调用 Agent 的旧路径。
2. 新增 `start_personal_analytics_insights(agentType, range)`，复用现有 ACP runtime 和中英文固定提示词。

9. 前端首次 snapshot、live event、start response 和 cancel response 统一进入 merge；不同 operation 先比较 generation，同一 operation 再比较 revision，终态不得被迟到响应回退。

### 2026-08-30 扫描性能收口记录

### 优化方案评审结论

- 根因：日期筛选和重复分析暴露出缺少持久派生投影；统计与洞察耦合是生命周期设计缺陷，不是 UI 缺件。
- 复用：现有 SQLite/rusqlite、WAL、事务、Agent runtime、shadcn/ui 和原生日期输入满足需求，不新增第三方依赖。
- 必要性：SQLite 索引是本优化必要新增；8 张物理表加逻辑视图保留身份边界与查询能力，章节导航和洞察独立按钮是用户可见能力拆分。
- 边界：不新建第二个数据库、不做通用缓存平台、不保存无限历史报表、不引入服务端同步。
- 风险：索引迁移、fingerprint 成本、跨日期归属和洞察缓存一致性必须在接口测试中固化；SQLite 永远可重建，不能反向成为权威事实源。
