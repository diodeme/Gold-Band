1.首页任务列表，去掉导入requirements按钮，只保留创建任务
2.点击创建任务按钮，弹出创建任务弹窗
3.弹窗中支持手动填写任务标题、描述和详细需求内容，也支持导入现有需求（支持txt\md格式）覆盖当前编辑内容
4.填写或导入需求后，需要创建工作流
5.工作流可以新增节点和边，为每个节点配置不同的agent，agent来源为agent管理页面的agent卡片
6.工作流保存后持久化为json，在任务详情页的工作流中可以修改工作流，round详情中的工作流则是每一次工作流的运行时快照
7.节点前后需要有环境的生成和销毁(比如释放agent等)

关于工作流的修改与新增：最好是能做到画布式拖拽生成工作流，是否有现成组件可以使用？
关于工作流中的节点与边：
现有的节点类型现在可能要去掉execute节点，和execute-plan产出节点

节点的本质类型只有三种。1.普通节点 2.是否需要人工check？（人工check逻辑你先留白，本期不实现） 2.是否需要验证AI输出结果？ 2.1 输出的DSL配置（也就是AI要输出的指定类型，目前支持json） 2.2 DSL成功条件（json中指定字段的值） 2.3 成功流向（去哪个节点） 2.4 失败流向（去哪个节点），边可以设置一些属性，比如成功边，失败边，边可以指向其他节点（则节点生成新的attempt），或者new round（则生成新的round），边指向节点时，如果是回路（即A-C--》D--》E-->...-->->B-->A）,在B节点指向A的边中可以提供一个选择，是开启新的session，还是继续A刚刚的session？（这里涉及到环判断，可能比较复杂，如果实现困难，可以先用简单方式，即验证输出结果类型的节点，失败边提供这两个选项即可）
工作流这里可以提供一套默认工作流给用户选择：
interview（普通节点，访谈角色，产出 interview-spec.md，由人工 check 判定成功后继续） --> plan（普通节点，方案角色） --> 开发（普通节点，开发角色） --> review（普通+验证输出结果，DSL中输出review是否通过，成功指向测试，失败指向开发，默认是继续开发原session） --> 测试（普通+验证输出结果，DSL中输出test是否通过，默认是继续开发原session） --> 验收（普通+验证输出结果，DSL中输出verify是否通过） --> cleanup（普通节点，清理角色，无 AI 输出验证） --> 结束

- 节点会话按边上的 session 策略展示：`session=new` 的 attempt 始终是独立可切换 conversation；`session=continue` 挂回被继续的 provider session，并在同一 conversation 内用 attempt 分隔行展示。
- 工作流控制项支持可选的 `max_attempts` 与 `max_rounds`：前者在单个 round 内限制 `failure` 触发的修复/重试跳转次数，正常 `success` 前进和 schema 隐藏修复不消耗次数；后者限制 `$new-round` 打开的新 round 次数；留空表示不限制，超限时 workflow 失败并展示结构化停止原因。默认完整工作流和默认轻量工作流都显式配置 `max_attempts=10`、`max_rounds=3`。

- 用户级 context 存储维护跨 workspace 工作流模板列表 `~/.gold-band/context/workflows.json`，通过 `templates` 数组支持多个命名 workflow，并记录上一次创建任务使用的 workflow；同一模板的本机模型绑定在各 workspace 共用。创建任务 Sheet 中上次使用的命名模板以“上次创建使用的是：xxx”提示展示在下拉框旁，点击模板名后选中该模板并隐藏提示，不作为下拉选项；模板下拉顶部支持新增模板并进入空白画布，行内支持删除非默认模板。内置与自定义模板的主按钮均为“保存修改”：内置定义仍不可覆盖且必须在全部普通 Worker 绑定有效后保存，自定义模板允许保存不可运行的绑定状态；存在内置定义改动时只能另存全部修改，或“还原其他修改”后保留绑定草稿。模板保存/删除成功提示短暂展示后自动消失，错误提示展示在工作流模板操作区下方并持续保留，不占用创建任务顶部全局位置。
- 普通 Worker 通过内部 `executionSlotId` 关联模型绑定：修改 node id 保留绑定，复制节点生成新槽位并复制完整绑定，另存工作流保留槽位并由新 template ID 隔离。普通导出不包含模型绑定或槽位；导入生成新槽位并保持未配置。可编辑模板、Task 与定时任务采用一次性破坏式迁移，历史运行快照不迁移。模板绑定嵌入 `WorkflowTemplate`；Task 的 `{ workflow, modelBindings }` 聚合写入 `authoring/workflow.json`；定时任务把同一聚合冻结到 content snapshot；Run 只保存注入完整执行字段后的 `workflow.snapshot.json`。
- Managed Agent 删除影响统计已收敛为用户级聚合接口：工作流模板只统计用户级 store 一次，Task/定时任务遍历全部已注册会话 workspace 与当前 Workbench workspace，并按稳定 `projectId` 去重；磁盘与 SQLite 扫描通过 async command 的 blocking pool 执行。删除确认弹窗只有在统计成功后才启用删除，失败时保留结构化原因并支持原位重新统计，迟到请求不得覆盖新选择。
- “另存为新的工作流模板”时后端会自动重置 `workflow.id` 为新的分布式唯一值，不向用户暴露内部碰撞；如果用户手动编辑 JSON 导致模板库内 `workflow.id` 与其他模板重复，则保存模板会失败并返回 `workflow.duplicate-id`。
- 工作流编辑器 JSON 视图支持直接编辑完整 workflow DSL，便于用户手动修复 `workflow.id` 冲突等模板级问题。
- AI-DYNAMIC 保存时会额外校验其引用的所有模板；只要被引用模板存在 `workflow.id` 与其他模板重复的脏数据，当前工作流就不能保存，直到用户修复对应模板 JSON。
