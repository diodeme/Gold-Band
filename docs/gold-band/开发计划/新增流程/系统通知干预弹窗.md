# 系统通知干预弹窗

> 完整设计与校准方案见 `.claude/design/system-notification-intervention-reimpl-plan.md`。本文档为开发计划侧的实现记录，保持与代码同步。

## 1. 背景与边界

- 编排器在 5 类关键干预场景（人工确认 / elicitation 提问 / 权限请求 / 执行错误 / 进程中断）下需要主动提醒用户。桌面端 EXE 主路径不保留 terminal 心智，因此通过 **OS 系统通知（Windows Toast）** 单一表面提醒。
- **只涉及弹窗功能本身**，不改动主干编排器控制流、ACP 命令逻辑、session builder、PermissionRequestCard 数据源。
- 弹窗生命周期：展示目标时长由 `configs/app-config.toml` 的 `notificationAutoDismissTargetSecs` 管理，当前为 20 秒。Windows 按最近原生档位解析为 Long，实际约 25 秒后自动收起；未点击时仍保留在通知中心。通知无 resolved 闭环，点击「忽略」或「查看详情」后清 dedup key；自然超时不清 dedup，避免同一事件重复提醒。

## 2. 数据结构（领域划分）

| 结构 | 所属领域 | 位置 |
| --- | --- | --- |
| `InterventionNotification` | 核心库（与 Tauri 无关，可单测） | `src/app/notification.rs` |
| `InterventionType` / `PauseReason→文案映射` | 核心库 | `src/app/notification.rs` |
| `NotificationDedup`（去重 + 软上限淘汰） | 核心库 | `src/app/notification.rs` |
| `App.intervention_notifier` 回调字段 | 核心库 App | `src/app/mod.rs` |
| OS Toast / action 编解码 / AUMID 注册 / notify-rust response | 桌面端桥接 | `src-tauri/src/notifications.rs` |
| `DesktopState.notification_dedup` | 桌面端状态 | `src-tauri/src/state.rs` |
| `PendingInterventionNavigations` | 桌面端可靠导航队列 | `src-tauri/src/notifications.rs` |
| 前端 VM / 订阅 / hook / 卡片 | 前端 | `web/src/...` |

### dedup key

runtime pause 等 attempt 级干预使用 `project:run:round:node:attempt:reason`。ACP permission/elicitation 属于 request 级交互，使用 `project:run:round:node:attempt:kind:request_id`：同一请求的重复 live update 只弹一次，同一 Direct/ACP attempt 内的后续请求可以再次提醒。`projectId` 是跨 workspace 身份的一部分，不能因为 task/run 目录编号看似相同而省略。

### PauseReason → 文案映射（集中在 `InterventionNotification::new`）

| PauseReason | title | InterventionType |
| --- | --- | --- |
| `WaitingForUserInput` | 人工确认 | `manualCheck` |
| `WaitingForUserInput + pending elicitation` | 需要回答问题 | `elicitationRequest` |
| `PermissionRequested` | 权限请求 | `permissionRequest` |
| `ErrorBlocked` | 执行错误 | `errorBlocked` |
| `ProcessInterrupted` | 进程中断 | `errorBlocked` |

`body = {task_label} · {node_label} {body_template}`，`task_title` 缺失时回退 task_id。

## 3. 生命周期与去重

- **配置驱动的短时展示**：`notificationAutoDismissTargetSecs` 表达跨平台产品目标。Windows 在 Default 场景下把目标秒数映射到最近的 Short（约 7 秒）/Long（约 25 秒），20 秒映射为 Long；Linux/BSD 通过 `notify-rust` 传递精确毫秒 timeout，macOS 由系统决定实际时长。自然超时不等价于业务解决。
- **点击后清理**：OS Toast「忽略」/「查看详情」按钮点击时，后端 `handle_toast_action` 清 dedup key（允许同节点再次弹出）；自然超时不清 dedup，避免同一 canonical event 重复弹出。
- **查看详情**：后端先把含必填 `projectId` 的 `ViewActionPayload` 写入待导航队列，再恢复/重建主窗口并 emit 可用信号；前端先监听、再原子 drain 队列后 deep-link 到目标节点。事件可丢失，队列事实不可丢失。
- **无 resolved 事件、无 `resolve_intervention`**——弹窗消失是 OS Toast 动作，无前端卡片。
- `clear_run(projectId, runId)`：run 终态或通知治理需要时只批量清该 project/run 的所有 key（内存治理，防常驻 EXE 泄漏），不得影响其他项目的同名 run；软上限 5000 FIFO 淘汰兜底。

## 4. 接入路径

### 路径 A：编排器 4 个暂停入口（`src/app/orchestrator.rs`）

抽 `emit_intervention_notification` helper，在 4 个分散暂停入口各追加一行调用，**不改控制流**：

| 入口 | 场景 |
| --- | --- |
| A | 节点执行失败暂停（`failed_node`） |
| B | 节点暂停 |
| C | 人工 check 暂停 |
| D | `apply_control_decision` PauseRun |

reason 直接读 `run.pause_reason`。`:6252` 的 Paused 是恢复路径，**不挂接**。

### 路径 B：ACP 旁路监听 `permissionRequest` / `elicitationRequest`（`src-tauri/src/commands.rs`）

`acp_live_update_emitter` 中检测 `kind=="permissionRequest" && status=="pending"` 或 `kind=="elicitationRequest" && status=="pending"`，分别构造 `InterventionRequested(PermissionRequested/ElicitationRequested)`。event id 必须带 `AcpUiEvent.id`；桌面通知 subscriber 直接采用 lifecycle event id 作为 dedup key，不得再次按 attempt+reason 重建并丢失 request identity。node label 优先读取 Direct conversation Agent identity，其次读取节点实际 provider 展示名，缺失时才回退 node id；不改主干 session 逻辑。

2026-07-24 修正：Direct 与节点完成后手动追问会长期复用同一 attempt。旧的 attempt 级 permission/elicitation key 会让首次系统通知之后的所有后续请求被 dedup；现已改为 request-scoped canonical event id，并为连续两次 elicitation 固化回归测试。当前同一 session 前台可见时仍按 attention policy 抑制通知，这属于预期行为。

## 5. OS 系统通知（`src-tauri/src/notifications.rs`）

- `tauri-winrt-notification` 0.7：`Toast::new(AUMID).title().text1().duration(resolve(targetSecs)).scenario(Default).add_button("查看详情", view).add_button("忽略", dismiss).on_activated(...).icon(...).show()`。Windows 原生 API 只提供 Short（约 7 秒）与 Long（约 25 秒）两档，没有精确 20 秒档；解析器按绝对时间差选择最近档位，等距时选择较长档，且禁止使用会持续显示直到手动关闭的 Reminder 场景。
- 配置链路：`configs/app-config.toml` → `ProjectAppConfig.notification_auto_dismiss_target_secs` → `RuntimeConfig.notification_auto_dismiss_target_secs` → lifecycle notification subscriber 注册参数。配置值必须大于 0，非法的 0 回退内置默认 20 秒。
- AUMID = `local.gold-band.desktop`（与 tauri.conf identifier 一致）。`Once` 注册 AUMID + 校验/重建开始菜单 .lnk（TargetPath 不符则重建）。Windows 下注册表写入与快捷方式校验/重建属于后台非交互 helper，必须通过统一 process helper 启动 `reg` / PowerShell 并应用 `CREATE_NO_WINDOW`，避免 Win10 首次通知时闪出终端窗口。
- action 编码：`view:` / `dismiss:` + base64(url_safe_no_pad, json)。
- `on_activated`：view 或正文默认点击 → `route_intervention_navigation`；dismiss → `clear_key`。route 固定执行“入队 → 清 dedup → `ensure_main_window` → emit 可用信号”。
- **图标**：`include_bytes!("../icons/icon.png")` 编译期嵌入码灵图标字节；运行时 `Once` 幂等写入 `app_local_data_dir/maling-toast-icon.png`，`toast.icon(path, Square, "码灵")` 绑定 Toast 左上角。不走运行时 `BaseDirectory::Resource` 解析（dev/prod 落空会导致图标回退默认）。
- macOS/Linux 走 `notify-rust 4.18`（`native-notification` feature），在独立后台线程等待 typed `NotificationResponse`。`Default` 与 `Action("view")` 进入统一 route；其他 action、reply、关闭、忽略和过期只清 dedup，不触发导航。
- Direct 自动待发送队列不把每个成功 turn 都提交给 OS：Direct 首轮成功 `RunCompleted` 只更新运行状态，通知与后续普通/queued prompt 一并进入 600ms 用户优先窗口。`AcpTurnFinished.batchProgress` 携带 `completedReplyCount + continues`；只有确实 claim 到后继时标记 `continues=true` 并由 subscriber 抑制。队列为空、暂停、preempted、claim 失败或已有新 prompt activity 时，终点事件带出完整累计数并清理进程内批次状态；单条显示“回复完成”，多条显示“已连续回复 X 条”。失败立即通知并清理批次，不经过成功合并策略。

## 6. 事件契约

| 事件 | payload | 方向 |
| --- | --- | --- |
| `gold-band://intervention-navigate` | `{projectId, taskId, runId, roundId, nodeId, attemptId, dedupKey}` | OS Toast「查看详情」→ 前端导航 |

该事件从 2026-08-09 起只表示“导航队列可用”，payload 不再承载事实。可靠数据接口为 `take_pending_intervention_navigations() -> Vec<ViewActionPayload>`。

> 应用内右上角弹窗已移除：不再有 `gold-band://intervention-required` 入队事件，不再有 `dismiss_intervention` / `dismiss_intervention_by_fields` 命令。去重清理统一由后端 `handle_toast_action` 在 Toast 按钮点击时完成。

## 7. 前端集成（`web/src/...`）

- `types.ts`：`InterventionNavigateEventVm`（仅导航事件 payload）。
- `api/client.ts` + `desktop.ts` + `browser.ts` + `api.ts`：`subscribeInterventionNavigate` 与 `takePendingInterventionNavigations`。
- `desktop.ts`：先稳定订阅 `gold-band://intervention-navigate`，再 drain 待导航队列；信号回调只串行触发新一轮 drain，避免并发读取和重复导航。
- `lib/use-intervention-notifications.ts`：消费 drain 后的 `ViewActionPayload` 并触发 `onNavigate` deep-link。
- `App.tsx`：按 uiMode 导航——
  - **工作台**：`round-detail` + `roundSelection.node`。
  - **会话**：直接使用 payload 的 `projectId` 定位 `conversation-run`，在 `sessionTree` 内按 `(roundId, nodeId, attemptId)` 匹配叶子（含 outer 字段）后 `switchConversationSession`。禁止再由 sidebar `tasksByWorkspace` 按 taskId 反查项目。

> 应用内右上角堆叠卡片组件 `components/InterventionNotificationQueue.tsx` 已删除。

## 9. 测试记录

| 范围 | 用例 | 结果 |
| --- | --- | --- |
| 核心库 `notification` | project-scoped dedup_key、跨项目相同局部 ID 不碰撞、reason→文案映射、try_send/clear_key/clear_run、软上限淘汰 | ✅ |
| 核心库 `app` | notifier 回调触发 + `clone_for_background` 传播；absent 时静默 | 2 ✅ |
| 桌面 `notifications` | 含 projectId 的 view/dismiss action roundtrip、garbage 安全解码、view/dismiss 区分 | ✅ |
| 核心库 `config` | 通知目标秒数 JSON roundtrip、app-config override、0 值回退默认 20 秒 | 3 ✅ |
| 桌面 `notifications` 展示策略 | 10 秒映射 Short（约 7 秒），20 秒映射 Long（约 25 秒），均使用非持久 Default 场景 | 1 ✅ |
