# 默认轻量工作流实施方案

## 1. 目标

在不削弱现有完整交付链路的前提下，新增一条适合低风险、小范围需求的内置轻量工作流：

```text
拷问 -> 开发测试 -> 验收 -> $end
                    |
                    +-- failure -> 新 Round / 开发测试
```

- 现有内置模板展示名调整为“默认完整工作流”。
- 新增内置模板“默认轻量工作流”。
- 新增“开发测试”内置角色，在同一次节点执行中完成实现、自动化测试和必要回归。
- 轻量工作流的拷问节点可按 workspace 偏好关闭，交互与完整工作流的采访开关一致。
- 完整与轻量工作流的默认控制参数统一为 `max_attempts=10`、`max_rounds=3`；修复跳转与新 Round 次数完全遵循现有 Control DSL，不为轻量工作流增加专用重试规则。

本方案状态：已完成（2026-08-13）。

## 2. 设计判断

### 2.1 根因

当前问题不只是缺少一个模板。现有“需求采访”能力被前后端直接绑定到模板 ID `default` 和字段 `includeInterview`，模板是否内置、是否不可删除、是否存在可选入口阶段也依赖单模板特判。继续为轻量模板增加 `default-lightweight` 特判会让模板、开关、定时任务和会话启动产生第二套分支。

因此本次应先修复模板能力模型：由后端模板元数据声明“内置模板”和“可选入口节点”，前端按元数据展示开关，启动服务按元数据裁剪本次任务的 workflow。采访和拷问只是同一套可选入口机制的两个配置实例。

### 2.2 复用现有能力

- 继续使用现有 `WorkflowDsl`、`success/failure` 条件边、`$new-round`、`new_round_entry` 和 `control.max_rounds`，不新增轻量工作流专用状态机。
- 继续使用现有内置 Profile、ACP elicitation、JSON 输出验证和结构化 workflow control error。
- UI 继续复用 shadcn/ui `Select`、`Switch`、`Tooltip` 与现有 `WorkflowEditor`，不新增自研模板选择器或开关控件。
- 开源依赖已能覆盖画布、表单和状态控件；本需求没有需要新增第三方库的领域能力。

## 3. 数据设计

### 3.1 内置模板身份

| 模板 | 稳定 ID | 是否内置 | 中文展示名 | 英文展示名 |
| --- | --- | --- | --- | --- |
| 完整模板 | `default` | 是 | 默认完整工作流 | Default full workflow |
| 轻量模板 | `default-lightweight` | 是 | 默认轻量工作流 | Default lightweight workflow |

`default` 只修改展示名，不修改稳定 ID，避免破坏任务、运行模式和定时任务中的既有引用。`isBuiltIn` 只表达模板是否由系统管理，不编码完整/轻量类型；模板身份、展示名和拓扑分别由稳定 ID、前端 i18n 和 `workflow` 表达。用户自定义模板仍展示用户输入的名称。

### 3.2 模板元数据

扩展 `WorkflowTemplate`：

```text
isBuiltIn: boolean
optionalEntryStage?: {
  nodeId: string
  labelKey: string
  defaultEnabled: boolean
}
```

约束：

- `isBuiltIn=true` 时模板不可覆盖、不可删除，只能另存；另存后的自定义模板必须写为 `isBuiltIn=false` 并移除 `optionalEntryStage`。
- `optionalEntryStage.nodeId` 必须等于 workflow 当前入口，且只能有一条 `success` 出边；否则模板加载失败并返回结构化错误码。
- `optionalEntryStage.labelKey` 是前端 i18n 语义键，用于区分“需求采访”和“需求拷问”，不代表模板类型。
- 自定义模板必须为 `isBuiltIn=false` 且不得携带 `optionalEntryStage`，其真实拓扑永远不受 workspace 偏好裁剪。
- 模板加载时由后端按稳定 ID upsert 两个内置模板，保留全部自定义模板；不在前端构造默认 workflow。

### 3.3 可选入口偏好

删除只表达采访语义的 `includeInterview`，统一为：

```text
optionalEntryPreferences: Map<templateId, boolean>
```

- 偏好归属 workspace/project 运行模式配置，与模板生命周期分离。
- 首次选择某个内置模板时读取 `defaultEnabled=true`。
- 切换模板时读取该模板自己的偏好；切到自定义模板只隐藏开关，不清空内置模板偏好。
- 会话或任务提交只传当前模板解析后的 `includeOptionalEntry`；定时任务定义冻结该布尔值，执行时不读取后来变化的 workspace 偏好。
- 当前仍处于开发阶段，本次删除旧字段和旧消费路径，不保留双写、fallback 或长期兼容分支；缺少新偏好的已有 workspace 按默认开启处理。

### 3.4 内置“开发测试”角色

新增稳定 Profile ID `pf-builtin-dev-test`，中英文提示词分别位于：

- `src/prompts/zh-CN/profile/dev-test.md`
- `src/prompts/en/profile/dev-test.md`

角色职责：

1. 读取 requirement、拷问共识和上一轮验收失败证据。
2. 先定位根因并实现需求，不接受只针对单一现象的补丁式修复。
3. 实现后执行与改动风险匹配的单元测试、接口测试和必要回归；失败时继续修复，不能把已知失败交给验收节点。
4. 同步维护产品设计文档和开发计划。
5. 产出可供验收读取的实现与测试证据；角色正文不硬编码在 Rust 实现中。

完整工作流继续使用独立的 `pf-builtin-dev` 与 `pf-builtin-test`。新增组合角色只服务轻量模板和用户显式选择，不删除现有角色。

## 4. 工作流定义

### 4.1 默认完整工作流

拓扑保持不变，入口节点的结果判定调整为人工 check：

```text
interview -> plan -> dev -> review -> test -> accept -> cleanup -> $end
```

- 稳定模板 ID 继续为 `default`。
- `optionalEntryStage.nodeId = interview`。
- `interview` 不声明 output contract 或 success condition；Agent 会话自然结束后进入人工 check，只有用户判定成功才继续到 `plan`。
- 只修改展示名为“默认完整工作流 / Default full workflow”。
- `control.max_attempts = 10`、`control.max_rounds = 3`。review/test 的 failure 修复跳转和 accept 的新 Round 继续按现有 Control DSL 计数与限流。

### 4.2 默认轻量工作流

```text
grill -> dev-test -> accept -> $end
                       |
                       +-- failure -> $new-round(new_round_entry=dev-test)
```

配置：

- workflow ID：`task-workflow-lightweight`。
- entry：`grill`。
- `grill` 使用 `pf-builtin-grill`，不声明 output contract 或 success condition；Agent 会话自然结束后进入人工 check，只有用户判定成功才继续到 `dev-test`。
- `dev-test` 使用 `pf-builtin-dev-test`，负责实现和测试。
- `accept` 复用 `pf-builtin-accept` 及现有 `{"reason":"String","result":"boolean"}` 输出约束和 `$.result == true` 成功表达式。
- `accept.success -> $end`。
- `accept.failure -> $new-round`，`new_round_entry=dev-test`，新 Round 使用新 ACP session，并通过现有 hidden runtime context 读取上一轮验收失败产物和附件。
- `control.max_attempts = 10`、`control.max_rounds = 3`，与默认完整工作流一致。当前轻量拓扑没有同一 Round 内指向真实节点的 failure 修复边，因此 `max_attempts` 暂不被消耗，但仍作为统一默认控制配置保留；`max_rounds=3` 允许最多额外打开 3 个 Round，连同初始 Round 最多执行 4 轮。再次请求新 Round 超限时，现有 runtime 以 `workflow_control_limit_exceeded / max_rounds_exceeded` 完成失败。

关闭拷问时只为本次创建的任务移除 `grill` 节点，把 entry 改为其唯一 success 后继 `dev-test`；持久化的内置模板仍保留完整拓扑。

## 5. 接口与状态流转

### 5.1 模板查询

`get_workflow_templates` 返回模板 DSL 与内置元数据。所有入口以同一份 store 为权威来源，前端不根据 ID 猜测是否显示开关或是否允许删除。

### 5.2 启动输入

会话创建、任务创建与定时任务统一使用：

```text
workflowTemplateId: string
includeOptionalEntry?: boolean
```

后端启动流程：

1. 按稳定 ID 解析模板。
2. 校验模板元数据和 workflow 拓扑。
3. 若模板声明可选入口且本次值为 `false`，在内存副本上移除入口节点并重定向 entry。
4. 以变换后的 workflow 创建 task authoring 数据并冻结 run snapshot。
5. 返回最新 canonical task/run；不回写或修改模板本体。

非法元数据或非法裁剪返回稳定错误码及参数，例如 `workflow.optional-entry.invalid`；后端不返回对客文案，前端负责中英文提示。

### 5.3 内置模板更新

模板 store 加载时原子 upsert `default` 与 `default-lightweight`。两者使用稳定 ID 覆盖内置定义；自定义模板、最后使用模板和 workspace 选择保持不变。若最后使用模板已不存在，才回到 `default`。写盘继续使用现有原子 JSON 写入边界。

## 6. UI 交互

- 工作流模板选择器同时展示“默认完整工作流”和“默认轻量工作流”，内置模板的删除操作保持禁用。
- 选择完整模板时展示“需求采访”Switch；选择轻量模板时在同一位置展示“需求拷问”Switch；选择自定义模板时隐藏该行。
- 开关默认开启，使用清晰 label、键盘焦点和 `aria` 语义；不增加解释实现机制的可见文案。
- 运行模式管理页始终展示模板完整真实拓扑；关闭开关只影响后续创建的会话/任务，不改变编辑器画布。
- 模板另存后成为普通自定义模板，不再显示内置入口开关；用户若要移除入口节点，应直接编辑自定义模板拓扑。
- 会话 composer、旧创建任务 Sheet、运行模式管理页共用同一模板显示名与可选入口解析 helper，禁止各自维护 ID 列表。

## 8. 单元测试与接口验收

### 8.1 Rust

- 模板 store 首次创建和已有 store 加载后都恰好包含两个稳定 ID、`isBuiltIn=true` 的内置模板，重复加载不产生副本。
- `default` 保持原稳定 ID 并显示为完整模板；轻量模板包含三个节点和规定的四条边；两者都冻结 `max_attempts=10`、`max_rounds=3`。
- 模板查询接口返回的完整模板 `interview` 与轻量模板 `grill` 均为 `manual_check=true`，并且都不声明 output contract 或 success condition。
- `pf-builtin-dev-test` 在中英文目录结构、ID、名称、摘要和正文映射上完整一致。
- 关闭完整模板采访后从 `plan` 启动；关闭轻量模板拷问后从 `dev-test` 启动；模板原始 DSL 不被修改。
- 自定义模板忽略 `includeOptionalEntry`，不能被偏好裁剪。
- 轻量模板连续验收失败时依次允许打开 3 个新 Round，且每轮都从 `dev-test` 开始；第 4 次请求新 Round 时触发 `max_rounds_exceeded`，run/round 以 failure 完成并发布终态 lifecycle。
- 完整模板的 failure 修复跳转与新 Round 分别受 `max_attempts=10`、`max_rounds=3` 约束，边界内允许继续，下一次超限时产生现有结构化控制错误。
- 定时任务保存解析后的开关值，后续 workspace 偏好变化不改变已保存定义。
- 非法可选入口元数据返回结构化错误码，不泄漏对客文案。

### 8.2 Web

- 两个内置模板使用中英文 i18n 展示名，自定义模板名称保持原样。
- 完整模板、轻量模板、自定义模板分别显示“需求采访”、显示“需求拷问”、隐藏开关。
- 两个内置模板分别记忆开关值；切换自定义模板不会清空偏好。
- 内置模板不可删除/覆盖，另存后的模板可编辑且不再携带可选入口元数据。
- composer、运行模式管理和创建任务入口提交同一 `includeOptionalEntry` 语义。

### 8.3 UI 验证

启动前端后 deep link 到 `/chat` 和 `/chat/run-modes`，分别验证浅色/深色、正常桌面宽度和窄窗口下的模板选择、开关切换、键盘操作、内置模板另存与画布拓扑。验证结束后关闭测试页面并清理本次启动的进程。

## 9. 性能影响

- 模板数量只从一个内置模板增加到两个，store 仍为小型有界列表；加载、校验和选择均为 O(模板数 + 当前 workflow 节点/边数)，无全量任务或运行扫描。
- 可选入口裁剪只在创建任务/会话时对当前 workflow 的内存副本执行一次 O(V+E) 变换，不进入流式事件、React render 或滚动热路径。
- 前端只根据当前模板元数据派生一个 Switch，不扩大 Context 订阅范围，不引入轮询、缓存或额外请求。
- 两个默认模板都由 `max_attempts=10`、`max_rounds=3` 严格限制失败修复与新 Round，队列、ACP session、日志和附件不会因默认模板形成无界增长。
- 无明显性能风险，不需要新增 benchmark；生产构建和接口回归足以验收本次规模。
