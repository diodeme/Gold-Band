# 用户反馈上报实现方案

## 0. 背景

用户需求：
1. wb 渠道新增反馈入口，用户填文字、贴截图，连同日志一起上传到码灵控制台。
2. 异常收集（崩溃自动上传日志）。

经盘问收敛，**本期只做需求 1（主动反馈）**，崩溃自动收集留作扩展位。交互与数据范围见产品设计文档 `产品设计文档/interaction/app/feedback.md`，本文档只描述实现。

## 1. 问题判断

主动反馈和被动崩溃收集触发场景、生命周期、可靠性要求完全不同：
- 反馈：进程健康，用户主动触发，可走同步 command，失败可提示重试。
- 崩溃：进程正在死亡，panic hook 内网络请求大概率失败，需写本地文件 + 下次启动引导。

强行合并会互相拖累。结论：**传输层（endpoint 拼接 + 认证 + multipart 构造）抽成共享函数复用；领域模型、command、状态管理各自独立**。本期 feedback 自成一个模块 `feedback.rs`，崩溃后续另建 `crash.rs`。

## 2. 现有基础设施（代码事实，可直接复用）

| 能力 | 位置 | 复用方式 |
| --- | --- | --- |
| metrics 通道认证 + base_url 解析 | `src-tauri/src/metrics.rs` `metrics_base_url()` / `get_api_key()` / `endpoint_from_base_url()` | 直接调用，拼 `/api/client-report/feedback` |
| 编译期默认 endpoint + api_key | `src-tauri/src/channel.rs` `GOLD_BAND_METRICS_BASE_URL` 等环境变量 | 复用同一套 channel 默认值 |
| 运行日志文件 | `src/storage/mod.rs` `GoldBandPaths::runtime_log_file()` | 读尾部 512KB |
| 会话快照文件 | `src/storage/mod.rs` `GoldBandPaths::acp_session_file()` → `acp.snapshot.json` | 由 session_ref 解析路径后读取 |
| command 注册 + 错误结构 | `src-tauri/src/commands.rs` `CommandResult` / `CommandErrorVm` | 新增 command 沿用同一模式 |
| 前端 API 抽象 | `web/src/api/client.ts` `RuntimeApi` + `web/src/api/desktop.ts` | 新增 `submitFeedback` 方法 |
| 标题栏 | `web/src/components/AppTitleBar.tsx` | 加帮助按钮 + DropdownMenu |

reqwest 当前 features 只有 `json` + `native-tls-vendored`（`src-tauri/Cargo.toml`），**需新增 `multipart`**。

## 3. 设计原则

1. 先定数据，再定接口，再补实现。
2. 传输层共享，领域分离：`feedback.rs` 不塞崩溃逻辑。
3. 错误码用结构体管理，后端只返回 `code`，不含对客文案。
4. 不硬编码 endpoint / 限额：限额用常量统一管理，endpoint 走 channel + config 解析。
5. 文件操作用 `LiteralPath` / 现有 storage 路径 API，不拼接魔法字符串。
6. 前端优先 copy-in shadcn / prompt-kit 组件，不自研基础控件。

## 4. 数据结构（后端）

新建 `src-tauri/src/feedback.rs`：

```rust
// --- 限额常量（统一管理，避免硬编码散落） ---
pub const MAX_DESCRIPTION_CHARS: usize = 2000;
pub const MAX_SCREENSHOTS: usize = 4;
pub const MAX_SCREENSHOT_BYTES: usize = 5 * 1024 * 1024; // 5MB
pub const LOG_TAIL_BYTES: usize = 512 * 1024; // 512KB
pub const FEEDBACK_ENDPOINT_PATH: &str = "/api/client-report/feedback";

// --- 会话定位（可选关联上下文） ---
#[derive(Debug, Clone, Deserialize)]
#[serde(rename_all = "camelCase")]
pub struct SessionRef {
    pub workspace: String,
    pub task_id: String,
    pub session_key: Option<String>,
}

// --- 前端入参 ---
#[derive(Debug, Clone, Deserialize)]
#[serde(rename_all = "camelCase")]
pub struct FeedbackInput {
    pub description: String,
    #[serde(default)]
    pub session_ref: Option<SessionRef>,
    #[serde(default)]
    pub screenshot_paths: Vec<String>, // 已落地的临时文件路径
    #[serde(default = "default_true")]
    pub include_logs: bool,
}

fn default_true() -> bool { true }

// --- 上报结果（返回前端） ---
#[derive(Debug, Clone, Serialize)]
#[serde(rename_all = "camelCase")]
pub struct FeedbackResult {
    pub success: bool,
}
```

错误码沿用项目既有 `CommandErrorVm`（含 `code` 字段），不返回对客文案。feedback 特有 code 见产品设计文档 §7。

## 5. 接口设计

### 5.1 Tauri command

```rust
#[tauri::command]
pub async fn submit_feedback(
    state: State<'_, DesktopState>,
    input: FeedbackInput,
) -> CommandResult<FeedbackResult>
```

职责：
1. 校验：`description` 非空且 ≤ 2000 字符；截图数 ≤ 4、单张 ≤ 5MB、文件存在。
2. 组装诊断包：
   - 元数据 JSON：`client_version`（channel `app_version`）、`reported_at`、`workspace`、可选 `sessionRef`。
   - 日志：`include_logs` 为真时读 `runtime.log` 尾部 512KB（注意 UTF-8 字符边界，从截断点向后找首个非 continuation byte）。
   - 会话快照：`session_ref` 存在时解析 `acp.snapshot.json` 路径并读取。
   - 截图：按路径读取文件。
3. 解析 endpoint：复用 `metrics_base_url(&config)` + `FEEDBACK_ENDPOINT_PATH`；api_key 复用 `get_api_key(&config)`。
4. reqwest multipart POST：`multipart::Form::new().text("metadata", json).part("log", ...).part("screenshot_0", ...)...`，header `X-Maling-Report-Key`。
5. 成功返回 `FeedbackResult { success: true }`；失败按错误码返回 `CommandErrorVm`。

### 5.2 前端 API

`web/src/api/client.ts` 的 `RuntimeApi` 新增：

```ts
submitFeedback(input: FeedbackInput): Promise<FeedbackResult>;
```

`web/src/api/desktop.ts` 实现转发到 `invoke('submit_feedback', { input })`；`browserApi` 给一个返回 `feedback.endpoint-unconfigured` 的桩，保持 web 兜底一致。

## 6. 码灵控制台 endpoint 契约（交付给后端）

``+POST /api/client-report/feedback
Content-Type: multipart/form-data
X-Maling-Report-Key: <api_key>

Parts:
  metadata        (application/json)  必填  FeedbackMetadata
  log             (text/plain)        可选  运行日志尾部 512KB
  session_snapshot(application/json)  可选  acp.snapshot.json 内容
  screenshot_0..n (image/*)           可选  截图文件，最多 4 个

FeedbackMetadata:
  client_version: string
  reported_at:    string   // ISO-8601
  workspace:      string
  session_ref?:   { workspace, task_id, session_key? }
  log_attached:   boolean
  screenshot_count: number

Response 200:
  { "reportId": "..." }

Response >=400: 服务端返回任意错误，客户端统一映射为 feedback.server-error。
```

认证复用现有 `X-Maling-Report-Key`（与 heartbeat / node-metrics 一致）。服务端当前尚未实现，文档先行；客户端实现时对「endpoint 返回 404/连接拒绝」归类为 `feedback.server-error`，不崩溃。

## 7. 实现步骤

1. `src-tauri/Cargo.toml`：reqwest features 加 `multipart`。
2. 新建 `src-tauri/src/feedback.rs`：常量 + 数据结构 + `submit_feedback` command + multipart 上报函数（复用 metrics 的 base_url / api_key 解析，独立于 heartbeat 逻辑）。
3. `src-tauri/src/main.rs`：`mod feedback;`、invoke_handler 注册 `submit_feedback`。
4. `web/src/api/client.ts` + `desktop.ts` + `browserApi`：新增 `submitFeedback`。
5. `web/src/types.ts`：新增 `FeedbackInput` / `FeedbackResult` / `SessionRef` 类型。
6. `web/src/components/AppTitleBar.tsx`：最小化按钮左侧加帮助按钮（`DropdownMenu`，含「用户反馈」项，`MessageSquareWarning` 图标）。
7. 新建 `web/src/components/feedback/FeedbackDialog.tsx`：Dialog + Textarea + 会话 Select + 截图粘贴/选择 + 日志 Switch + 知情提示 + 同步提交 + loading + 错误 toast。i18n 文案走 `web/src/i18n.ts`。
8. 截图落地为临时文件：复用现有 attachment 落盘流程（`web/src/lib/attachment-service.ts`），把临时路径传给后端。
9. 单元测试（见 §8）。
10. 同步两份文档（见 §9）。

## 8. 测试

从接口层面固化验收，便于后续回归：
- `feedback.rs`：
  - `FeedbackInput` 校验：空描述拒绝、超长描述拒绝、截图超数量拒绝、单张超 5MB 拒绝、路径不存在拒绝。
  - 日志尾部截取：构造 > 512KB 日志，断言截取后 ≤ 512KB 且为合法 UTF-8。
  - multipart 构造：mock endpoint，断言 form 含 metadata / log / screenshot 各 part，header 含 `X-Maling-Report-Key`。
  - endpoint 缺失场景：base_url 与 channel 默认都为空时返回 `feedback.endpoint-unconfigured`。
- 前端：FeedbackDialog 字段校验、loading 状态、错误码 → 文案映射。
