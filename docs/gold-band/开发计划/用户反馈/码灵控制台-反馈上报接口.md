# 码灵控制台反馈上报接口

本文档描述 Gold Band 桌面端向码灵控制台提交主动反馈的 HTTP 契约。客户端实现位于 `src-tauri/src/feedback.rs`。

## 1. Endpoint

| 项 | 值 |
| --- | --- |
| 方法 | `POST` |
| 路径 | `/api/client-report/feedback` |
| 完整地址 | `{metrics_base_url}/api/client-report/feedback` |
| Content-Type | `multipart/form-data` |
| 认证 | 可选 header `X-Maling-Report-Key` |
| 客户端连接超时 | 10 秒 |
| 客户端请求总超时 | 60 秒 |

认证与 heartbeat、node-metrics 使用同一个渠道配置。服务端应对请求体和各 part 独立设置限制，不能只依赖客户端校验。

---

## 2. Multipart parts

| name | 类型 | 必须 | 说明 |
| --- | --- | --- | --- |
| `metadata` | text | 是 | UTF-8 JSON |
| `description` | text | 是 | 用户描述，1–2000 字符 |
| `log` | `text/plain` file | 否 | `runtime.log` 尾部，最多 512 KiB |
| `session_archive` | `application/zip` file | 否 | 关联任务目录归档，文件名 `task.zip` |
| `screenshot_0..n` | `image/png` file | 否 | 规范化 PNG，最多 4 张 |

客户端按 `metadata → description → log → session_archive → screenshot_0..n` 构造，但服务端必须按 part name 解析，不依赖顺序。

`description` 始终作为独立 text part 上传；旧文档中“description 不在 multipart”的描述已废弃。

截图在前端 command 输入中使用 base64 只是 WebView IPC 表达；进入 HTTP multipart 前已解码、验证并重新编码为 PNG，HTTP body 中是二进制图片，不是 base64 文本，也不是本地路径。

---

## 3. Metadata

示例：

```json
{
  "userId": "alice",
  "clientVersion": "0.9.0",
  "reportedAt": "2026-07-30T16:30:00",
  "sessionProjectId": "d--projects--gold-band",
  "sessionTaskId": "task-015",
  "logAttached": true,
  "archiveAttached": true,
  "archiveBytes": 6144,
  "archiveUncompressedBytes": 12288,
  "archiveFileCount": 38,
  "screenshotCount": 1
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `userId` | string | 与 metrics 同源的系统用户标识 |
| `clientVersion` | string | 桌面客户端版本 |
| `reportedAt` | string | 客户端本地时间 |
| `sessionProjectId` | string \| null | 关联会话的 Gold Band project id |
| `sessionTaskId` | string \| null | 关联任务 id |
| `logAttached` | boolean | 是否包含 `log` |
| `archiveAttached` | boolean | 是否包含 `session_archive` |
| `archiveBytes` | number | ZIP 压缩后字节数 |
| `archiveUncompressedBytes` | number | 归档文件的未压缩总字节数 |
| `archiveFileCount` | number | 归档文件数量 |
| `screenshotCount` | number | 截图 part 数量 |

`sessionProjectId` 与 `sessionTaskId` 同时有值或同时为 null。客户端不再上传 workspace 绝对路径，控制台不得依赖本地文件路径定位会话。

## 4. 客户端资源策略

| 项 | 客户端上限 |
| --- | ---: |
| 描述 | 2000 字符 |
| 截图数量 | 4 |
| 单张截图输入/规范化输出 | 5 MiB |
| 截图尺寸 | 最大 8192×8192 |
| 任务归档未压缩大小 | 100 MiB |
| 任务归档压缩后大小 | 20 MiB |
| 任务归档文件数 | 5000 |
| 日志 | 512 KiB |
| 单次有效载荷 | 30 MiB |

服务端建议把 multipart 请求总上限设为不低于客户端 30 MiB 有效载荷加 boundary/header 开销，并分别限制文件数量、单 part 大小、ZIP 解压总量和解压文件数量。

`session_archive` 的客户端生成规则：

- 只归档后端通过 project/task 标识解析出的 canonical task 目录。
- 不跟随符号链接。
- ZIP entry 使用相对路径和 `/` 分隔符。
- 客户端以临时文件流式发送，不保证可重放同一个 HTTP body。

---

## 5. 响应

任意 `2xx` 视为成功。当前客户端不消费响应 body；控制台可返回：

```json
{ "reportId": "feedback-20260730-001" }
```

任意非 `2xx` 在客户端映射为 `feedback.server-error`，并可带数字 `status` 参数。连接、DNS 或超时映射为 `feedback.network-failed`。客户端不会把网络库原始错误字符串展示给用户或放入 command 响应。

客户端本地错误还包括：

| code | 含义 |
| --- | --- |
| `feedback.disabled` | 渠道未启用反馈 |
| `feedback.endpoint-unconfigured` | base URL 缺失 |
| `feedback.validation-failed` | 基础字段无效 |
| `feedback.session-not-found` | project/task 无法解析 |
| `feedback.attachment-invalid` | 截图无效 |
| `feedback.payload-too-large` | 资源策略超限 |

---

## 6. 服务端验收建议

1. 无附件请求能读取 `metadata` 和 `description`。
2. 同时包含 log、ZIP、4 张 PNG 时按 name 正确解析。
3. 验证 `X-Maling-Report-Key` 的缺失、错误和正确场景。
4. 对超过服务端请求、文件、ZIP 解压限制的请求快速拒绝。
5. 文件存储使用服务端生成的 ID/路径，不信任 multipart filename。
6. ZIP 后续解压时继续阻止 `..`、绝对路径、symlink 和解压炸弹。
7. 日志中不要记录 description、截图内容或 ZIP 内容；只记录 report id、大小、计数和状态。
