# 用户反馈上报接口（码灵控制台对接）

> 本文档面向码灵控制台后端团队，描述 Gold Band 桌面端「用户反馈」功能向控制台上报反馈数据的 HTTP 接口契约。客户端实现已完成（`src-tauri/src/feedback.rs`），接口尚未在控制台落地，本文档先行交付。
>
> 关联文档：
> - 产品设计：`docs/gold-band/产品设计文档/interaction/app/feedback.md`
> - 客户端实现方案：`docs/gold-band/开发计划/用户反馈/用户反馈上报方案.md`

## 1. 背景

Gold Band 桌面端顶栏「帮助 → 用户反馈」让用户一键把**问题描述 + 截图 + 运行日志 + 会话快照**上报到码灵控制台，用于问题定位与产品改进。

- 仅**主动反馈**：用户手动触发，不做崩溃自动收集（本期不做）。
- 复用现有 metrics 通道的认证与 base_url 机制，与 heartbeat / node-metrics 共用同一套 `X-Maling-Report-Key` 与 `metrics_base_url`，**不新建网络层、不新增配置项**。

## 2. 接口概览

| 项 | 值 |
| --- | --- |
| 方法 | `POST` |
| 路径 | `/api/client-report/feedback` |
| 完整 URL | `{metrics_base_url}/api/client-report/feedback` |
| Content-Type | `multipart/form-data` |
| 认证 | `X-Maling-Report-Key: <api_key>`（与 heartbeat / node-metrics 同一 key） |
| 请求体 | multipart，含 1 个 JSON 元数据 part + 可选的日志 / 会话快照 / 截图 part |
| 成功响应 | `200`，建议返回 `{ "reportId": "<string>" }`（reportId 可选，客户端当前不消费） |
| 失败响应 | 任意 `>= 400`，客户端统一归类为 `feedback.server-error` |

> 说明：客户端**只看 HTTP 状态码**判断成败（2xx 成功，其余失败）。响应体目前不被解析；建议返回 `reportId` 以便后续「工单追踪」扩展位接入。

## 3. 鉴权

复用现有 metrics 通道的共享密钥：

```
X-Maling-Report-Key: <api_key>
```

- `api_key` 由渠道配置（`channel.rs`）或用户设置中的 `desktop_metrics_api_key` 提供，与 heartbeat、node-metrics 上报**完全一致**。
- 控制台侧的 key 校验逻辑应与 heartbeat / node-metrics 共用同一中间件，避免三套校验。

## 4. 请求体：multipart 结构

`Content-Type: multipart/form-data; boundary=...`，包含以下 part：

| Part 名 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `metadata` | `application/json`（以 text part 传输） | 是 | 反馈元数据，JSON 文本，结构见 §5 |
| `description` | `text/plain` | 是 | 用户填写的问题描述，1–2000 字符，UTF-8 纯文本 |
| `log` | `text/plain` | 否 | 运行日志尾部，最多 512KB，UTF-8 |
| `session_snapshot` | `application/json` | 否 | 关联会话的 `acp.snapshot.json` 内容 |
| `screenshot_0` ... `screenshot_n` | `image/png` | 否 | 用户截图，最多 4 张，单张 ≤ 5MB |

字段语义：

- `metadata`：**总是存在**。即使用户关掉日志、没选会话、没附截图，`metadata` 也会携带 `logAttached=false`、`screenshotCount=0` 等标记。
- `log`：仅当用户开启「同时上传运行日志」（默认开）且日志文件存在时才附带。内容为 `runtime.log` 的**尾部 512KB**，按字节截断并保证 UTF-8 字符边界完整。
- `session_snapshot`：仅当用户选择了「关联会话」时才附带。内容是该会话目录下最新的 `acp.snapshot.json` 原文件内容（结构化会话状态摘要）。
- `screenshot_i`：仅当用户附加了截图时才附带，`i` 从 `0` 起递增。`metadata.screenshotCount` 给出实际张数。

### 4.1 实际请求样例

一个带描述 + 日志 + 1 张截图 + 关联会话快照的完整请求（boundary 由 reqwest 随机生成，此处用 `----xYz` 占位）：

```http
POST /api/client-report/feedback HTTP/1.1
Host: maling.example.com
X-Maling-Report-Key: <api_key>
Content-Type: multipart/form-data; boundary=----xYz

------xYz
Content-Disposition: form-data; name="metadata"

{"clientVersion":"0.9.0","reportedAt":"2026-07-24T15:30:00","workspace":"D:\\IdeaProjects\\Gold-Band","sessionRef":{"workspace":"D:\\IdeaProjects\\Gold-Band","taskId":"task-015"},"logAttached":true,"screenshotCount":1}
------xYz
Content-Disposition: form-data; name="description"

界面卡住了
------xYz
Content-Disposition: form-data; name="log"; filename="runtime.log"
Content-Type: text/plain

<runtime.log 尾部 512KB 的原始字节，未做 base64>
------xYz
Content-Disposition: form-data; name="session_snapshot"; filename="acp.snapshot.json"
Content-Type: application/json

<acp.snapshot.json 原文件字节>
------xYz
Content-Disposition: form-data; name="screenshot_0"; filename="screenshot_0.png"
Content-Type: image/png

<PNG 二进制原始字节>
------xYz--
```

要点：

- **字节原样进 body**：日志、会话快照、截图都是原始字节流，**不再做 base64 编码**。multipart 本身二进制安全，控制台用任意 multipart 解析库（Node `multer` / Java `commons-fileupload` / Python `multipart`）按 `name` 取 part 即可。
- **文件名是序号名**：截图 part 的 `filename` 是 `screenshot_0.png`、`screenshot_1.png`…**不是用户本地原始文件名**（前端落地时用序号命名，原始文件名未上送）。
- **文本 part 无 `filename` / `Content-Type`**：`metadata` 与 `description` 是纯文本 part，只有 `name`，没有 `filename` 和单独的 `Content-Type`。
- **part 顺序**：`metadata` → `description` 恒在前，随后按需追加 `log` → `session_snapshot` → `screenshot_0..n`。顺序不参与解析，控制台按 `name` 匹配即可。

## 5. `metadata` 结构

`metadata` part 是一段 JSON 文本，字段如下（`camelCase`）：

```json
{
  "clientVersion": "0.9.0",
  "reportedAt": "2026-07-24T15:30:00",
  "workspace": "D:\\IdeaProjects\\Gold-Band",
  "sessionRef": {
    "workspace": "D:\\IdeaProjects\\Gold-Band",
    "taskId": "task-015"
  },
  "logAttached": true,
  "screenshotCount": 2
}
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `clientVersion` | string | 是 | 客户端版本号（来自 Tauri `package_info().version`，如 `0.9.0`） |
| `reportedAt` | string | 是 | 反馈提交的本地时间，格式 `yyyy-MM-ddTHH:mm:ss`（**注意：本地时间，无时区后缀**）。控制台落库时建议按服务器接收时间或统一时区处理 |
| `workspace` | string | 是 | 当前工作空间的绝对路径（本地路径，可能含敏感信息） |
| `sessionRef` | object \| null | 否 | 关联的会话引用，结构见下；未关联会话时为 `null` 或缺省 |
| `logAttached` | boolean | 是 | 是否附带了 `log` part |
| `screenshotCount` | number | 是 | 附带的截图数量（对应 `screenshot_0..n` 的数量） |

`sessionRef` 子结构：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `workspace` | string | 是 | 会话所属工作空间绝对路径 |
| `taskId` | string | 是 | 会话对应的任务 id（如 `task-015`） |

> 注：客户端数据结构 `SessionRef` 当前仅含 `workspace` + `taskId` 两个字段（见 `feedback.rs`）。产品设计文档里提到的 `sessionKey` 为预留扩展，当前版本**不上送**。

## 6. 限额与校验

客户端在提交前已做以下校验，控制台侧建议做相同校验以防御异常客户端：

| 项 | 限额 | 客户端校验位置 |
| --- | --- | --- |
| 问题描述长度 | 1 – 2000 字符（按 Unicode 字符计数） | `validate_input()` |
| 截图数量 | ≤ 4 张 | `validate_input()` |
| 单张截图大小 | ≤ 5 MB（5 \* 1024 \* 1024 字节） | `validate_input()` |
| 日志尾部大小 | ≤ 512 KB（512 \* 1024 字节） | `read_log_tail()` |

> 问题描述字段当前**不在 multipart 中传输**，仅作为元数据的一部分。控制台若需要展示用户描述，应从 `metadata` 之外获取——见 §10 待澄清项。截图路径在客户端为本地临时文件，已读取为 bytes 上传，控制台拿到的是文件内容而非路径。

## 7. 成功响应

```
HTTP/1.1 200 OK
Content-Type: application/json

{
  "reportId": "fb_2026_07_24_a1b2c3d4"
}
```

- 状态码 `2xx` 即视为成功。
- `reportId` **当前可选**：客户端不解析响应体、不展示给用户（MVP 成功后只 toast「反馈已提交，感谢」）。但建议返回，作为后续「工单追踪 / 控制台查询页」扩展位的预留。
- 若控制台暂时无法生成 reportId，返回空对象 `{}` 或任意 2xx 即可，不要因此返回非 2xx。

## 8. 失败响应

客户端不区分服务端错误类型，统一归类：

| 客户端错误码 | 触发条件 | 控制台对应场景 |
| --- | --- | --- |
| `feedback.server-error` | HTTP 状态码 ≥ 400（非网络错误） | 控制台返回 4xx / 5xx、key 校验失败、内部异常等 |
| `feedback.network-failed` | 网络层失败（连接拒绝、DNS、超时） | 控制台不可达 |
| `feedback.endpoint-unconfigured` | `metrics_base_url` 未配置 | （控制台无关，客户端极端兜底） |

控制台失败响应**无需遵循特定结构**，客户端只看状态码。建议返回便于排查的 JSON：

```
HTTP/1.1 400 Bad Request
Content-Type: application/json

{ "error": "invalid_metadata", "message": "metadata.clientVersion is required" }
```

## 9. 与现有上报通道的关系

控制台已有两个来自 Gold Band 的上报端点，三者共用 `{metrics_base_url}` 前缀与 `X-Maling-Report-Key`：

| 端点 | 方法 | 用途 | Content-Type |
| --- | --- | --- | --- |
| `/api/client-report/heartbeat` | POST | 客户端心跳（user_id / workspace / version） | `application/json` |
| `/api/client-report/metrics/batch` | POST | 节点执行指标批量上报 | `application/json` |
| **`/api/client-report/feedback`** | POST | **用户反馈（本接口）** | **`multipart/form-data`** |

`metrics_base_url` 是服务根地址（如 `https://maling.example.com`），客户端通过 `endpoint_from_base_url(base, "/api/client-report/feedback")` 拼接完整 URL。base_url 的归一化会自动剥离已知后缀路径与末尾斜杠。

## 10. 待澄清 / 后续协作项

1. **用户描述（description）已作为独立 description text part 上传**（早期版本曾遗漏，现已修复，并有回归测试 eedback_parts_always_include_description_and_metadata 守护）。控制台读取该 part 即可获得用户填写的问题描述。
2. **`reportedAt` 时区**：客户端发送的是本地时间无时区后缀。控制台落库建议统一转 UTC 或带时区存储，避免跨时区错乱。
3. **reportId 是否需要回传客户端**：当前不需要。若未来要做「工单追踪」，客户端需要展示 reportId 时再调整。
4. **敏感信息**：日志与会话快照几乎一定含本地路径、代码片段，**客户端不做自动脱敏**（产品决策，避免虚假安全感）。控制台侧存储与展示需自行评估合规与访问控制。
5. **大小限制的服务端兜底**：客户端已做限额，但建议控制台对单次请求总大小设上限（如 30MB），防御异常或恶意客户端。
