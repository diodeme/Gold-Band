# Static Website Delivery

The website, recording source and read-only Demo are separate Vite entries. This configuration is a local static hosting reference, not a public deployment declaration. A public host, HTTPS termination, deployment access and approved complete history data are still required. Do not expose an incomplete candidate or source recordings.

## Build And Develop

The root .env.local can set DEMO_DATASET_PATH to the existing exported dataset. Both Demo development and production builds read this setting. Development serves files on demand at /data/ji-history/; production copies the verified publication inventory, including task.json and workflow snapshots, into the bundled Demo directory. Raw task directories must first pass through the existing export pipeline. The local dataset currently has 1610 missing source references, so complete production validation still fails until those sources are supplied.

Use the repository lockfile (`npm ci`) and Node 22.18+ (recording scripts import TypeScript). Run commands from the repository root. The website is `marketing/site`, recording source is `marketing/recording`, and Demo is `marketing/demo`. Copy and API boundaries remain in the existing source files:

- Website copy/style/config: `marketing/site/content.ts`, `style.css`, `config.ts`.
- Official rrweb replay, scene models and canonical media: `marketing/site/` and `marketing/site/media/{before,workflow,after,personalize}`.
- Recording actions/cameras: `scripts/*-source-storyboard.mjs`, `workflow-camera.mjs`, `record-workflow.mjs`, `record-site.mjs`.
- Shared client UI: `web/src`; read-only injection: `marketing/demo/runtime.ts`, `api.ts`, `dataset.ts`; fixtures: `marketing/shared/fixture.ts`.

```powershell
npm run site:dev
# Separate terminal, only when needed:
npm run demo:dev
```

## Static Hosting

Use official Caddy 2 (verified locally with 2.11.4). No npm runtime dependency or custom HTTP server is needed. Set both mount values **without** the trailing slash and use two disjoint, non-root mounts. Dist paths must point only to completed build outputs. Do not point them to a repository, runtime directory, recording output or raw export directory.

```powershell
$env:SITE_MOUNT='/product'
$env:DEMO_MOUNT='/nested/demo'
$env:SITE_DIST=(Resolve-Path '.codex-temp/site-dist').Path
$env:DEMO_DIST='C:/delivery/demo-dist'
$env:PREVIEW_ADDRESS='http://127.0.0.1:15671'
caddy validate --config marketing/deployment/Caddyfile --adapter caddyfile
caddy run --config marketing/deployment/Caddyfile --adapter caddyfile
```

Stop with Ctrl+C and close verification tabs afterward. `site:preview` and `demo:preview` are also available for individual build inspection; Vite preview is not the production hosting configuration.

Caddy redirects mount roots with 308, strips each prefix to its own output root, falls back to index only for navigation, and returns 404 for missing assets/data. Unmounted paths return 404. Gzip is negotiated using `Accept-Encoding`; already-compressed archive files remain downloadable bytes. Vite fingerprint assets have one-year immutable caching. HTML, manifests, scene recordings, posters, history and public assets without fingerprints use `no-cache` revalidation. No directory listing or desktop backend is enabled.

For public hosting, use an approved HTTPS frontend terminating TLS in front of this configuration, or adapt the Caddy address/TLS settings with the host operator. The supplied configuration intentionally disables automatic HTTPS for loopback testing. A local HTTP response does not verify DNS, certificates, CDN rules, upload permissions or public reachability.

## Updates And Regression

1. Rebuild Demo after shared `web/src`, runtime adapter, locale, prompt or public-resource changes. Run Demo interface tests with `DEMO_DATASET_PATH` set, plus recording factory/identity boundary tests, then `demo:build` with the completeness exception absent. Run `site:test`, website/recording builds when their shared dependencies change.
2. Export history only when its authorized source changes. Verify the entire dataset and Raw reports offline, including privacy, missing references, published file count and hashes. Keep the manifest, dataset, publish-index and all referenced resources together.
3. Prepare a new immutable release directory. For updates involving un-fingerprinted scene/data resources, use new versioned URL prefixes (for example `/releases/<release-id>/product/` and `/releases/<release-id>/demo/`) and rebuild both bases and the Demo URL. Configure the old release routes alongside the new ones for open tabs; switch the public entry only after the complete new release is verified. Do not overwrite individual files in a live release. Roll back the entry to the previous intact release when necessary.
4. On the target host verify navigation, language/theme, four replays, 390px layout, real Download click, independent Demo hash deep link and refresh, Logo/fonts/nested resources, manifest hash, gzip, fingerprint cache and missing-resource 404. Verify no requests to desktop IPC, Agent/MCP/Git execution services or recording entries.
5. Archive commit and config hashes, build logs, source/dataset manifests, asset verification, interface results, screenshots and inherited motion/visual review references. Run the HTTP contract in `scripts/static-hosting.test.mjs` with `STATIC_PREVIEW_URL` set to the mounted host origin. Installer downloads need actual bytes and matching release digest; installation/EXE execution is a separate validation level.

The full visual matrix and second-scene semantic acceptance may be inherited only while the associated code/assets remain unchanged. Hosting configuration changes require focused independent acceptance. Complete history and public deployment remain explicit delivery conditions.
