## 開発・テスト自動コミット

要件実装と必要な自動テスト完了後、ノード終了前にこの締め処理を実行する。

1. `memory_read` を使用してタスクスコープの `storyId` と `storyName` を確認する。どちらも空でない場合は両方を再利用する。いずれかが欠落、空、またはペアになっていない場合、まず `storyId=0` と要件名抽出ルールでアイデンティティを生成し `memory_write` を試行する。存在しない key には `operation="create"` を使用し `expectedRevision` を省略する。既存 key には `operation="update"` とその revision を使用する。ツールが利用不可または読み取り失敗の場合、アイデンティティが読み取れなかったことを述べる。書き込みまたは検証失敗の場合、永続化されなかったことを述べる。いずれも BLOCKER ではない：ユーザーに要件アイデンティティを尋ねるか、本 run で確認されたアイデンティティで続行する。
2. 本ノードが生成したタスク関連変更を特定する。コード、テスト、プロンプト、製品設計ドキュメント、開発計画を含む。実行前から存在していた変更、または明らかに無関係なユーザー変更は除外する。
3. タスク関連変更がない場合、空コミットを作成しない。「コミット不要」、根拠、および含めなかった未コミット変更を記録する。
4. 実際のタスク関連 diff から標準 Conventional Commits タイプ token と簡潔な日本語説明を選択する。実行履歴、モデル名、汎用文ではなく、提供結果に焦点を当てる。
5. 特定パスのみで `git add` を実行する。`git add -A` を使用せず、無関係な変更を含めない。ノード実行成功後に 1 つの論理コミットを作成する。
6. コミットメッセージは正確に 3 行であること：

```text
--story=[{storyId}] {storyName}
{type}: {中文描述}
#AI COMMIT#
```

7. コミット後、コミット OID、完全なコミットメッセージ、タスク関連パス状態を検証する。コミットまたは検証失敗時にノード完了を宣言してはならない。
8. 開発・テストレポートにコミット OID、3 行メッセージ、含めたパス、除外パス、理由を記録する。CICD はこれらのコミット OID を使用して、本タスクに未 push コミットがあるか判断する。
9. ユーザーにコミットメッセージまたは形式の確認を求めない。既存 ACP コマンド権限ルールは有効のまま。自動コミットのために権限境界を迂回してはならない。
10. コミット失敗時は元のエラーと現在の Git 状態を保持し、既存のノード失敗、手動回復、または acceptance 失敗パスに委ねる。代替コミットを作成したり、コミット履歴を書き換えたりしてはならない。
