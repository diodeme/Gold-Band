## 要件アイデンティティ事前チェック

トポロジ列挙、Interview Round 0、または Grill ブランチ列挙の前に本セクションを実行する。本セクション開始時にまず `memory_read` を呼び出し、その後アイデンティティチェックを行う。

1. `memory_read` を使用して現在のタスクとワークスペース記憶を読み取る。返却スナップショットの `task` エントリのみを確認する。ワークスペースの `storyId` または `storyName` は現在タスクの既存アイデンティティとしてカウントしない。
2. タスクに `storyId` と `storyName` の両方が存在し、trim 後にどちらも空でない場合のみ、元のロール Workflow を続行する。
3. いずれかの key が欠落、空、またはペアになっていない場合、まず要件アイデンティティについて正確に 1 つの質問をする。必須の意味選択肢は次のとおり：
   - `不存在`
   - `其他（用户自行输入）`
4. `AskUserQuestion` または同等の elicitation ツールが利用可能な場合はそれを使用する。そうでない場合はプレーンテキストで質問を出力するが、同じ 2 つの意味選択肢を保持する。この質問はトポロジステップ、曖昧性ラウンド、Interview ラウンド、または Grill ブランチではない。ユーザーが回答した後、元の Workflow を続行する。
5. ユーザーが `不存在` を選択した場合：
   - `storyId` を文字列 `0` に設定する。
   - 要件から短い `storyName` を抽出する：明示的なタイトルまたは先頭行要約を優先し、次に目標の核心名詞句を使用し、抽出が不可能な場合のみ `系统需求` を使用する。
   - テンプレートラベル、ステータス注記、Markdown マーカー、無関係な句読点を除去する。最大 40 Unicode 文字の 1 行で保存する。
6. ユーザーが `其他（用户自行输入）` を選択した場合、要件 ID と要件名の両方を取得する。自由テキストを 2 つの値に明確に分割できない場合、もう 1 回質問する。依然として不明な場合は推測せず、明確化を待つ。両方の値を trim し、それぞれ 1 行として保存する。
7. `memory_write` を使用して両方のエントリをタスクスコープに書き込む。書き込み前に、最新の `memory_read` から対象 key の revision を使用する：key が存在しない場合は `operation="create"` を使用し `expectedRevision` を省略する。既存 key を修正する場合は `operation="update"` と一致する revision を使用する。これらの key をワークスペーススコープに書き込んではならない。
8. 両方の書き込み後、再度 `memory_read` を呼び出し、タスクスコープの `storyId` と `storyName` がユーザー確認値と完全に一致することを確認する。
9. `gold-band-memory` が利用不可または読み取り失敗の場合、要件アイデンティティが読み取れなかったことを述べ、ステップ 3 に従って通常どおり質問する。書き込みまたは書き込み後検証が失敗した場合、要件アイデンティティが永続化されなかったことを述べる。いずれも BLOCKER ではない。ユーザー確認済みまたは新たに提供された `storyId` と `storyName` で続行する。後続ノードが再度質問する場合がある。
10. メモリファイルを直接編集してはならない。アイデンティティ取得後、Interview 初期化または Grill 決定木列挙を続行する。ツール書き込みが成功した場合はタスクスコープのコピーを保持する。
