## 開發測試自動提交

完成需求實作和必要自動化測試後，在節點結束前執行本節收尾。

1. 使用 `memory_read` 檢查任務作用域中的 `storyId` 和 `storyName`。兩者已有非空值時直接使用；缺失、為空或不成對時，優先按 `storyId=0` 和需求身份提取規則產生名稱並嘗試 `memory_write`。不存在 key 使用 `operation="create"` 並省略 `expectedRevision`；已有 key 使用 `operation="update"` 並傳入對應 revision。工具不可用或讀取失敗時說明身份未讀取；寫入或核驗失敗時說明未持久化。二者都不是阻塞：可向使用者詢問需求身份，或使用本輪已確認身份繼續提交。
2. 識別本次節點實際產生的任務相關改動，包括程式碼、測試、提示詞、產品設計文件和開發計畫；排除執行前已存在或明顯無關的使用者改動。
3. 若沒有本次任務相關改動，不建立空提交。記錄「無需提交」、判斷依據和仍保留的未納入改動。
4. 根據任務相關差異選擇標準 Conventional Commits 類型 token 和簡短中文描述。描述聚焦功能結果，不寫執行過程、模型名稱或泛化說明。
5. 僅按具體路徑執行 `git add`，禁止 `git add -A`，不得納入無關改動。每次節點成功執行產生一次邏輯提交。
6. 提交訊息嚴格為三行：

```text
--story=[{storyId}] {storyName}
{type}: {中文描述}
#AI COMMIT#
```

7. 提交後核驗 commit OID、完整提交訊息和任務相關路徑狀態；不得在提交失敗或核驗失敗時宣告節點完成。
8. 在開發測試報告中記錄 commit OID、三行提交訊息、納入路徑、未納入路徑及原因。CI/CD 將使用這些提交 OID 判斷本次任務是否存在未推送提交。
9. 提交過程不向使用者詢問提交訊息或確認格式。現有 ACP 命令權限規則不變，不得為了自動提交繞過權限邊界。
10. 提交失敗時保留原始錯誤和目前 Git 狀態，交給現有節點失敗、人工恢復或驗收失敗路徑處理，不建立替代提交，不修改提交歷史。
