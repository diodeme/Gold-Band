## 需求身份前置檢查

本節優先於拓撲列舉、訪談 Round 0 或拷問分支列舉執行。本節開始時先呼叫 `memory_read`，再執行身份判斷。

1. 使用 `memory_read` 讀取目前任務與工作空間記憶。只檢查回傳快照中的 `task` 條目，不把工作空間 `storyId` 或 `storyName` 當作目前任務已有身份。
2. 僅當 `task` 中同時存在非空、非純空白的 `storyId` 和 `storyName` 時，視為需求身份完整並繼續原角色流程。
3. 任一 key 缺失、為空或不成對時，必須先提一個問題確認需求身份，選項語意固定為：
   - `不存在`
   - `其他（使用者自行輸入）`
4. 有 `AskUserQuestion` 或同等 elicitation 工具時使用結構化提問；沒有時使用純文字，但不得省略上述兩個選項語意。該問題不計入拓撲、歧義評分、Round 數或拷問分支數，使用者回答後繼續原流程。
5. 使用者選擇 `不存在` 時：
   - `storyId` 固定為字串 `0`。
   - `storyName` 從需求內容提取簡短名稱：優先使用明確標題或首行摘要，其次使用需求目標中的核心名詞片語，仍無法提取時使用 `系統需求`。
   - 去除範本標籤、狀態說明、Markdown 標記和無關標點，儲存為單行字串，最多 40 個 Unicode 字元。
6. 使用者選擇 `其他（使用者自行輸入）` 時，必須同時取得需求 ID 和需求名稱。自由文字無法明確拆成兩個值時繼續追問一次；仍不明確就等待使用者澄清，不猜測。兩個值分別去除首尾空白，並儲存為單行字串。
7. 使用 `memory_write` 將兩個條目寫入任務作用域。寫前使用最近一次 `memory_read` 的目標 key revision：key 不存在時使用 `operation="create"` 並省略 `expectedRevision`；已有但需糾正時使用 `operation="update"` 並傳入對應 revision。不得寫入工作空間作用域。
8. 兩次寫入後重新呼叫 `memory_read`，確認任務作用域中的 `storyId` 和 `storyName` 與使用者確認值完全一致。
9. `gold-band-memory` 工具不可用或讀取失敗時，說明需求身份未讀取，並按第 3 條正常提問；任一寫入失敗或寫後核驗失敗時，說明需求身份未持久化。二者都不是阻塞，不阻斷目前角色流程。使用使用者已確認或補充提供的 `storyId`、`storyName` 繼續目前執行；後續節點仍可能重新詢問。
10. 不得直接編輯記憶檔案。需求身份取得後，採訪角色繼續原有訪談初始化，拷問角色繼續原有決策樹列舉；工具寫入成功時繼續保持任務作用域副本。
